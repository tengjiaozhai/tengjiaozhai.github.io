# 多路派生投影

## 一句话定义

一份数据被多条下游链路各自建模成不同形态（稠密向量、倒排索引、Wiki 页面、图关系），**它们之间没有主从更新关系，只有"同一个源的各自投影"关系**；改动其中一路，不会自动传导到另外任何一路。

## 我目前的判断

这套结构的价值不在于"多存了几份"，而在于**每一路都能单独失效、单独重建**。WeKnora 的分层正好是一个干净的样本：

```text
源文档 → 解析 / OCR / 富化 → Chunk
                                ├─→ Embedding（pgvector，halfvec + HNSW）
                                ├─→ 全文索引（ParadeDB pg_search，BM25）
                                ├─→ 摘要与问题生成
                                ├─→ 可选：知识图谱（Neo4j，实体/关系）
                                └─→ 可选：Wiki 页面（wiki_pages 表，slug + Chunk 证据）
```

**Chunk 是唯一的事实来源，其余五路都是它的投影。** 这条判断有三个可直接用的推论：

1. **可选的两路（图谱、Wiki）挂掉不影响主检索链。** 不配 Neo4j，向量召回 + BM25 照常工作，Wiki 页面图谱也照常能画（它靠 `wiki_pages` 表，不靠图数据库）。
2. **投影可以按公式重算，源不能。** 向量丢了能从 chunk 文本重算回来，chunk 文本丢了就只剩重传源文档 —— 这就是 [[wiki/synthesis/误删weknora知识库的恢复链路|误删 WeKnora 知识库的恢复链路]] 里"能救回 99%、原始文件救不回"的分界线。
3. **反向操作没有自动传导。** 改了 Wiki 正文，不能推断 Neo4j 的边会跟着变、向量会跟着重算、本体定义会跟着更新。每个投影各有自己的写入路径，这条必须显式写在架构文档里，否则运维会按"数据库触发器"的直觉去预期。

**两种图谱必须分开看**，这是最容易混的一处：

| | 知识图谱 | Wiki 页面图谱 |
|---|---|---|
| 节点是什么 | 业务实体 | Wiki 页面 |
| 边是什么 | 抽取出的语义关系 | 页面间的 `[[链接]]`（OutLinks / InLinks） |
| 存储 | Neo4j（可选） | `wiki_pages` 表（PG 内） |
| 不配 Neo4j 时 | 不存在 | 仍然存在 |

**图上有边 ≠ 已经抽出了业务语义关系。** 一个 Wiki 页连到另一个 Wiki 页，只证明两个 slug 被同时提到，不证明"这个实体属于那个概念"。

## 关键机制

Wiki 这一路投影的生成过程最能说明"投影"是什么意思 —— 它不是一次 map，而是五道关卡：

1. **Pass 0 抽候选**：从 chunk 里抽 `name` / `slug` / `aliases` / `description` / `details`
2. **去重身份归一**：`pg_trgm` 做候选召回（trigram 字面相似）→ 精确匹配 → 剩下歧义的交给 LLM 判（`WikiDeduplicationPrompt`）
3. **Pass 1..N Chunk 证据归因**：把 chunk 挂到候选页上
4. **Reduce 汇总**：多批结果压成一页
5. **Finalize 补链**：`injectCrossLinks` + `linkifyContent` 把正文里的实体名变成链接，`parseOutLinks` 维护 OutLinks / InLinks

其中两个设计点值得单记：

- **slug 复用 = 身份归一，slug 关联 = 页面连接。** 前者是"这两个名字说的是一件事"，后者是"这两件事有关系"。混起来就必然出现漏页或错并页。
- **`PreviousSlugs` 保标识稳定。** 改名时旧 slug 留在历史里，避免外部链接和历史证据归因断掉。
- **"相关 ≠ 相同"的判据**：RAG 与"检索增强生成"可合并（同一件事的两种叫法）；RAG 与"向量数据库"不可（手段与组件）。这条判据不是语义相似度能替代的。
- 补链范围**受当前批次限制**：只在本批候选之间建边，所以边是"部分图"，不是全量图 —— 这解释了为什么 Wiki 图看着稀疏。

配套的工程零件全在 PG 里：`pg_trgm` 的三元组索引做候选召回、JSONB + GIN `jsonb_path_ops` 存 `source_refs` 证据、版本化迁移管投影结构变更。详见 [[wiki/entities/postgresql]]。

## 我的实例

WeKnora v0.8.3 本机部署（100 个文档 / 13,901 个 chunk / 2,832 个 Wiki 页）。两个方向都验证过：

- **正向投影**：正常摄入时五路各自生成，检索侧三路（向量 / BM25 / 重排）并联。
- **反向不传导**：误删事故里，`embeddings` 是物理 DELETE（表里没有 `deleted_at`），其余四张表是软删。恢复时必须**改标记 + 按公式重算向量**两件事都做 —— 改标记不会把向量改回来，重算向量也不会把标记改回来。这正是"投影之间无自动传导"的一次实测。

## 取舍与边界

**代价是存储与一致性面成倍放大。** 五路投影意味着五种失效模式、五套重建脚本、五次一致性核对。WeKnora 用"可选"来削这个代价：图谱和 Wiki 不做也不影响主链路。

**投影的合法性依赖源字段完整。** 向量重算要求 `chunks.content` 与 `context_header` 都在；Wiki 重生成要求 chunk 引用还在。缺一个，重建出来的东西与检索侧对不上，而且是**静默不一致** —— 行数对、检索错。

**这套模型不适合"读多写少但要求强一致"的场景。** 如果下游必须实时反映上游修改，那就不是投影，是物化视图，该由数据库触发器或事务来保证，不是靠重算脚本。

**什么时候失效**：源数据本身多份（同一事实存在两个 chunk），此时投影之间会打架，且没有仲裁者。WeKnora 的答案是退回到 LLM 判重复，这是尽力而为，不是保证。

## 待澄清

- 补链范围受批次限制，那么**跨批次**的实体链接是何时补的、有没有补偿任务，笔记未覆盖。
- 落选候选（Pass 0 抽出来但没建页的实体）是被丢弃还是留存待后续批次合并，未查到代码。
- 本体层（`ontology`）与 Wiki 层的定义冲突时以谁为准，笔记只写了"五者分工"，没给冲突裁决顺序。
