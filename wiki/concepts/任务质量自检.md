# 任务质量自检

## 一句话定义

分数不对时，先证明**题目是对的**：一条任务要被两位领域专家独立判出同一结论、有一个跑得通的参考解、评分器检查的每一项都在题面里写明。三条都过了，分数才开始指代能力。

## 我目前的判断

**分数低的第一嫌疑是题面与评分器，不是模型。** 最硬的证据是 CORE-Bench：Opus 4.5 初测 42%，查出的问题是评分过僵（预期得分「96.124991…」却被扣分）、任务规范含糊、随机任务难以精确复现，再加上一个限制过多的评测框架 —— 修完后同一个模型 **95%**。48 个百分点的差距全部来自评测系统，与模型能力无关。这类差距在总分上跟「模型退化」长得一模一样，只有读轨迹才分得开。

**评分器比题面严，等于惩罚听话的模型。** METR 的时间范围基准里，任务要求「优化到某个分数阈值」，评分却要求「超过该阈值」—— 遵循指令的模型被扣分，无视既定目标的模型反而得分更高。这与 [[wiki/concepts/Agent评测]] 里「题面有歧义时，评估测的是猜出题人意图」是同一个病，只是这次歧义发生在**评分器**一侧。

**pass@100 = 0 是任务缺陷的信号，不是能力不足的信号。** 前沿模型 100 次尝试全灭时，第一反应应该是查题面与评分器（文件路径没写、验收条件没写清），而不是「模型还不行」。Terminal-Bench 的审计就抓到过：任务要求写脚本却没指定输出路径，测试却假定脚本在某个固定路径 —— agent 在并非自身过错的情况下失败。

**参考解是任务的最小验收。** 一份已知可行、能过全部评分器的输出，同时证明两件事：任务可解、评分器配得对。它比开会讨论题面有效，因为它可执行。

**部分计分不是宽容，是诊断力。** 正确识别问题、核实了客户身份、但没退成款的客服，明显好于一开始就失败的客服；二元判定把这个连续谱压成一个 0，评估就失去「改哪里」的信息。这也是 [[wiki/concepts/失败归因与回归任务]] 的前置条件 —— 全是 0 分时归因只能靠人肉读轨迹。

**只测一个方向，就只会训练出一个方向的偏置。** 只测「该搜索时搜索」，会训出一个几乎什么都搜的 agent；Claude.ai 的 web 搜索评估因此同时覆盖两类题：该搜的（查天气）与该凭已有知识回答的（谁创立了苹果）。触发不足与触发过度都要有题。

## 关键机制

**任务级三条验收**：

| 检查 | 判据 | 不合格的后果 |
|---|---|---|
| 专家同判 | 两位领域专家独立得出相同 pass / fail 结论；且他们自己能在合理时间内通过 | 题面歧义直接变成评分噪声 |
| 参考解 | 存在一份能过全部评分器的输出 | 无法区分「任务不可解」与「模型不行」 |
| 题面完备 | 评分器检查的每一项（文件路径、格式、阈值、禁用动作）都在任务描述里写明 | 模型因规范缺失而失败，被记成能力问题 |

**评分器侧的四个坑与对策**：

| 坑 | 表现 | 对策 |
|---|---|---|
| 过僵 | 预期值「96.124991…」被扣分；只认字面形式 | 用范围 / 容差；能写程序化断言就写，但别把合法变体判死 |
| 与题面不一致 | 题面说「优化到阈值」，评分要「超过阈值」 | 交付前把评分器逐条对着题面读一遍（这是 CORE-Bench 与 METR 的共同根因） |
| 不可复现 | 随机任务每次不同、无法精确重跑 | 固定随机种子或把随机化成参数化实例（见 [[wiki/concepts/评估环境设计]]） |
| 可绕过 | 改断言、加 skip、mock 掉被测逻辑 | 及格必须要求真正解决问题；测试改动本身要被检查（见 [[wiki/concepts/失败归因与回归任务]] 的 hack 类） |

**做对之后仍要防的两种系统性偏低**：

- **类别不平衡**：「该发生」与「不该发生」两类题数量要对称，只测一边会得到一个单向优化的 agent。
- **框架限制**：评测框架给的工具 / 上下文比生产少，模型做不到但被记成不会。CORE-Bench 那次修复里，除了评分与题面，也换掉了限制过多的框架。

**评分器内部的三条**（模型裁判部分）：提供「Unknown / 信息不足」的出口、每个维度用独立裁判而不是一个裁判评全部、与人类专家持续校准。这三条已在 [[wiki/concepts/Agent评测]] 的 Rubric 一节，此处只作引用。

**难度标注只给有稳定共识的任务。** 京东 OxyEcomBench 的 P0–P3 四档标尺「只应用在能够达成稳定专家共识的任务上，共识不稳定的任务不硬标难度」。理由比「宁缺毋滥」更硬：难度标签一旦是硬标出来的，它会污染分层报告 —— 按 P1 通过率 80% 得出的结论，在 P1 的定义本身不稳时没有意义。这等于承认「难度」也是一种需要验证的判断，不是出题人的感觉。

**防作弊要设计进题库，不只设计进评分器。** 京东的「视觉证据优先」：评测集优先选关键证据在图像里而不是文本里的多模态案例。因为通用模型靠文本先验就能把题蒙对，测不出真实能力。这是「抗绕过」在**选题阶段**的做法，与「评分器抗绕过」（不让人改断言、要求真跑过）互补 —— 前者让捷径不存在，后者让捷径被发现。

**专家同判要落到流程上。** VitaBench 的做法是每个任务由多名标注员 + 领域专家多次校验，同时确认两件事：够复杂、且可完成。这与本文「任务级三条验收」里那条「专家自己能通过吗」是同一条判据的工程执行版。

## 我的实例

`Agent 评测方法论.md` 附章的判据设计，本质上是一次**评分器自检**：把「有没有调搜索」换成「澄清请求是否只索要用户独占信息」。前者是过僵的字面条件（用户直接给出定义也能达成目标，却会被判失败），后者才是任务真正要求的。这是本仓唯一一条自己动手做过的自检，代价是重写一遍判据。

[[wiki/concepts/金标]] 是「参考解」在业务侧的极端形式：不只要求存在一份能通过的输出，还要求它与老系统**逐格一致**。金标比参考解贵得多，但换来的是「重构没改行为」这种强断言 —— 参考解证明任务可解，金标证明答案没变。

**本仓没有任务级验收流程。** 目前唯一的自动检查是 `tools/wiki-lint.mjs` 的六项结构校验（断链 / 孤儿 / frontmatter / 漂移 / 重复概念 / 过期），它检查的是「页面之间是否自洽」，不是「任务是否合格」；0 条业务任务、0 份参考解、0 次专家同判。这条自检对本仓还是纸面规则。

## 取舍与边界

**自检成本 ≈ 每条任务一次专家评审 + 一份参考解。** 换来的是什么：SWE-bench Verified 用 93 名 Python 开发者审 1699 条、留下 500 条（淘汰 71%），换来更高信噪比，后续评估成本下降约 80%。这是一次性支出换长期便宜，但**只有在任务会被反复运行时**才划算 —— 一次性题目不值得这么审。

**参考解不该只由出题人写**（推断，原文未提）：出题人写参考解时，会不知不觉按自己脑子里的隐含约定写，恰好绕过题面的空白。让没参与出题的人按题面写一遍，才测得出题面完备性。

**失效条件**：
- 题面完备、评分正确，但**需求本身错了** → 评估会忠实执行一个错误的需求，自检验不出这一层（那属于需求验收，不是评估验收）
- 自检只证明题目合理，不证明题库覆盖了真实分布；一份全对但没覆盖长尾的题库，自检会全部通过
- 单方向抽检：只审新题不审老题，老题会在环境变化后悄悄失效（OSWorld 发布 15 个月暴露 300 余问题的教训）

## 待澄清

- 部分计分的权重怎么定？原文只给了必要性（「在结果中体现成功与失败的连续性至关重要」），没给算法；第 7 章教材的 `reward_basis` 也只是分层聚合，不是加权方案。
- 参考解与 [[wiki/concepts/金标]] 的边界：一个证明可解，一个锁死期望输出 —— 什么任务该要求哪一个，没有判据。
- 「两位专家独立同判」在小团队只有一位领域专家时怎么降级？本仓判断可降级为「出题人与一位非出题人」，但无实测。
