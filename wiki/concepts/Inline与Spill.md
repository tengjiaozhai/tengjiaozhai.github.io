# Inline 与 Spill

## 一句话定义

把上下文窗口当 Cache 管：**Inline** = 近期很可能用到的信息直接内联进窗口，省掉一次工具往返；**Spill** = 超出预算或低频的完整信息留在窗口外，只保留引用或摘要。两者配上一个「每次召回都内联下一跳 ID」的约定，就得到**链式召回（Chain of Recall）**：对象在底层构成引用图，模型可以顺着引用逐跳展开上下文，而不是一次性把全量历史塞进窗口。

## 我目前的判断

这是 [[wiki/concepts/上下文压缩]] 的**事前**对偶：压缩处理「已经进来的历史怎么缩短」，Inline & Spill 处理「什么该进来」。两者共用一个预算，但不能互相替代 —— 压缩发生在事后，代价是信息损失与摘要漂移；Inline & Spill 发生在事前，代价是**必须预先猜对什么会被用到**，猜错就多一次工具往返。

原文给这条设计配了一句很到位的成本判断：「浪费上下文窗口，就是浪费模型的智能。」以及两个方向的失效模式：注入过多会挤占窗口、稀释注意力；注入过少会迫使模型反复调工具读取、增加执行步数。所以它不是「尽量少」或「尽量多」的问题，是**命中率**问题。

## 关键机制

三步递进（原文 §3.3）：

| 步 | 动作 | 具体做法 |
|---|---|---|
| 1 | 从最少信息开始 | 只给当前对象的 ID 与内容摘要 |
| 2 | 利用局部性逐步 Inline | 先附紧密关联对象的 ID；再附时空相邻内容 —— 内容前 50 字、IM 中前后相邻消息与所回复的消息、代码评论所在评审讨论的相邻评论 |
| 3 | 超出上限则 Spill | 设较小的长度上限，截断超出部分并保留续读入口，模型需要完整内容时再调工具读取 |

链式召回则要求一个额外约定：**每次工具召回的结果本身也遵循 Inline & Spill**，返回里内联下一跳对象的摘要与 ID。于是「当前消息 → 所在 Thread → 相关 Worker Session → 该 Worker 关联的另一个评审 Thread」这样的多跳路径可以按需展开，而不必预先装入。

这套机制的成立依赖「对象有稳定唯一 ID」：Trigger、Thread、Worker Session 都被赋 ID，注入时内联紧密关联对象的 ID，引用图才存在。

## 我的实例

- 本仓 [[wiki/concepts/游标分页]] 是同一种思路在数据库侧的写法：不取全量、只取锚点，靠「上一页最后一条」这个引用继续往下走。两者都是「用引用换窗口」。
- [[wiki/concepts/KV缓存与提示词缓存]] 关心的是同一份前缀别重复算；Inline & Spill 关心的是同一份内容该不该进来。前者是算力经济，后者是注意力经济。
- 反例参照：[[wiki/concepts/上下文压缩]] 里的摘要替换属于 Spill 的一种激进形态（原文明说「一种简单直接的做法是截断超出部分并保留续读入口」）。

## 取舍与边界

- **预测错就白花一次往返。** 「近期很可能用到」是启发式，没有可验证的判据；原文只给了局部性（时间相邻、空间相邻、引用相邻）三条经验。
- **Spill 的续读入口必须可靠。** 一旦引用指向的内容被后续操作改掉或删掉，链式召回就断链，模型会陷入「反复召回同一空结果」。这是本机制最脆的环节，原文未给处置方案。
- **链式召回有跳数上限。** 原文没给数字。跳数越多，每跳都要一次工具调用，延迟线性增长。
- **只适用于有明确对象边界的系统。** 如果系统里没有 Thread / Session / Trigger 这种可命名的对象，引用图无从建立。
- **和「把历史全塞进去」比，它的失败模式更隐蔽**：全塞会明显变慢变贵，容易被发现；Inline & Spill 猜错时只是多几次工具调用，看起来一切正常，只是慢了一点、贵了一点。

## 待澄清

- 「较小的长度上限」到底取多少？原文没有给数值，也未说明是否随模型窗口自适应。
- 长程（跨月）记忆退化问题，原文列入 §8.1 开放问题，明确说「长程记忆成为制约可扩展性的主要瓶颈」—— 也就是说链式召回只解决了「近期任务与会话历史的按需检索」。
- 若被引用对象在召回前已被删除，是否要保留 tombstone 以保证引用可解析？本仓 [[wiki/concepts/Agent团队状态模型]] 里 task 的 `deleted` 保留为 tombstone 是这个方向的一个先例，但两篇文档没有互相引用。
