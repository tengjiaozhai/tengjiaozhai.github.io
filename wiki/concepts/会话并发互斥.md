# 会话并发互斥

## 一句话定义

同一个 session 的并发控制要拆成两件事：**逻辑互斥是集群级的（Redis 分布式锁），物理句柄是进程级的（本地字典存 asyncio.Task）**。两者不是冗余，是分工严密的两级防御。

## 我目前的判断

这两件事放一起做必然错。`asyncio.Task` 是包含调用栈的内存指针，无法序列化存进 Redis，谁创建就只能活在谁的内存里；而「这个 session 只能有一个 run 在跑」是跨机器的所有权问题，必须由中心仲裁。

所以：

| 职责 | 载体 | 作用范围 | 解决什么 |
|---|---|---|---|
| 这个 session 只能有一个 run | `MessageBus.session_run` 分布式锁 | 集群级（Redis） | 逻辑所有权，防脑裂脏写 |
| 这个 session 的 task 在哪 | `ChatRunRegistry._tasks` 本地字典 | 进程级（堆内存） | 物理寻址，能 cancel 到 |

## 关键机制

**两级流水线，时序刻意错开**：

```text
[前端 HTTP 请求]
  1. chat_router.py（同步，<1ms）
     └─ chat_run_registry.spawn()
        └─ existing is not None → 抛 409 Conflict   ← 第 1 道防线：本地防抖
  HTTP 立即返回 {"status":"started"}，连接释放

[后台协程，10s ~ 60s]
  2. chat_service._run_body()
     └─ async with acquire_lock(...)               ← 第 2 道防线：集群独占
```

**为什么不能直接在 HTTP 请求里等 Redis 锁**：推理耗时 10~60 秒，HTTP 线程同步等锁会瞬间耗尽连接池。原则是「前台秒级登记占坑并返回，后台排队争锁慢慢跑」。

**spawn 撞车直接抛 RuntimeError，不重试**：

```python
existing = self._tasks.get(session_id)
if existing is not None and not existing.done():
    raise RuntimeError(f"Session {session_id!r} already has an active chat run in this process.")
```

理由：正常流程必须先抢到 Redis 锁才允许调 `spawn`。本进程发现同名活跃 Task 说明并发控制有 bug 或锁失效。**设计缺陷引起的并发冲突绝不能宽容重试** —— 排队会把 bug 掩盖成幽灵并发。

**跨进程取消用「广播 + 各查自留地」**：

```text
用户点停止 → 请求到节点 A → 广播到 session_cancel 频道
                                  ↓
                        所有节点收到，各自查本地 _tasks
                                  ↓
                        命中的节点 B 执行 task.cancel()
                        → 协程在下一个 await 退出 → finally 释放 Redis 锁
```

不做点对点寻址的理由：把 `sid → Node_IP` 存中心存储，节点崩溃会留下死指针。广播方案发起方无需维护拓扑，无状态且鲁棒。

**第 2 道防线还承担多源汇聚**：触发源不止前端 HTTP，还有定时调度器、子 Agent 唤醒、HITL 回调。它们可能由集群任意进程发起，**Redis `acquire_lock` 是唯一最终仲裁者**。

## 我的实例

- 本地防抖失效的后果：轻微性能损耗（多发一条锁请求，返回 409）
- 集群锁失效的后果：灾难性 —— 两个 Worker 同时读写 DB 会话状态，数据错乱
- Java 对标：本地 `ConcurrentHashMap.putIfAbsent(sid, task)` / Redisson `RLock`

Redis 锁本身用看门狗续期，见 `PY学习笔记.md` §「Redis 分布式锁底层实现与看门狗机制（acquire_lock）」。

## 取舍与边界

**单机部署时两级防御退化为一级**：本地字典足够，Redis 锁是纯开销。但代码不为此分叉 —— 保留统一路径，让本地防抖承担「避免无意义网络往返」的既有职责。

**「一 session 一 run」是产品约束不是技术约束**。如果将来要支持同一会话并行多条消息，这套结构需要重做：本地字典的 `session_id` key 得改成 `session_id + message_id`，Redis 锁粒度同步下沉。当前设计假定串行语义。

**已知风险**：`spawn` 抛 `RuntimeError` 后 HTTP 层返回 409，前端需要能识别并提示用户「上一条还在跑」。这条链路的前端实现未在本仓验证。

## 待澄清

- 锁超时与推理耗时谁兜底：看门狗续期防止锁提前释放，但如果进程整个崩掉，锁会等到 TTL 过期。TTL 取值与最长推理时长的关系未记录。
