# Agent评测

## 一句话定义

**评估是一份可执行的成功约定** —— 给 agent 一个输入和一个干净环境，跑完后检查环境里留下了什么状态、过程里有没有越界。它回答的不是「它看起来会做」，而是「要求什么 → 实际做了什么 → 怎么判定 → 能不能重复」。

## 我目前的判断

靠手动测和 dogfood 能走很远，问题出在上线之后：用户说「改完变差了」，团队只能等投诉、手动复现、修完祈祷别处没坏。**没有评估就分不清真实回退和噪声。**

好处是复利的：早期评估逼你把「成功」写清楚（两个人读同一份需求，对边界情况的理解可以完全不同，一套题面能消掉这种歧义）；后期换来基线 —— 延迟、token、单任务成本、错误率都能挂在固定题库上纵向对比。换新模型时差距最大：没评估的团队花几周试，有评估的几天就能判断强在哪、提示词要不要调。

**评估对象不是模型，是模型 + Harness 的组合体。** 同一个模型换一套 Harness（提示词、工具设计、反馈循环）能差出量级，所以「分数低」这个观察本身不含改进方向。区分「模型能力不足」和「Harness 设计缺陷」靠**模型替换实验（model swap）**：固定 Harness，只换更强 / 更弱的模型 —— 换强模型分数不涨，瓶颈在 Harness；换弱模型大跌，表现主要由模型决定。它和消融是两种方法：消融关掉 Harness 的某个组件（定位哪个部件重要），model swap 固定 Harness 只换模型（定位瓶颈在哪一侧）。方向判错的代价是几周：把一个 Harness 观察通道缺失记成模型能力问题，接下来会去换模型和训 OCR，而真正该改的是补通道（实例见 [[wiki/concepts/失败归因与回归任务]]）。

## 关键机制

**outcome 和 transcript 是两回事**。agent 最后说「已移到项目甲，权限不变」不算通过，判定看环境不看自述。同一句回复可以对应三种真相：

- 文档还在收件箱（只是嘴上说完成）
- 文档确实移动且权限不变（真完成）
- 文档移了但权限被改成「任何持链接的人可见」（做了一半还越界）

第三种最危险，因为它的回复字面意思和第二种完全一样。

**三类裁判的分工**：

| 方式 | 适合查什么 | 代价 |
|---|---|---|
| 代码裁判 | 目录 ID、权限集合、文件数、跑测试 | 快、便宜、可复现；只认某种字面形式，把合法变体误判为失败 |
| 模型裁判 | 开放表达：说明是否清楚、语气 | 灵活但不确定、更贵，必须人工校准；偏爱长答案，或被「我已成功」骗 |
| 人工裁判 | 争议裁决、量表是否贴合真实需求 | 金标准，也用来校准模型裁判；慢、贵，人之间会分歧 |

顺序：能用确定性代码判的用代码，开放维度用模型裁判，人工只做校准和抽检。每个维度单独跑隔离的裁判，比一个裁判评所有维度稳；量表要给「Unknown / 证据不足」的出口，否则模型会硬猜。

**模型裁判要写成 Rubric，不是打一个总分。** 四条准则（Scale AI）：基于专家指导（缺领域知识只能评出流畅度）、全面覆盖（正面标准之外要列陷阱项）、按重要性加权（必要 / 重要 / 可选 / 陷阱，支持一票否决）、每项自包含（「引用了至少两个权威理论并解释如何支持结论」而不是「展示了深刻理解」）。四档制（优秀 / 良好 / 及格 / 不及格）每档配可验证的具体行为；幻觉这类维度设 veto，一票归零，它同时是防关键词堆砌的闸门。教材的用户记忆例子里，180 次评判中幻觉否决触发 28 次 —— 这不是罕见分支。

**三类已知偏差必须写进流程**：长度偏差（偏爱更长回答 → Rubric 显式罚冗长、配对前先控长度、定期审计「高分是否总是长回答」）；位置偏差（系统性偏向先出现的候选 → 交换顺序各评一次，取平均或只在两次一致时计入）；同源偏差（Agent 与裁判同家族 → 古德哈特定律：指标一旦成为优化目标就不再是好指标，Agent 会学会绕开裁判不擅长的错误类型）。缓解手段是**多源异构评判**：不同模型家族分别评、共用同一份 Rubric、加权平均或一致性检查；部署期单模型快速评，定期用完整多源评判做审计。

**Rubric 的用处不是给分，是把笼统的失败率拆成几类可修的问题**：没检索到信息 / 人物关系想错 / 补了没依据的内容。没有这层拆分，分数只回答差多少。

**「只评产出、不评路径」有边界**。检查「必须按某顺序调工具」确实太脆，agent 经常找出设计者没想到的合法路径；但授权、必要的澄清、禁止操作这类过程约束是任务要求的一部分，本来就该查。判别方法一句话：**换一条合法路径达成同一目标，为什么它该失败？** 答不上来，这条就不该进裁判。

**pass@k 与 pass^k 选哪个看产品形态**：

```text
pass@k：k 次里至少成功一次 = 1 − (1 − p)^k   → k 越大越高
pass^k：k 次全部成功       = p^k              → k 越大越低
p = 75%、k = 3：至少一次 98.4%；全部成功 42.2%
```

允许反复生成候选稿（写代码、出方案）用 pass@k；每次都必须准确执行用户操作（客服、下单）用 pass^k。

**这两个数的距离有多大，VitaBench 给了一组实测**：跨场景任务上最佳模型 Pass@4 约 60%（四次里总有一次成），Pass^4 接近 0%（四次全成几乎不发生）；单场景 Avg@4 只有 48.3%，跨场景 30.0%。换句话说，**「能做」和「能稳定做」之间是 60% 与 0% 的距离** —— 这也是为什么面向用户的产品不能用 pass@k 汇报。

两个坑：
1. **不同题难度不同，不能把平均成功率代进公式**。两道题 p 分别是 100% 和 0%，平均 50%；各跑两次逐题算再平均还是 50%，把 50% 代进公式却得到 75%。
2. **独立性是假设不是事实**。共享缓存、同一服务故障、上一轮留下的文件都会让试验不再独立。

**能力集 vs 回归集**：能力集问「现在能做到什么」，放还做不稳但产品真正需要的题，起点就该低通过率；回归集问「以前会做的现在还做不做」，通过率接近 100%，掉分说明有东西坏了。两个都要跑。

**两集之间有毕业机制**：能力集里通过率达到高水平的部分，可以转成持续跑的回归集 —— 问句从「能不能做到」变成「能不能稳定做到」。反过来不行：回归集不该塞没跑通的能力题，否则掉分时说不清是退步还是根本没学会。

**题源有三个，不是一类**：公开基准（粗筛模型、借鉴设计手法，不用于产品决策）、自建业务集（覆盖真实分布，选型与 Harness 决策的依据）、生产轨迹回流（线上真实失败 → 归因 → 回归用例；成本最高、准确度也最高，系统跑稳后成为主体）。这与「能力集 / 回归集」是两个正交的轴：前者说题从哪来，后者说这批题用来问什么。

**分数差异要先扣噪声再谈结论**：n 道题上成功率 p，标准误 `SE ≈ √(p(1-p)/n)`。100 题、70% 时 95% 区间约 ±9 个百分点（教材原文此处印作「约为 70 个百分点」，按公式重算应为 ±9，疑为裁剪丢符号），所以「新模型 73% 对旧模型 70%」不足以支持切换。同一批题比两个配置要做**配对分析**：逐题记录谁胜出，用 McNemar 或 paired bootstrap，而不是相减两个独立成功率；每个配置跑 3–5 个随机种子，报均值与波动，单次运行只用来筛方向。判据三条：分差超过噪声、在配对分析中成立、能复现。并行验证多个假设还要收紧阈值或对正向结果独立复跑。

**另一个正交的四层**（业务视角，来自美团）：结果层（任务是否完成、输出是否可用）、过程层（规划是否合理、步骤是否稳定）、效率层（耗时 / token / 工具调用次数）、风险层（越权、误操作、安全隐患）。它与 τ²-bench 那四层（终态 / 关键动作 / 告知 / 断言）不是替代关系 —— 那边切「检查什么」，这边切「从哪个视角看」。

**「评过程」与「不评路径」并不矛盾，但边界要说清**：反对的是「必须按某个顺序调工具」这类固定路径断言（合法路径会被误杀），要的是「过程可见 + 行为维度可评」—— 步骤是否稳定、是否在重复无效操作、耗时与 token 是否可接受。美团的过程层与 VitaBench 的轨迹 rubric 都属于后者。分界线仍是那句：换一条合法路径达成同一目标，为什么它该失败？

**按 agent 类型选评分器组合**（没有通用配方，只有配方模板）：编码 = 单元测试（FAIL_TO_PASS / PASS_TO_PASS）+ 代码质量 rubric + 静态分析；对话 = 终态状态检查 + 轮数约束 + 语气 rubric + 第二个模型扮演用户；研究 = 论断是否有检索到的资料支撑 / 关键事实覆盖 / 来源质量 / 客观题精确匹配；计算机使用 = 真实或沙盒环境 + 后端状态验证（订单真下了，而不只是页面出现）。

**评估只是六种信号之一**（瑞士奶酪模型：没有哪一层能发现所有问题，靠叠加互补）：

| 方法 | 强项 | 盲区 |
|---|---|---|
| 自动化评估 | 快、可复现、每次提交都能跑、完全不碰真实用户 | 前期投入大、需持续维护、与实际使用模式不符时会造成虚假自信 |
| 生产监控 | 大规模真实行为，能发现合成评估漏掉的问题 | 被动；问题在你知道之前已经影响了用户；信号有噪声；缺基准 |
| AB 测试 | 真实用户结果（留存、任务完成率），能控制混杂因素 | 慢（数天到数周），要足够流量；看不到「为什么变」 |
| 用户反馈 | 预期外的问题，附带真实案例 | 稀疏、自选择偏差、偏向严重问题、极少解释原因 |
| 人工转录审核 | 培养对失败模式的直觉，校准「好」的标准 | 耗时、不可扩展、覆盖不一致、审阅疲劳 |
| 系统性人体研究 | 黄金标准，能处理主观任务，用来校准模型裁判 | 贵、慢，评审间分歧要协调，专业域必须请专家 |

阶段分工：自动化评估放在 CI / 发版前当第一道防线 → 上线后用生产监控抓分布漂移 → 有流量后 AB 验证重大变更 → 用户反馈与转录审核常态进行 → 系统性人体研究只在校准裁判与判定主观输出时动用。这条与 [[wiki/concepts/内部评估基础设施]] 是同一件事的内外两面：那边讲产品内建的开关与实验，这边讲「用什么尺子量」。

## 我的实例

`output/agent-evals.html`（见 [[wiki/outputs/图解索引]]） 是本仓这套方法的交互式讲解（两份讲解比较 → 三种真相切换演示 → 术语与裁判分工 → pass@k / pass^k 交互曲线 → 四类 Agent 证据表 → 0→8 落地路线 → 诊断反例表 → 自测题）。

从零开始的 8 步，每步留一个可检查的产物：0 早点开始（20~50 条从真实失败里挑的任务）→ 1 先搬手动测的 → 2 写明确的题面（两个领域专家独立判分会得出同一结论）→ 3 两边都要测（「该发生」和「不该发生」）→ 4 环境要隔离 → 5 裁判防绕过 → 6 读 transcript → 7 盯饱和 → 8 长期维护。这套 8 步的第一手出处是 [[wiki/sources/demystifying-evals|Anthropic 原文]]（2026-01）；第 2 步现在有了可操作的验收 —— 参考解、专家同判、pass@100=0 报警 —— 见 [[wiki/concepts/任务质量自检]]。原文还有一条本仓没用的形态：**评估驱动开发**，先写评估定义计划中的功能再实现；能力评估因此等于「对模型几个月后性能的押注」，新模型发布时跑一遍就知道押对没有。

**一次 badcase 的判定样例**（见 [[wiki/sources/agent-评测方法论]] 附章）：agent 遇到公共可查的陌生模型名，未检索就向用户索要定义。判据不能写成「有没有调搜索」——用户直接给出定义也能达成目标，那是过度贴合路径；该判的是「澄清请求是否只索要用户独占的信息」。归类为回归集掉分（工具与权限都在），不是能力缺口。口径用 pass^k，否则第二轮补上搜索就把 0 洗成 1。

**分数骗人的四种解释**：agent 变了 / 题目变了 / 裁判变了 / 环境变了。所以先读失败证据，再解释聚合分数。

## 取舍与边界

**评估成本会随规模线性增长**。数百道题 × 多次 trial × 长 transcript，单次全量评估的成本可能高于一次发版。所以能力集和回归集要分开跑，回归集不必每题跑 k 次。

**模型裁判必须持续校准**。裁判本身是模型，会漂。人工抽检不是可选项。

**与金标的分工**：金标（见 [[wiki/concepts/金标]]）锁确定性部分，评估管决策质量。混在一起会让两边都做不好。

**失效条件**：
- 题面有歧义时，评估测的是「agent 能不能猜中出题人的意图」，不是能力
- 环境不隔离时，agent 可能翻上一次试验的 git log 占便宜（内部评估里真实出现过）
- 接近饱和时，能力的大提升只表现为分数小涨（Qodo 起初低估 Opus 4.5 就是原因：一次性的编码题测不出长任务的收益）
- **模型给出比题面更好的解时，评估会判它失败**：Opus 4.5 在 τ²-bench 的订票任务里发现政策漏洞、给出了对用户更好的方案，按题面仍是失败。静态评估只认预设的成功形态，这是它换取跨模型可比性付的代价
- **评分器与题面不一致时，评估在惩罚听话的模型**（CORE-Bench 初测 42% → 修完 95%，48 个百分点全部来自评测系统），详见 [[wiki/concepts/任务质量自检]]
- **线上低通过率更可能是评测自己错了**：淘宝的流程类域早期通过率极低，逐层排查后根因是 Prompt 不适配线上数据（数据层），不是 Agent 差。做法是把归因顺序倒过来 —— 先排除数据层 / Prompt 层 / Rubric 层，剩下的才算 Agent 缺陷，见 [[wiki/concepts/在线评测]]
- **「证据不足就判 N/A」会悄悄抬高通过率**：N/A 样本不进分母，踢得越多分母越小。这条没人讨论过，是本仓推断，见 [[wiki/concepts/在线评测]] 的失效条件

## 待澄清

- **Release Gate（发布门禁）仍未覆盖**：现在有了「分差超过噪声 + 配对成立 + 可复现」三条判据，但没有门禁阈值、没有自动化形态。
- `Agent 评测方法论.md` 标注为「后续可扩展」的 SWE-bench / LLM-as-Judge / 分层 Rubric，口径已由 [[wiki/sources/ai-agent-book-chapter7|第 7 章]] 补齐（见上），但那本书的配套实验未在本仓复跑，数字转引不转验。
- 评估套件的成本控制策略有一半了：纯随机采样的样本量算法（±1pp≈4k / ±0.5pp≈15k）、数仓与推理解耦、按域独立 workflow 并行、错峰调度 —— 但「采样科学化」（用更少样本拿同等精度）、级联 Judge、Batch API / Prompt Caching 三家都还在规划中。
