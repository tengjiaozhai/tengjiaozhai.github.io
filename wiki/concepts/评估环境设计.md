# 评估环境设计

## 一句话定义

能让同一个 Agent 从同一个初始状态出发、得到可比较结果的一整套装置：**数据集、可重置的环境状态、两套原子工具、评分标准、执行协议** —— 五样缺一，评估就从「装置」退化成「演示」。

## 我目前的判断

**五要素是最小完备集，不是清单。** 缺「执行协议」时评估变成「扔进沙盒随便跑」，同一次失败没法判断是能力问题还是聊太久被判失败；缺「可重置」，两次运行根本不在同一条起跑线上。本仓此前对评估的讨论全在「评分标准」这一格上（裁判、量表、口径），另外四格是空的 —— 这正是为什么 [[wiki/concepts/Agent评测]] 的 8 步路线里「环境要隔离」总像一句口号。

**工具抽象层次决定了评估到底在测什么。** 工具给到「解决用户上网问题」这种高层抽象，规划与推理就被工具本身吸收了，测出来只剩单次函数调用的正确性。教材这条（两侧工具都必须是原子操作）比它看起来严格：它约束的不只是工程整洁，是评估的有效性。

**人机交互型与工具调用型的分野不是难度，是有没有交互对象。** 前者验「引导」，后者验「行动」，评分标准形态完全不同：前者要 actions / communicate_info / nl_assertions 这些过程维度，后者一段测试代码或终态断言就够了。拿同一套量表去评两类任务，是把沟通能力折算成分数，必然失真。

**双控（Dual-Control）是这次真正新学到的东西。** 让模拟用户也持有一套工具（查状态栏、开关飞行模式、重插 SIM、跑测速），评估目标就从「Agent 说对了」升级为「Agent 读到了用户侧的真实变化」—— 用户改完状态，Agent 必须重新调工具才能知道结果。单控环境里 Agent 完全可以凭想象推进，且这一点在轨迹里看不出来。

**渐进式信息透露要建模成字段，不能靠提示词。** τ²-bench 把用户认知拆成 `known_info` / `unknown_info` / `task_instructions`：故障原因（飞行模式开着、漫游关着）不在 `known_info` 里，Agent 只能问出来。写成「不要一次说完」的提示词约束是同一件事的脆弱版本 —— 提示词会被模型忽略，字段不会。

## 关键机制

**五要素在 telecom 一条任务里的落位**：

| 要素 | 实例里的形态 | 缺了会怎样 |
|---|---|---|
| 数据集 | 一条 JSON：工单 + 用户剧本 + 初始动作 + 验收标准 | 无法批量、无法统计 |
| 环境状态 | 客户 / 线路 / 套餐 / 账单 + 设备侧开关与余量，`initialization_actions` 负责重置 | 两次运行起点不同，结果不可比 |
| 工具接口 | Agent 侧（查客户、查用量、充值、转人工）+ 用户侧（查状态栏、开关、测速），全是原子操作 | 规划被工具吸收 |
| 评分标准 | 四层检查 + `reward_basis` 聚合规则 | 只能靠人看 |
| 执行协议 | 模拟用户输出 `###STOP###` / 轮数上限 / 耐心耗尽即记失败 | 不知道一次运行何时算结束 |

**四层检查的分工**：`env_assertions` 验终态（数据可用、测速 ≥200 Mbps 且评级 excellent）、`actions` 验关键动作是否发生、`communicate_info` 与 `nl_assertions` 验必要信息是否告知。`reward_basis` 决定用哪几层聚合成一个二元奖励 —— 也正是它让「一次发两个工具调用」这类政策违规漏网（教材自己点破了这个代价）。

**两类环境**：交互型（有对话对方，验沟通策略）与工具调用型（只有工具，验可观测状态变更）。后者省掉用户模拟器，其余四要素仍在：环境状态是文件系统 / 数据库，评分标准是一段测试代码，执行协议退化为「持续调用工具直到给出答案或耗尽轮次」。

**工具调用型的四种粒度**（Verifiers 框架）：

| 环境类型 | 状态保持 | 工具调用 | 典型用例 |
|---|---|---|---|
| SingleTurnEnv | 无 | 无 | 单轮问答、数学题 |
| ToolEnv | 无 | 多轮 | 搜索 + 信息综合 |
| StatefulToolEnv | 有 | 多轮 | 改数据库记录后验状态变化 |
| SandboxEnv | 有 + 隔离 | 多轮 | 沙盒里跑代码后查输出文件 |

这套分档的价值在于**它把「我要造一个多复杂的盒子」变成一个选择题**：先问要不要保持状态、要不要隔离，环境类型就定了。

**终止信号是协议的一部分**：正常终止（`###STOP###`）、轮数上限、以及模拟用户耐心耗尽主动结束 —— 沟通效率过低本身计为失败。把「太啰嗦」写成失败条件，是交互型环境独有的设计。

**任务复杂度可以被算出来（VitaBench 的三维框架）** —— 本仓此前把难度当标签，VitaBench 把它当变量：

| 维度 | 可量化指标 | 在 VitaBench 里的实现 |
|---|---|---|
| 推理复杂度 | 观测空间大小、部分可观测度、推理点数量 | 单任务涉及 5–20 个服务商、最多 100+ 候选产品；跨场景任务平均 9.7–10.3 个推理点 |
| 工具复杂度 | 工具图的顶点 / 边规模、调用链路长度、子图覆盖率 | 66 个工具、512 条依赖边，领域规则编码进图 |
| 交互复杂度 | 用户画像、行为属性（情绪 / 交互模式）、动态状态演化 | 每任务一个用户角色，由 User Simulator 扮演 |

三维各自被消融验证过：推理点越多成功率越低；66 工具 512 边的最难；**去掉用户模拟器（直接给完整指令）成功率升 15–25 个百分点**。最后这条是「交互复杂度不是装饰」的硬证据，也把「模拟用户只是让评测更真实」这种软性说法量化了。

**模拟器与评估器都要单独验可靠性**：VitaBench 给用户模拟器算信息保真度（9.48/10）与人格一致性（9.34/10），给滑动窗口 rubric 评估器算与人工标注的 Cohen's κ（0.828），并与「无 rubric / 无滑窗」的基线对比。这条补上了本页原来那个空 —— **模拟用户的质量怎么验证，现在有一个可抄的做法**。

**从评估环境到仿真环境**（本篇的出口，接第八章）：评估考几百分就够出结论，训练要喂上百万次 episode，于是提出两条新要求 —— **可靠的 reset 语义**（否则上一轮的残留状态污染梯度）与**远高于评估的吞吐**（并行度、单实例开销）。同时，一套定义清晰的验证器 / Rubric 本质上就是可验证奖励（RLVR）的奖励函数：验证脚本直接就是奖励脚本。这是「评估资产」能转成「训练资产」的唯一接缝。

## 我的实例

本仓最接近「评估装置」的是 [[wiki/concepts/金标]]：确定性夹具逐格比对，功能上等价于 `env_assertions` 那一层。它没有执行协议、没有交互对方、没有工具接口，所以只能锁住「LLM 参与之前」的那段计算 —— 这个边界金标页已经写明，此处只是把五要素的视角补上。

**本仓没有交互式评估环境，也没有任何可重置的评估沙盒。** `output/agent-evals.html` 讲的是方法论，不是装置；已建的评估资产只有题库口径（能力集 / 回归集）与一条 badcase 样例。

教材里 AndroidWorld 的 4 项 Wi-Fi 子集给了「装置的最小可用形态」示范：范围压到 4 个任务 × 配对对照，成本可控到一个人跑完，也能分辨「看不见界面」和「不够耐心」两种病因。这条路径（先小范围判病因、再谈整体水平）比一步到位搭大环境更贴近本仓现状。

## 取舍与边界

**交互式环境的成本是三份**：模拟器（本身是个 LLM，要写剧本还要防它被说服）+ 双套工具 + 重置脚本。这也是为什么先有客服、终端、GUI 这些高价值域，而不是先有通用环境。

**五要素是参照框架，不是验收清单**：AndroidWorld 没有用户模拟器，仍有五要素中的四个；把「必须五样齐全」当门槛，会把一类有效评估排除掉。

**失效条件**：
- 重置脚本不完备 → 残留状态污染。与「环境不隔离时 Agent 会翻上一次试验的 git log」是同一个病，只是那次是 Agent 主动作弊，这次是装置自己漏了
- 工具侧错误只返回一个失败标志而不是清晰错误 → Agent 无从调整策略，失败轨迹变成噪声
- 模拟用户本身未经验证：教材思考题 4 提了「如何验证模拟用户的质量」（它可能系统性低估情绪激动、表达不清的用户），没有答案

**不要把「加了个模拟用户」当成环境升级**。真正升级的那一步是双控 —— 用户能改状态，且 Agent 必须重新查才知道。

## 冲突

> ⚠️ 领域规则放在哪里，两种做法互斥。两边都保留，未定论。

**观点 A（policy 文档）**：把业务规则写成一大段 Agent 政策文本随任务下发（[[wiki/sources/ai-agent-book-chapter7|第 7 章]] 的 τ²-bench telecom 领域）。好处是**可读、可审计、贴近真实岗位 SOP**；代价是教材自己点破的 —— 政策里的违规（一次发两个工具调用）验证器抓不到。

**观点 B（编码进工具图）**：把领域规则编码进工具依赖图，让模型通过工具描述自行推理（[[wiki/sources/vitabench|VitaBench]] 明确「避免冗余的领域策略文档」）。理由是 policy 文档会 ①限制探索空间 ②把「长文本指令遵循能力」混进结果 ③让难度被文档写法左右。

分歧点：**规则是「给模型读的约束」还是「环境结构的一部分」**。A 认为约束必须显式，否则无法判违规；B 认为约束应内化进环境，否则测到的不是领域能力。

待验证：同一批任务做成 A/B 两种形态，比较 ①分数差异是否只来自指令遵循 ②政策违规捕获率 ③跨模型排名是否稳定。本仓无此实验。

## 待澄清

- 双控环境的工具面要多大？τ²-bench 的 telecom 给了 4 个用户侧工具，其他领域（金融、医疗）的等价集合没有参考。
- 模拟用户的信息透露策略与真实用户差多少，结论就不可用？没有阈值。
- reset 的完备性判据：哪些状态必须重置、怎么证明没漏。教材只说「可靠的 reset 语义」，工程上怎么验收未写。
