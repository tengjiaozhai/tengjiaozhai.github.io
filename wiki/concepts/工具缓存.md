# 工具缓存

## 一句话定义

agent 工具返回的数据要不要缓存、缓在哪一层，由**两个问题**决定，与「查库贵不贵」无关：读方是否只有当前会话的 Agent 实例？数据有效期是否约等于会话期？

## 我目前的判断

两个问题都答「是」→ 放会话上下文（同会话缓存）；任一答「否」→ 放 Redis（跨会话缓存）。

这条判据的根源不在性能，在**失效成本**：会话级缓存是「写方和读方拿着同一个对象」，所以失效只需置 null，成本极低；一旦共享边界跨到别的 Agent 实例或别的会话，够不到对方的缓存，就只能靠 TTL 和写路径自觉维护。

## 关键机制

| | 同会话缓存（`AgentSessionContext`） | 跨会话缓存（Redis） |
|---|---|---|
| 载体 | volatile 字段 / `ConcurrentHashMap` | key: userId（按 provider 隔离） |
| TTL | 免 TTL、免序列化 | 按业务寿命：30min 画像 / 24h 中间结果 / 7~30d 凭证 |
| 生命周期 | 随会话销毁，新会话自动回源 | 需显式失效 + TTL 兜底 |
| 一致性 | 置 null / 覆盖（写方拿得到同一对象） | 写路径失效 + TTL 兜底 |
| 免疫外部修改 | 天然免疫 | 有陈旧风险 |
| 故障行为 | — | Redis 挂了当 miss 回源，不阻断 |

读路径：`get → 命中返回 → miss 查 MySQL → 回填`。写路径：`成功后置 null`（不是更新）。

## 我的实例

`gogo-agent` 的两层：

- 政策、用户信息、订单等读工具的返回值 → `AgentSessionContext` volatile 字段
- 用户画像、中间计算结果、第三方凭证 → Redis，key 按 `userId` / `provider` 隔离，凭证只存密文

`thoughts/039_✅使用缓存减少工具重复调用`（109 行）是同一机制在 LLMentor 里的落地记录。

跨层接力的实例：`ItineraryPlannerTool` 算完写 Redis，`ItineraryReviewTool` 从 Redis 读 —— 两个工具不共享会话对象（可能是不同子 Agent），见 [[wiki/concepts/Skill-vs-Tool]] 的引用链设计。

## 取舍与边界

**工具缓存与 LLM 提示词缓存是两件不同的事**，容易混。工具缓存省的是数据库/外部 API 调用；提示词缓存省的是模型侧的 KV 重算（见 [[wiki/concepts/KV缓存与提示词缓存]]）。两者失效机制相反：工具缓存靠 TTL，提示词缓存靠前缀逐字节稳定。

**不该缓存的工具返回值**：
- 写操作的回执（缓存了会让模型以为写成功了）
- 强实时数据（航班/景点/天气），缓存等于骗模型
- 幂等键的生成结果（会让第二次调用复用同一个键，反而破坏幂等）

**同会话缓存的隐藏风险**：`volatile` 字段在多线程/多协程下不保证可见性。当前实现依赖「同一 session 只跑一个 run」（见 [[wiki/concepts/会话并发互斥]]），一旦这个约束放开，缓存一致性会出问题。

## 待澄清

- 写工具的失效策略只有「置 null」一种。如果写路径失败但已经置 null，会话内会重复回源，没有观察到实际影响。
- Redis 缓存穿透（大量 miss 同时打到 DB）本仓未见防护措施。
