# 工具熔断

## 一句话定义

对 agent 工具的熔断，落点不是「拦截调用后报错」，而是**把工具从模型可见的 toolkit 里卸载** —— 模型看不见它，自然不会调用它。

## 我目前的判断

传统微服务的调用方是固定代码，知道「调用失败就换策略」，所以熔断器拦住请求、返回降级结果就够了。agent 的调用方是 LLM，它的决策依据是**下一轮可见的工具清单**。报错对它只是又一条 Observation，它会在 30 轮迭代里反复选同一个坏工具。

所以工具熔断必须前移：从「每次调用后的惩罚」改成「下一轮决策前的预防」。状态机只在 Redis 记账，真正的执行动作是改变 LLM 每轮可见的工具清单。

## 关键机制

**三态由 Redis 推导，不存显式标记位**：

```text
OPEN      = gen:{tool} hash 里存在 at 字段（开启时间戳）
HALF_OPEN = OPEN 且冷却期已过        ← 推导，无显式存储
冷却时长   = min(initial × multiplier^(代数-1), max)
每 tool 仅 2 把 key：fail:{tool} 计数 / gen:{tool} 代数+开启时间
```

**两个 hook 职责刻意不对称**：

| | PostActing（工具执行完） | PreReasoning（模型思考前） |
|---|---|---|
| 角色 | 写路径：统计 + 触发熔断 | 读路径：状态机唯一权威 |
| 计数失败 | 连续失败达阈值 → 原子脚本进 OPEN | 只读 Redis |
| 半开失败 | 代数 +1、刷新时间戳、**立即**卸载 | — |
| 半开成功 | 清 OPEN + 重置计数，**不碰 toolkit** | — |

三条由此推出的规则：

1. **熔断要立即生效，恢复要延迟统一做**。熔断若等到下一轮 PreReasoning，模型可能带着旧清单再调一次坏工具；恢复晚一拍无害，冷却期内工具本就不该可见。
2. **恢复只在 PreReasoning 做**。「组里有什么」只有一个权威来源，避免在事件回调里反复 addTool 造成抖动。
3. **操作只作用于自己的 group**。只有被点名放进熔断组的工具才会被熔断，基础设施工具（DB/缓存）不参与，避免熔断把自己打死。

**为什么状态放 Redis 而不是进程内 Map**：多实例共享同一份熔断视图（重启不丢）、`INCR`/`HINCRBY` 天然原子、TTL 自动清理脏数据。并发一致性靠 Lua 脚本把「计数+续期」「代数递增+时间戳写入」各放在单次脚本内完成，避免「代数已增但时间没记上」的半状态。

## 我的实例

`ToolCircuitBreakerHook`（gogo-agent）：

- `agent 开发学习笔记.md` §7 的并行开关 `ToolkitConfig.parallel(true)` 只管并行，熔断是独立 hook，两者正交
- 白名单 `monitoredToolNames` 只点名外部实时源 `destinationLiveTools`（航班/景点/酒店）
- 保守判错：只认框架统一前缀 `Tool execution failed`，不识别具体业务字段
- 极端兜底：OPEN 冷却中仍被调用 → WARN（说明 LLM 在熔断前已决策调用）
- 失败静默：group/toolkit 为 null 时跳过，熔断机制自身的故障不影响 agent 主流程

配套的退避专题见 `output/tool-circuit-backoff.html`（代数阶梯 + 存代数 vs 现算冷却 + 三段真实代码 + 五个设计决策）。

## 取舍与边界

**已知留白**：配置里定义了 `excludeToolNames` 黑名单字段，但 hook 目前只解析白名单，黑名单未接入。

**什么时候不适用**：
- 本地稳定工具（查政策、查订单）不该进熔断组 —— 它们失败是 bug 不是外部故障，熔断只会掩盖问题
- 单实例部署时 Redis 是过度设计，进程内 Map 够用；但多实例下必须共享
- 熔断无法区分「工具坏了」和「参数传错了」。如果模型每轮都传错参数，熔断会把一个好工具摘掉。这是白名单策略的代价：只对已确认会因外部故障反复失败的工具开启

## 待澄清

- 半开探测只给一次机会（冷却期过后自动加回）。如果外部服务恢复但首探仍失败（比如冷启动慢），会重新熔断并翻倍冷却。是否需要「半开期允许 N 次探测」未验证。
- 代数自增的封顶值取多少没有依据，当前是配置项。
