# 向量库选型

## 一句话定义

选型的多数判断和「哪家检索更准」无关，而由**形态、一致性和运维**决定。规模不是主要决策点。

## 我目前的判断

四个库不是同一类东西，**形态决定运维成本、一致性模型和规模上限**：

```text
Qdrant   独立专用服务（Rust）       → 生产独立 RAG 的首选答案
Milvus   分布式专用服务（存算分离） → 为十亿级与水平扩展而生，运维最重
pgvector PostgreSQL 扩展           → 向量只是表里的一列，无新服务
Chroma   嵌入式客户端库            → 零配置，向量界的 SQLite
```

**规模不是主要决策点**。对数刻度看：Chroma ≤ 100 万 → pgvector/Qdrant 千万级 → Milvus 亿级以上，每格差一个数量级。但绝大多数业务 RAG 落在 100 万~1000 万区间，四个库都覆盖。真正拉开差距的是运维负担与下面两个分水岭。

## 关键机制

**分水岭一：混合检索（稠密 + 稀疏 + 重排）**。稠密向量懂语义不懂字面，稀疏向量精确命中词但不认同义词，互补才有完整召回。

```text
Qdrant   原生：稀疏向量 + 命名多向量 + Query prefetch，RRF 融合
Milvus   原生：sparse/dense 字段 + Ranker（RRF/加权）
pgvector 无原生；0.7+ 有 sparsevec 类型，需自行拼 BM25 + vector 再融合
Chroma   无
```

**分水岭二：元数据过滤**。Qdrant 的过滤与 HNSW 集成（过滤感知遍历，payload 过滤是招牌）；Milvus 有倒排/位图标量索引和表达式过滤；pgvector 过滤就是 SQL WHERE，最灵活但 KNN 非过滤感知，强过滤时查询计划会退化；Chroma 无专用过滤索引，过滤越强越接近暴力扫描。

**一致性光谱（最容易被忽略）**：

```text
pgvector 完整 ACID ──→ Qdrant 单机强一致 ──→ Milvus 近似最终 ──→ Chroma 无事务
  （同库事务、         （WAL 崩溃恢复，    （TSO 时间戳，删除/       （单写进程，
    与业务数据原子提交） 集群 Raft 复制）      索引生效有延迟）          崩溃丢未落盘段）
```

向量数据「看起来查到了」时错误不明显，但删改是否即时生效、能否和业务数据原子提交，在生产里会踩实坑。

**决策树**：

```text
① 向量要和业务数据同库 JOIN / 同一套事务、备份？
   需要 → pgvector（别家都做不到同库事务）
② 几天内出 demo / 本地工具？
   是 → Chroma；要平滑转生产可直接用 Qdrant 内嵌/小容器起步
③ 规模与扩展预期？
   千万级以内单机够 → Qdrant
   亿级以上/多副本/GPU → Milvus
   已有大规模 PG、不引新组件 → pgvector（接受混合检索自建）
```

## 我的实例

**手头服务器的实际盘点**（2026-10 状态）：

```text
已有：Milvus standalone（Dify 依赖，19530 端口，占 ~3.6G 内存）
      PostgreSQL 容器（Dify 内部网络，未映射宿主机）
没有：Qdrant / Chroma / Redis
```

AgentScope 的 `main.py`：Redis 是硬依赖（`RedisStorage` 存会话/凭据/agent 状态），向量层默认 `QdrantStore(location=":memory:")` —— 进程内嵌模式，零外部依赖。

结论：演示级 RAG 不用装任何向量库；要持久化时新开独立 Qdrant 容器（6333 端口空闲），比往共享的 Dify Milvus 里灌数据更安全 —— 隔离、可卸载。

**经验法则**：记忆层起步用进程内嵌或单容器，量到百万级以上、过滤与混合检索成为硬需求时再上专用服务；先被 Redis 这类「必须件」，后补「可选件」，避免为一个演示需求引入一套分布式运维。

`thoughts/095_✅接入RAG 知识库，让 Agent 拥有领域知识` 是同一套选型在 LLMentor 项目里的落地。

## 取舍与边界

**「已经有 Milvus 了所以用它」是陷阱**。共享实例的运维风险由所有使用方共担：Dify 升级会动到你的索引，你的写入会占用它的资源。隔离比复用更重要。

**pgvector 的唯一优势是同库事务**。如果业务数据本来就不在 PG 里，这个优势不成立，pgvector 就退化成「一个性能一般的向量索引」。

**Chroma 不适合生产**。无事务、单写进程、崩溃丢未落盘段。它的定位是本地工具和 demo，不是生产存储。

**Milvus 的运维重量容易被低估**：etcd + 对象存储 + 消息队列 + 多类节点。单人维护一套 Milvus 集群的成本可能超过它带来的检索收益。

## 待澄清

- Qdrant 集群版（Raft 复制）的实际运维体验本仓无记录，当前只用到单机。
- 各库的中文/中英混合检索效果差异未实测。
