# 上下文压缩

## 一句话定义

会话长度超过模型窗口后，用「摘要 + 卸载」替换历史原文，让 agent 能在有限上下文里继续跑。压缩不是删除，被卸掉的内容要用可回查的引用保留。

## 我目前的判断

四套方案的差异不在「用哪个摘要提示词」，而在**三个结构选择**：

1. **压哪里**：历史工具消息 / 大消息 / 历史轮次 / 当前轮
2. **怎么保证不丢**：卸载到 map + UUID 回查，还是原地覆写
3. **失败了怎么办**：事务式回滚，还是接受半成品

其中 (3) 最容易被忽略，也是 Grok Build 与本仓其他方案拉开差距的地方。

## 关键机制

**pi 的六层渐进式**（AgentScope 1.x `AutoContextMemory` 系列）从温和到激进依次：

| 层 | 动作 | 关键阈值 |
|---|---|---|
| 1 | 压缩历史工具消息（合并重复调用、保留写操作细节） | — |
| 2 | 大消息卸载（超 `largePayloadThreshold` 默认 5KB → 存 map + 前 200 字符预览 + `<context_offload uuid>`） | 保护最近 `lastKeep` 默认 50 条 |
| 3 | 同第 2 层但 `lastKeep = false`，搜索范围扩到最近 50 条 | — |
| 4 | 历史轮次摘要（整轮压成一段，不提工具） | — |
| 5 | 当前轮大消息 LLM 摘要（保守，明确提示「来自当前轮」） | — |
| 6 | 当前轮整体压缩，**比例化**：目标 = 原字符数 × `currentRoundCompressionRatio`（默认 0.3） | — |

设计逻辑是「能用温和方式解决就不要用激进方式」：策略 2 找到可卸载内容就返回，无功而返才落到策略 3。

**Grok Build 的两层 + 四模式 + 三守卫**：`select → fit → sample → guard → commit` 五步流水线，四种压缩模式决定「压哪里」，三个守卫做补偿设计，回滚是**事务式而非撤销式**。

**共同的硬约束**：卸载后的引用必须能被拉回。第 2/4 层的 `offloadContext` map 存原文，`<context_offload uuid="xxx"/>` 是回查入口 —— 压缩丢的是可见性，不是数据。

## 预算分配（压缩的另一面）

压缩解决「装不下怎么办」，预算分配解决「该装什么」。两者是同一个东西的两端：都是上下文选择器——一个在超限后动手，一个在装配时切分。本仓此前只有前者的记录。

`llm_wiki` 给的是一套显式比例（[[wiki/sources/llm-wiki-app-readme|README]] §7、§17）：窗口 4K–1M 可选，按 **60% wiki 页 / 20% 聊天历史 / 5% index / 15% 系统提示** 切分，页面按「搜索分 + 图关联度」综合排序后填空。

**与上面四方案的差别**：pi / AgentScope 1.x / 2.0 / Grok Build 都在「超出窗口后做什么」上做文章，都不管「没超出时怎么分」。比例是**前置**约束，压缩是**兜底**约束，同一个库里可以共存——先按比例装，装满了再触发压缩。

**边界**：固定比例在小窗口下会把 wiki 页挤没（4K 窗口的 60% 只有 2.4K）。本仓实际用法是「读 index + 按需读页」，等于把选择权交给检索而不是比例——这解释了本仓为什么长期不需要预算概念。

**待澄清**：本仓未实测比例分配与「全给 wiki 页」的召回差异；README 的 58.2%→71.4% 是向量检索的对照，不能拿来支持或否定比例分配。

**成本侧的实测补充**：压缩与缓存合用时收益不可相加 —— 仅压缩历史省 17.5%、仅稳定前缀省 28.3%，两者合用只省 30%，因为压缩本身就缩短了可命中缓存的前缀（详见 [[wiki/concepts/KV缓存与提示词缓存]]）。所以「压缩越勤越省」不成立，压缩频率要按「省下的输入 token」与「打掉的前缀命中」净算。

## 取舍与边界

**压缩阈值调太低会毁掉推理质量**。压缩摘要是有损的，模型后续基于摘要推理，摘要没保住的关键细节就永久丢失。第 2 层的 5KB 阈值和「保护最近 50 条」都是在防这个。

**压缩不是免费的**：摘要本身要花一次 LLM 调用，压缩越频繁总成本越高。所以触发条件必须绑真实信号（token 数、轮数），不能每轮都压。

**失效条件**：
- 会话里有大量结构化数据（JSON、表格）时，摘要会破坏结构。此时应走「卸载 + 引用」而不是「摘要」
- 需要精确复述早期内容的场景（法律、审计）不适合摘要式压缩，只能卸载 + 回查
- 压缩链路过长时（六层叠加），一次压缩可能触发多次 LLM 调用，延迟累加
