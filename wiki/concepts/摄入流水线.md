# 摄入流水线

## 一句话定义

把「一份新资料变成 wiki 里的一批页面」拆成固定步序，并规定每步的产物与失败处理，让摄入可重复、可回退，而不是每次凭手感。

## 我目前的判断

**摄入的难点不是「读懂」，是「改哪些页」。** 原文给的量级是：一份源可能触及 **10–15 个页面**（[[wiki/sources/llm-wiki-pattern|gist]] §Operations）。这条数字决定了两件事——摄入天然是批量写操作，中断的代价远大于一次问答；所以流水线至少要定义「哪些改动算一次原子提交」。

本仓现行 §6.2 是它的**人工收缩版**：读全 → 判归属 → 先汇报后落笔 → 建 source 页 → 扇出 concept/entity → 冲突处理 → 重建 index + 记 log。缺三样：增量缓存、持久化队列、失败重试。这三样在「一周 1–3 次写入、单篇串行」的节奏下是纯负担——**依据是使用频率，不是技术优劣**。

## 关键机制

**原文四步骨架**（gist §Operations）：

1. 读源，**与人对齐关键收获**（讨论先于落笔）
2. 写摘要页，更新 index
3. 更新受影响的 entity / concept 页（可能 10–15 页）
4. 追加 log

**实现版把它做成两次 LLM 调用 + 三道工程保障**（[[wiki/sources/llm-wiki-app-readme|README]] §3）：

- 第一步只分析：实体/概念/论点、与现有内容的关联、**矛盾与张力**、结构建议
- 第二步生成：带 `sources[]` 的页面、index、log、待审项、研究查询
- SHA256 增量缓存：源内容未变则跳过整个流程
- 持久化队列：串行、崩溃恢复、失败重试 3 次
- 兜底：摘要页即使被 LLM 漏掉也强制生成

两版的共同点值得单独记：**分析阶段必须先跑完才允许写**。本仓 §6.2 第 3 条「先汇报后落笔」是同一约束的人工形式——它保住的不是质量，是**可撤销性**。

## 我的实例

本仓 `AGENTS.md` §6.2（摄入）、§6.3 第 6 条（好答案回填成页，对应原文 Query 段的「不要让探索消失在聊天记录里」）。

实测规模：2026-10-22 这次 ingest（[[wiki/sources/llm-wiki-app-readme|llm_wiki README]]）共触达 6 个文件——source、entity、2 个 concept、index、log。与原文「10–15 页」同量级，说明这个量级判断对单篇中等长度文章成立。

## 取舍与边界

- **不引入队列与缓存**：写入频率是一周 1–3 次、单篇串行；缓存与队列的代码维护成本高于其收益。
- **失效条件**：一次性批量导入几十篇时（如 `thoughts/` 102 篇那次），无缓存会重复处理未变文件，无队列则会中途断且无法续跑。届时应引入缓存（哈希跳过）而不必引入队列。
- **不照抄「两次 LLM 调用」**：拆分收益在长文与高频场景；本仓单篇 + 人工审阅，拆成两步只是多一次上下文重建。
