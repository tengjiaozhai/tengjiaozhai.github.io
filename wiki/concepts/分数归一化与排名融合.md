# 分数归一化与排名融合

## 一句话定义

混合检索里两路结果（稠密向量 + BM25）的分数**不同量纲、不同分布、不同方向**，必须先各自换算到可比空间，再按名次（不是按分数）融合成一个排序 —— 换算是归一化，融合是 RRF。

## 我目前的判断

这两步是所有混检实现里最容易写错的地方，因为它**错得不明显**：归一化错了，返回条数是对的、相关性是错的；融合错了，也不报错，只是好结果排在后面。

三条硬判断：

1. **归一化必须按存储后端分别做，不存在"统一公式"。** 同一个余弦相似度，PostgreSQL 给的是距离 `d`，Qdrant 给的是 `sim`，OpenSearch 给的是 `(1+cos)/2`。照抄一家的算子到另一家，分数会整体偏。
2. **BM25 不参与向量归一化。** BM25 的分数是无界正数，天然不可与 `[0,1]` 比较；硬塞进同一套 `clamp01` 只会把高分全压到 1。
3. **融合按名次，不按分数。** RRF 只用 `r_i(d)`（该文档在第 i 路里的排名），分数只用来排出名次。这是它鲁棒的原因 —— 某一路的分数尺度漂了，名次不一定漂。

## 关键机制

### 一、向量分归一化：逐引擎查表

| 后端 | 原始返回 | 换算 |
|---|---|---|
| PostgreSQL / SQLite（pgvector / sqlite-vec） | 余弦**距离** `d` | `1 - d` |
| Qdrant | 相似度 | 直接用 |
| Milvus（IP / COSINE） | 相似度 | 直接用 |
| Milvus（L2） | L2 距离 `d` | `1 - d/2` |
| OpenSearch | `(1+cos)/2` | `2*score - 1` |
| Weaviate | `certainty` | `2*certainty - 1` |
| Elasticsearch v8 | 相似度 | 直接用 |

实现上这层被收在一个 `EngineAwareNormalizer` 里，逻辑就两句：

```go
if retrieverType != types.VectorRetrieverType { return score }  // 非向量路原样返回
return clamp01(score)                                          // NaN → 0
```

`clamp01` 的行为：`0.8 → 0.8`、`-0.2 → 0`、`1.2 → 1`。

**它不是什么**（这四条比"是什么"更常被搞错）：

- 不是 Min-Max 归一化（不依赖当前批次的 max/min，所以结果稳定、可跨请求比较）
- 不是 Z-score（不做分布假设）
- 不是统一 `(cos+1)/2`（那只对余弦成立，对 L2 和 certainty 都错）
- 不是全局缩放（每路独立换算，互不参考）

**跨后端还要 embedding 模型一致。** 换模型等于换向量空间，`1-d` 算出来的数再"对"也没有可比性 —— 这是归一化解决不了的一层。

### 二、加权 RRF

标准形式：

```text
RRF(d) = Σ_i 1 / (k + r_i(d))        r 从 1 起，未命中该路则该项为 0
```

`k` 经典取 60。`k` 越小，头部名次优势越大；`k` 越大，融合越平。

WeKnora 加了权重，并做最大值归一化：

```text
RRF_w(d) = w_v / (k + r_v(d)) + w_b / (k + r_b(d))
S(d)    = RRF_w(d) / ( (w_v + w_b) / (k + 1) )
```

分母 `(w_v+w_b)/(k+1)` 是"两路都拿第 1 名"时的理论最大值。用这个分母而不是"当前批次最大值"，结果才能跨请求比较 —— 和上面不用 Min-Max 是同一个理由。

算例（`k=60`、`w_v=0.7`、`w_b=0.3`）：

| 文档 | 向量名次 | BM25 名次 | S(d) |
|---|---|---|---|
| B | 2 | 2 | **0.984** |
| C | 3 | 1 | 0.978 |
| A | 1 | 未命中 | 0.700 |
| D | 未命中 | 3 | 0.290 |

**关键结论在 B 与 A 的对比上：两路都认可的第 2 名，压过了只有一路第一的文档。** 这就是 RRF 想要的"共识奖励"。反过来，只被一路命中的文档，分数上限就是该路权重 `w/(k+1)` 除以分母的部分 —— A 的 0.700 正好等于 `0.7/1.0`。

融合前的几处细节（漏掉任何一个，名次就会算歪）：

- **各存储的各列表分别排名**，不是全局排一次
- 同一路多个列表命中同一文档，**取最好名次**
- 仅向量路：按 Chunk 去重，保留 cosine
- 仅关键词路：每个列表先按最高分缩放到 `[0,1]`，再去重

### 三、相似度的语义：`pg_trgm` 的 `similarity=0.8`

这个数容易读成"80% 把握"，实际是 **trigram 字面重合度**：两个字符串共享的三元组比例。它衡量拼写，不衡量语义。

`CREATE INDEX idx_wiki_pages_title_trgm ON wiki_pages USING GIN (lower(title) gin_trgm_ops);`

在 WeKnora 里它只做一件事：为"这两个 Wiki 页标题是不是同一个实体"召回候选（阈值 0.8 用作候选门槛，最终由精确匹配 + LLM 判定）。评价它好不好不能看阈值本身，要看 **Recall@K 与误合并率** —— 阈值调高漏召回，调低错并页，两个方向的错误代价不同。

## 我的实例

WeKnora v0.8.3 混合检索：`halfvec(1024)` + HNSW 出向量路，ParadeDB `pg_search` 出 BM25 路（`content ||| query` 是 OR/任意 token 匹配，`paradedb.score(id)` 排序，中文走 `chinese_lindera` tokenizer），两路各出 50 条 → 归一化 → 加权 RRF → 重排。

实测判断依据：`candidate_count=50` 而不是 3 —— 说明 HNSW 索引确实工作在完整集合上，不是退化成了全表扫。这条观察来自恢复事故后的验证（见 [[wiki/synthesis/误删weknora知识库的恢复链路|误删 WeKnora 知识库的恢复链路]]）。

## 取舍与边界

**为什么用 RRF 而不是加权求和分数**：分数求和依赖两路分数在同一量纲，而这正是归一化不可能完全保证的事（分布不同）。RRF 只看名次，把"分数尺度不可比"这个问题绕过去了，代价是丢掉了名次之间的差距信息 —— 第 1 名和第 2 名的真实差距被抹成 `1/61` vs `1/62`。

**RRF 不是 Rerank 的替代。** RRF 是**排名融合**（无模型、毫秒级、只做并集排序），Rerank 是**模型精排**（cross-encoder 逐对打分、几十到几百毫秒）。生产上的顺序是 RRF 先缩到 50 条，Rerank 再精排到 5–10 条。

**归一化解决不了的事**：embedding 模型不一致、索引维度与查询维度不匹配、某一路整体失效（此时该路名次随机，RRF 会给它同等权重，反而拖累结果）。第三种情况需要的是熔断，不是更好的公式。

**失效条件**：单路检索时这套全不启用（纯向量不触发 `pg_search` 探测，`EngineAwareNormalizer` 也原样返回）；文档总量小于 `k` 时名次项差距被压平，融合几乎等于取并集。
