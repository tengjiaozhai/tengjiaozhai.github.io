# 递归自我改进

## 一句话定义

让系统改进自己，并把**被接受的改进留下来当作下一轮的起点** —— 「递归」的严格含义是状态继承，不是「能改自己」这个动作本身。

## 我目前的判断

**「能改自己」和「递归」不是一回事，这个区分决定了一个项目该不该叫 RSI。**

综述给的定义比我此前见过的都严：递归锚定在**状态继承**上 —— 一个周期里被接受的改进，成为后续周期的起始状态。而「递归进展」是更强的论断：**继承的状态还要改进「改进者本身」**。

按这个尺子量，绝大多数自称 RSI 的工程只是「自动化调优」：它们能改 prompt、改工具、改记忆，但改完之后没有一个环节让「改进能力」本身变强。**这是 RSI 叙事的第一个水分。**

**第二个水分是「改进提案」的地位。** 我原先也容易把「Agent 说这样改会更好」当成结论。RSI 学习那份笔记纠得很直：**提案只是一个待验证的假设**。它举的例子很具体 —— 为降低权限遗漏而增加权限检查步骤，后果可能是 Token 涨、耗时涨、简单任务被过度分析。所以提案必须配一个**可验证的假设**，而且要用新旧版本跑同一批任务来判。

**第三个水分、也是最硬的一条：「是否升级」不能交给被优化的那个 Agent。** 这不是流程洁癖，是 Reward Hacking 的直接防线。一旦被优化的对象有权改评估标准，它最省力的进步方式就是「让标准变松」，而这条路径比「真的变强」容易得多。

## 关键机制

**五步闭环**（本仓按两份材料合成，术语取综述的英文原文）：

```text
① 执行任务      用当前版本跑真实任务
② 评估与诊断    分析失败案例，定位能力瓶颈
③ 提出并实施改进  改 Prompt / Skill / 工具 / 代码 / 记忆 / 模型
④ 对比验证      新旧版本跑同一批任务（含 Holdout 与回归）
⑤ 接受或回滚    由预设规则裁决，不由被优化对象裁决
    ↓
   被接受的版本成为下一轮的起始状态 ← 递归就发生在这里
```

**四个必须回答的问题，缺一个闭环就不成立：**

| 问题 | 核心回答 | 失效形态 |
|---|---|---|
| 怎么评估好坏 | 硬性约束（准入门槛）+ 优化指标（比较用），**不能加权成总分** | 功能 95 分但有越权漏洞，综合分很高却不能上 |
| 怎么知道改进是好的 | 提案是假设，用 Holdout 集与回归测试验证 | 反复练同一批 20 题全对，换新题全崩 |
| 标准怎么适配场景 | 评估**框架**统一，指标与阈值由业务成功条件定 | 拿一套权重套所有 Agent |
| 谁决定接受或回滚 | 规则引擎自动裁决 + 人管高风险 + AI 只出证据 | 问 AI「你觉得这版好吗」 |

**可靠性要拆三层，不能笼统说「RSI 可靠」：**

| 层次 | 能否保证 |
|---|---|
| 决策执行正确（严格按规则接受/拒绝） | 在可信实现下可以 |
| 测试结果可信（候选在所测任务上更好） | 可以积累较强证据 |
| **真实能力全面提升（所有未来场景都更好）** | **通常无法保证** |

第三层不可保证，是 RSI 从理论走向工程的硬边界。现实中的 RSI 更像一个**受约束的实验性优化系统**：反复提案、验证、筛选、积累，提高「找到有效改进」的概率，而不是保证每次迭代都更强。

## 我的实例

**本仓没有任何 RSI 实践。** 这个域在 2026-10-28 之前完全是空的 —— 29 个 concept 里没有一页讨论自我改进。

能对上的只有两处结构性类比（类比，不是来源）：

- 本仓 [[wiki/concepts/失败归因与回归任务]] 的「归因 → 回归用例」链路，正好是 RSI 闭环的第 ② 步。但本仓止于这一步：归因出来了，没有「自动提出改进 → 独立验证 → 规则裁决」的后半段。
- 本仓 `tools/wiki-lint.mjs` 的六项检查有一处**形态相同的问题**：过期检查会反复报同一批页，而「修」往往只是更新 `as_of` —— 这正是「让指标好看」而不是「真的变好」，与 Reward Hacking 同构。这一条已记在 [[wiki/concepts/评审收敛]]。

**离 RSI 最近的一次尝试是 [[wiki/synthesis/误删weknora知识库的恢复链路]]**：先诊断（查队列、查表结构、查清理进度），再提方案（四条 UPDATE + 向量重算），最后验证（三次真实检索）。但这全程由人裁决，且**没有留下可继承的状态**（下次遇到同类事故仍要从头推），所以它连「自我进化」都算不上，只是个案处置。

## 取舍与边界

**为什么这件事难，难在评估器。** RSI 学习那份笔记最后收口在一个矛盾上：**如果 AI 的能力超过了当前评估器能判断的范围，评估器怎么知道它真的进步了？** 这不是实现问题，是逻辑问题 —— 它解释了为什么 RSI 、LLM-as-a-Judge、Reward Hacking、过程监督、可验证奖励会形成一组绑在一起的研究问题。

**所以工程上的现实做法是「缩小递归范围」**：不让它改评估标准、不让它改准入规则、不让它跨任务迁移收益。改的只是 prompt / 工具 / 记忆这些局部工件，收益也只在同一任务族内验证。这已经不是完整的 RSI，但它是当前唯一能落地的形态。

**失效条件：**

- 被优化的对象能读到或改到测试集 → 收益不可信
- 只有 Holdout 没有回归 → 单项提升、整体退化
- 评估标准长期不更新 → 测试题失去区分度，通过率虚高
- 把所有失败都总结成一段经验提示词 → 改进对象与根因错配（缺资料补来源，别名错改规则，不该都变成 prompt）

**一句话的判据**：一个自称 RSI 的系统，如果删掉「独立评估器」和「规则裁决」这两块还能跑，那它不是 RSI，是自动调参。
