# 代码评审分层

## 一句话定义

不设一道总闸门，而是六层各自拦一部分缺陷，外面再套一层回滚兜住漏网的。人工批准只放在有风险的那几层，且**分级由变更决定、不由作者决定**。

## 我目前的判断

**「有没有人读过代码」是不精确的度量。** 该问的是「这个变更有哪些地方可能出错，哪一个检查 —— 自动的还是人工的 —— 才是抓它的正确工具」。这一句把评审从「人的动作」改写成「检查的分配问题」，后面所有设计都是从它推出来的。

**人的时间是双向成本。** 只统计评审耗时会把账算成一半：修烂代码的时间同样是人的时间。所以只降前者不降后者等于没省 —— 这是本仓此前所有成本讨论都没算过的一项。回滚率与事故率因此不是结果指标，是**护栏**：它俩一升，说明人力没有减少，只是挪了位置。

**每层都会漏，所以层数不是安全感，覆盖面才是。** 六层里没有一层是完备的；靠的是「很少有缺陷能穿过全部层」。这条推翻了「把评审做深一层就够了」的直觉 —— 深一层只是把那层的召回提高，剩下的仍然漏。

**高风险由变更判定，不由作者判定。** 这个反直觉的选择解决的是老问题：按作者定级会让「熟人改危险代码」和「新人改安全代码」都被错配。两个分类器分工 —— 一个判变更的风险级别，一个判「即使级别不够也必须再加一次批准」（后者的典型触发是 owner 标记的敏感路径、任何 CI workflow 文件）。

**agent 出现的三个效力边界，本仓此前没有任何规定**：①agent 的批准**不算**人工批准；②agent 写的 PR，其**操作者始终计为必需评审人**（作者责任不能转移给 agent）；③一次批准只对一个 commit 有效，有不可信 commit 进来（agent push、手工解冲突）就必须重批。第三条尤其值得抄：它把「批准」从「对这个 PR 认可」收紧成「对这个具体状态认可」。

**反复出现的问题要从源头修，不是逐条改。** 自动评审器反复报同一类问题时，改 skill、加 lint 规则、更新 CLAUDE.md 或 REVIEW.md —— 而不是让作者一条条修。这跟 [[wiki/concepts/评审收敛]] 的「指定 bug 类别，一次改一整类」是同一个原则的两层应用。

## 关键机制

**六层 + 一层回滚**：

| # | 层 | 拦什么 | 谁来拦 |
|---|---|---|---|
| 1 | 建 PR 前验证 | 例行缺陷、没跑过的改动 | agent 自己（跑测试 / 构建 / 比截图）+ 全新上下文的子 agent 评审 diff |
| 2 | AI 评审 | 逻辑不符意图、破坏其他部分、根因没找对 | Claude 评审 + 多 agent 并行找 bug + 投票过滤误报 + 风格类过滤 |
| 3 | 安全评审 | 安全类问题 | 自动安全评审，**可阻断合并** |
| 4 | 自动检查 | 语法 / 类型 / 平台兼容 / 构建 | lint、类型检查、全平台测试、构建 |
| 5 | 分级人工批准 | 高风险判断、架构、责任 | 人（级别由变更定，不由作者定） |
| 6 | 合并队列 + 放量 | 两个各自成功的 PR 合起来弄坏 main | 合并队列在 main 上带变更重跑全部检查；特性开关 + 内部先行 + latest/stable 分道 |
| — | 回滚 | 穿过前六层的一切 | 特性开关关闭、revert、分阶段回退（分钟级） |

**第 2 层的降噪三段**：多 agent 并行找 → 独立投票判有效/误报（票数够才确认）→ 过滤掉纯风格/诊断/清理类。剩下的按严重度排序，标 Important / Nit / Pre-existing（既有问题不冤枉作者）。**所有发现必须处理**：修掉，或写明理由关闭。

**第 5 层的三个约束**：分级看变更不看人；只有仓库可信名单上的作者享受放宽（一般就是拥有该仓库的团队）；其余一律要第二个人批准。agent 批准不能顶替必需的人工批准 —— 自动评审可以放行低风险变更，但需要人时必须有人。

**人的时间怎么记**：每个 PR 的人工批准中位数（含 p95）、人工评论数、PR 等人所花的时间。回滚率与事故率作护栏。

**人被保留在五类判断上**（其余都该自动化）：

1. **要不要做这件事** —— 决定是否构建、愿景、品味、目标
2. **审计危险代码** —— 计费、自动更新器、CI workflow
3. **架构评审** —— 这些选择会成为别人遵循的约定
4. **验证证据** —— 测试输出、跑过的命令、截图、评审意见。判据一句话：**如果你说不出这些检查会漏掉什么，那就别要一个赞，你需要的是真评审**
5. **承担责任** —— 每个上线的变更都要有人负责，不管是谁打的字

**责任模型：「你合并的，你负责」。** 中小变更合并后出问题，一般预期自己修。不失控靠五件事：小变更易回滚、一切可回退、影响半径决定门槛、遥测很快暴露回归、复盘看系统不追个人。

**机器读完代码后的学习路径**：没有正式机制，也没有人脑子里装着完整心智模型。谁想懂某块，就让 Claude 针对那个切片生成讲解 ——「读一行文案改动的 diff 学到的东西极少，为要改的模块生成一份讲解学到的很多」。

## 我的实例

**本仓没有任何代码评审流程。** 现状是：`AGENTS.md` §6.2 要求「先汇报后落笔」，`tools/wiki-lint.mjs` 跑六项结构检查，提交由用户明确说「提交/推送」才做 —— 三道都是**单点检查**，不是分层。

唯一能对上第 1 层的是 lint：它是「可运行的检查」，跑完把结果给人看。但它只查结构（断链 / 孤儿 / frontmatter / digest / 重复 / 过期），不查内容质量，也没有「全新上下文的子 agent 评审 diff」这一步。

**可搬运的一条**（成本极低）：把「一次批准只对一个 commit 有效」翻译成 wiki 语境 —— 每次 ingest 之后 index/log 重建完成才算那次改动落地；中间任何一步被手改，就得重跑 lint。本仓目前靠人记得做，没有机制。

## 取舍与边界

**分层的前提是变更量大。** 一天 2,500 → 30,000 个合并的规模下，逐行人工评审才「变得不可能」。小团队照抄六层会付出与收益不匹配的流程成本 —— 本仓判断：日合并量低于几十个时，第 1、4 层（可运行验证 + 自动检查）加上人工评审就够了。

**这套设计对 agent 产码高度特化。** 「建 PR 前让 agent 把结果拿给我看」「agent 的操作者必须是评审人」这两条都假定作者可能是 agent。人写代码为主的团队，第 1 层的价值主要是「先自己跑一遍」，第 5 层的特殊规则基本用不上。

**自动化评审的成本被低估**：第 2 层每次 PR 都要跑多个 agent 并行 + 投票，token 成本不低。文中没给这项数字 —— 属于转引不可复算的部分。

**失效条件**：
- 层数上去但没有回滚机制 → 漏网的缺陷直接到用户，分层变成心理安慰
- 分级分类器判错 → 高风险变更拿到低级别批准，这是单点失效且不报警的
- 只用「有没有人看过」当指标 → 会得到形式合规（approve 了但没真读），文中那句「别要一个赞」正是针对这个
- 把 Nit 与 Pre-existing 从评论里删掉 → 作者失去「这不是我引入的」这一信息，会误以为自己改坏了

## 待澄清

- 两个分类器的判据与训练方式未公开。「即使级别不够也要再加一次批准」的触发集合怎么维护，本仓无参照。
- 合并队列的实现在仓库名（`redesigning-source-control` 一文）里，本文未展开。
- 「最多一个人过手就能合并」这个目标怎么统计达成率？文中只给了要衡量的三个指标，没给目标值与实际值。
