# 失败归因与回归任务

## 一句话定义

**失败归因**把「这条轨迹失败了」变成「第 k 步的那次工具调用或那句答复开始偏了、属于哪一类、该由哪个组件负责」；**回归任务**再把这个边界冻结成可重复执行的问题。归因决定改哪里，回归决定改完怎么证明没退。

## 我目前的判断

**0 分里没有信息，归因才有。** 二元奖励换来跨模型可比的单一数字，代价是「线路选错」和「漏做充值」在报告里是同一个 0。公开排名不需要更多；生产系统需要 —— 这是 [[wiki/concepts/Agent评测]] 里那个「分数骗人的四种解释」唯一能真正拆开的地方。

**首个错误 ≠ 最后一个报错。** 后续报错多半是连锁反应。`edit_file` 的 `old_string` 匹配失败、之后三次重试仍没写进文件：那三次重试不是三个根因，是同一个后果的三次回响。判据是「最早且能解释后续失败」。

**静默失败才是主战场。** 有工具报错的失败好定位；难的是全程零报错、Agent 自己宣布完成、验证器判失败的轨迹。这类失败只能靠事实锚点比对或前缀二分去挖，搜报错关键字一个都抓不到。

**归因判错比不归因更贵。** 把 Harness 的观察通道缺失记成「模型缺 OCR 能力」，接下来几周会花在换模型和 OCR 训练上，而真正要改的是补观察通道。错误归因的成本不是返工，是方向错。

**前缀回归的性价比高于端到端回归，但端到端不可省。** 前者冻结上下文、只验一个决策边界，便宜且能隔离单点；后者守整条工作流，是唯一能回答「有没有把别处弄坏」的东西。两层互补，不是二选一。

## 关键机制

**信号从哪来（三来源）**：用户明确纠正（「不要这么做」）、用户点踩或负面反馈、事后通过状态检查 / 规则验证器 / LLM 评审发现 Agent 做了不该做的事。三者共同点是**都不需要 Agent 自述**。

**九类错误与首错定位**（教材给的一个可用初始集）：

| 类别 | 典型表现 | 首错怎么定位 |
|---|---|---|
| 需求理解与歧义 | 漏条件、范围理解宽窄错、仓库里两个同名配置直接选一个 | LLM 把原始需求与动作序列逐条对照，取第一处偏离，再回溯造成它的那次调用 |
| 流程与规范缺失 | 未跑测试就提交、未写 Plan 就改、绕过既定架构约定 | 找第一次违反流程约定的动作（首次 `git commit`、首次写文件），回看之前读过约定没有 |
| 工具调用错误 | 同一文件反复编辑失败、schema / 转义错误 | 记第一次失败的编辑及原始请求与错误返回；重复失败属症状 |
| hack 验证环境 | 改断言、加 skip、mock 掉被测逻辑、声称跑过其实没跑 | 取第一次改动测试的 message，再与轨迹里真实执行过的命令交叉核对 |
| 修改不完整 | 改了签名和三处调用方，漏了第四处动态调用 / 另一语言绑定 | 声称的影响面与真实影响面做集合差，取第一个遗漏项 |
| 对用户的信息反馈错误 | 工具都对，最终告诉用户的金额 / 状态 / 时间错了，或把部分做完说成全部 | 答复里每个事实断言与工具返回逐条对齐，取第一条无法溯源的 |
| 非功能性回归 | 改公开 API / schema 而无迁移脚本，为过校验而删校验 | 取第一次做出该改动的 message，看它是否意识到动的是公开接口 |
| 模型执行异常 | 输出截断、无故停止、超时、没做收尾就结束 | 定位第一个异常终止点，区分模型停止 / Harness 超时 / 工具服务故障 |
| 过早停止 | 多目标任务只做一部分、没穷尽方案就宣布不可能 | 定位第一次遗漏目标或放弃探索的决策，与最终验证失败分开记 |

**归因的前置一步：先排除「评测自己错了」。** 淘宝把它们分成三类假失败 —— 数据层（输入有问题：工具内部提示词被误读、卡片超长被截断、字段映射错）、Prompt 层（规则理解偏了、缺边界示例、子项边界模糊）、Rubric 层（标准与技术认知不一致，例如「模式 B 忠实兜底」被判 0）。只有排除这三类，剩下的才是本页意义上的真实缺陷。**不做这层过滤，归因会把评测的 bug 记到 Agent 头上** —— 淘宝的原话：「早期看到通过率下降第一反应是调 Prompt，越调越差，因为根因在数据层或 Rubric 层」。

**有一条省掉归因的捷径：直接把事故当打分集。** Claude Code 团队收集导致事故的 PR、修复提交与回滚，让懂那块代码的工程师核实每条 bug 的位置与判定，评审系统每天拿这个集合打分 —— 不做归因，只用它衡量「同样的判定还能不能复现」。代价明确：**只覆盖出了事故的 PR**，那些「漏了但也没出事」的缺陷永远进不了集合，所以召回上限天然低于真实缺陷分布。相比之下本页的「归因 → 回归用例」贵，但能回答「为什么漏」。两条不互斥：先用事故集把门守住，再对个别案例做归因。

**归因也可以长在系统结构里，不必是事后报告。** 京东两条线：①**多智能体分工即归因边界** —— 售前接待 / 规格推荐 / 催单催付 / 售后跟进各管一段，一次会话的失败按角色边界直接落到责任智能体；②NL2SQL 的四级降级链（精确匹配 → embedding 相似 → 别名索引 → 用户行为辅助），每级失败原因与修复动作一一对应（词表没配 / 语义没学上 / 别名没建 / 偏好没积累）。这种「归因即分层兜底」比出报告更接近工程实效：失败时系统自动降级，同时告诉你降级点在哪。

**先修哪一类，现在有量级了**：VitaBench 的失败分类统计是推理 61.8% / 工具 21.1% / 交互 7.9%。占比差别这么大，意味着在它的场景里「先补推理」是单调最优。本页的九类表按出现频率排序，方向一致，但此前没有可引用的权重。

**静默失败的两个定位法**：一是**事实锚点比对** —— 把 Agent 的每条陈述与工具返回值逐步对齐，取首次背离；二是**轨迹前缀二分** —— 把轨迹截到第 k 步交给人接手，能救回来说明错误在 k 之后。两者都是「做实验」，不是「找关键字」。

**规则先筛、LLM 再定位**。九类里至少三类可以先用规则从海量轨迹里挑嫌疑：完成声明与实际执行命令的交叉核对、diff 是否触及测试断言与 skip 标记、diff 是否改动公开 API / schema 而无迁移文件。把全部轨迹喂给 LLM 更贵也更不准。

**归因记录必须结构化**：主因 / 次因、步骤号、工具名、观察证据原文、是否可恢复、置信度。再连同任务目标、环境状态、Agent 与工具集版本、完整轨迹一起存档 —— 否则这份归因不能变成回归用例。

**两层回归任务**：

| 层 | 起点 | 验什么 | 成本 | 适合的失败 |
|---|---|---|---|---|
| 端到端回归 | 初始状态 + 用户请求 | 最终状态、必要输出、安全条件 | 高（整跑） | 流程缺失、修改不完整 |
| 轨迹前缀回归 | 冻结的上下文 / 工具返回 / 环境状态 | 只验下一步或下几步 | 低（单步） | 需求歧义、危险动作前未确认、信息反馈 |

前缀回归的答案必须是**可接受动作集合**加禁止动作，不是唯一动作 —— 写成唯一动作会把合法路径判死，与 [[wiki/concepts/Agent评测]] 里「只评产出、不评路径」的边界是同一条线。

**从归因到回归用例的映射**（教材给了逐类映射，挑两条最能说明问题的）：信息反馈类 → 验收里对**答复内容本身**设断言，而不只查环境状态；hack 验证类 → 在验收里加两条硬约束「不得修改测试断言」「完成声明必须附带真实执行过的命令输出」。

## 我的实例

本仓唯一一次成型的归因是 `Agent 评测方法论.md` 附章：agent 遇到公共可查的陌生模型名（Jev）未检索就向用户索要定义。那次做对的是判据写法 —— 「澄清请求是否只索要用户独占信息」而不是「有没有调搜索」，并把用例归到回归集、口径取 pass^k。缺的正好是本篇的九类分类与结构化记录，所以它至今是一条孤立样例，进不了统计。

[[wiki/concepts/Agent评测]] 的「outcome 与 transcript 是两回事」是这条链路的上游：不读 transcript 就没有归因的原料。

`agent 开发学习笔记.md` §18–19 的 GoGo 复盘在形态上是一次首错定位（确认被背景酒店关键词抢路由），但当时没有按九类归档，也说不清该归「需求理解」还是「Harness 路由缺陷」。这正是分类表缺位的代价 —— 已在待澄清里记下。

本仓的反面样本来自教材而非本仓：AndroidWorld T3A 那条 32 步轨迹，第 8 步 Agent 自己在思考里写下 `I cannot actually see the content/details of the expenses in the image`，第 11 步四条开销数据凭空出现，此后每步都基于幻觉数据。全程零报错，首错是一句 assistant message 而不是工具调用。

## 取舍与边界

**归因成本 ≈ 人工读轨迹 × 条数**，这是这条链路唯一真正的门槛。教材明说可以借助 LLM，但不能完全依赖 —— 失败归因往往反映产品问题，不止技术问题。

**分类会膨胀到数百种**：先九类跑通，别一开始就细分。分类细到没人对得上号，等于没有分类。

**前缀回归集的手工成本被低估**：每条案例都要截断轨迹、写可接受动作集合、写禁止动作。教材说「对高可靠性的生产级 Agent，它往往比端到端集更重要」，但没给规模下限 —— 见待澄清。

**失效条件**：
- 轨迹本身缺证据（无步号、无工具返回、无思考记录）时，归因退化成猜
- 单例不能支撑「某类错误占多数」；样本少于十几条时只能用来发现模式，不能用来排优先级
- 归因结论写进 prompt / Skill 后再没人回头看旧的类目，分类会停在第一版的直觉上

**本仓暂无归因体系**（0 例系统化归因、0 条结构化记录）。此页是口径的引入，不是实践记录。

## 待澄清

- 九类是不是最小闭集？「路由 / 意图被别的关键词抢走」在表里没有独立位置（最接近「需求理解与歧义处理」），它可能和 [[wiki/concepts/意图识别分层]] 是同一层的独立类目 —— 需要一次真实归档来验证。
- 前缀回归集要多少条才够？教材只给「往往更重要」，没给规模。
- 结构化记录的字段集：教材列了 6 项但没给 schema（JSON / YAML 都提了，选型未定）。本仓若建，`Agent 评测方法论.md` 是唯一可对标的样例。
