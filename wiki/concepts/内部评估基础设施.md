# 内部评估基础设施

## 一句话定义

五个组件把「偶尔做一次评估」变成「每次产品决策都带度量」：**消融、AB 测试、双层特性开关、提示词快照、隐私感知分析**。外部评估告诉你 Agent 有多好，内部基础设施告诉你**哪项改动**让它变好。

## 我目前的判断

**特性开关是一等架构组件，不是调试工具。** 它同时承担实验、渐进发布、紧急熔断三个职责，而且必须从第一天设计 —— 编译时开关要在构建阶段把代码物理移出，事后加装做不到。这条与 [[wiki/synthesis/dsh-插件设计模式]] 里「编辑期切面 / 运行期包覆」的选择是同一类判断：开关的位置决定它能做什么，后补的开关只能做事后能做的事。

**消融要能回到「裸模型」基线，且开关必须极早注入。** 教材给的约束很具体：开关须在启动路径的极早期注入，早于任何模块级常量捕获配置值。晚一步，「关闭」只是关掉了显示，模型侧行为没变 —— 这种消融实验会得出「该特性没贡献」的错误结论。

**区分机制指标与目标指标，是这类工程里最容易犯的错。** 缩短计划文件是机制（你直接改的东西），降低会话级成本是目标。计划短了可能导致更多「编辑-检查-编辑」循环，总输出反而涨。自检只有一句：**我改的东西和我关心的东西，是同一个吗？**

**护栏指标是「不能变差的底线」。** 目标指标改善但用户满意度下降 / 操作次数上升 / 错误率上升，实验就该停 —— 而不是「综合看还是赚了」。

**提示词是代码，却没有代码的待遇。** 三条最低要求：可确定性渲染（同输入同输出）、版本化快照、每次变更跑评估集回归。本仓的 `AGENTS.md` 事实上就是这几个 agent 的系统提示，但它既没有快照也没有回归 —— 这条对本仓是缺口，不是别人家的问题。

## 关键机制

| 组件 | 解决什么 | 关键设计约束 |
|---|---|---|
| 消融基础设施 | 每个特性到底贡献了什么 | 能一键禁用多个主特性造出裸模型基线；开关极早注入；定期跑（如每次大版本前）以发现「特性债务」 |
| AB 测试 | 改动是否真的有效 | 多臂而非二元（控制组 + 若干渐进变体，看剂量-效应）；机制指标与目标指标分开；设护栏指标；记录基线统计（样本量、p95、相关性） |
| 双层特性开关 | 实验 / 渐进发布 / 紧急熔断 | 编译时物理移除（外部构建里根本不存在，反编译也看不到）；运行时配置服务端下发 + 本地磁盘缓存，宁可读旧缓存也不阻塞启动 |
| 提示词敏感性评估 | 哪次提交改了系统提示、影响多大 | 能在指定 git 版本上提取完整渲染后的系统提示；提示词变更像代码变更一样跑 CI |
| 隐私感知分析 | 评估需要数据，数据是用户隐私 | 分析接口只接受特殊类型包装的值，类型名本身就是审计线索；约束从文档变成编译期检查 |

**几个容易被忽略的细节**：

- **多臂的价值在曲线不在胜负**：只测「有 / 没有」会停在「有效」；测三档强度才能找到最优点，也能发现过强反而更差。
- **曝光事件在每个会话最多记一次**，否则重复记录会污染实验分母。
- **编译时开关同时是干净的消融机制**：关掉不是运行时跳过，而是代码不存在 —— 这让「这个特性值不值得存在」变成物理问题。
- **五组件是闭环**：消融发现哪些特性重要 → AB 量化单项改动 → 开关提供实验与回滚的地基 → 提示词快照把系统提示纳入 CI → 隐私设计保证数据拿得到又合规。

**所有权要落在人头上**（第二来源，[[wiki/sources/demystifying-evals|Anthropic 原文]] §步骤 8）：试过多种维护方式后，最有效的是**专门评估团队管核心基础设施，领域专家与产品团队出任务并自己跑**。评估任务的编写应像维护单元测试一样成为日常，而不是集中在一个人手里 —— 这条对「基础设施建好了却没人写题」这类失效特别对症。

## 我的实例

**本仓没有 AB、没有特性开关、没有消融。** 最接近「开关」的是 `AGENTS.md` §6.2 的自动摄入授权：按置信度分级放行（高置信直接发布，中低置信保留候选）。形态上是分级开关，但它服务的是**发布**而不是**度量**，不能算评估基础设施。

**唯一的自动度量是 `tools/wiki-lint.mjs`**（六类检查：断链 / 孤儿 / frontmatter / digest 漂移 / 重复概念 / 过期）。它只管结构，不管产出质量；「这次 ingest 的页面比上次好还是差」目前完全靠人读。这就是评估基础设施缺席的具象形态 —— 见 [[wiki/concepts/摄入流水线]] 里「缺增量缓存 / 队列 / 重试」的同类判断：按使用频率决定要不要补。

**可移植的第一件事**：把 `AGENTS.md` 做版本快照 + 每次 schema 变更跑一次 lint 对照。这是本仓能以个位数成本拿到的唯一一条五组件实践。

## 取舍与边界

**五个组件一起上，对小团队是纯负担。** 推断（未验证）：先做提示词快照 + 特性开关（成本低、立刻能止损和回滚），消融与 AB 等有真实流量和足够样本再上 —— 没有流量时 AB 的结论全是噪声，与 [[wiki/concepts/Agent评测]] 统计显著性那节同一个理由。

**编译时开关与消融实验存在张力**：物理移除的代码无法在同一构建里开 / 关，做对照需要两套产物，「只改一个变量」的隔离性变弱。教材没讨论这一点，见待澄清。

**失效条件**：
- 开关数量膨胀 → 组合爆炸，没人知道线上到底是哪个组合
- 实验平台的分组配置与本地缓存策略不一致 → 实验组定义漂移，数据不可解释
- 只有曝光没有护栏 → 目标指标涨了，但把体验做坏了，几周后才发现

## 待澄清

- 编译时 / 运行时双层开关，如何做同一个实验？（同一构建内不可开关 vs 需要两套产物的隔离性损失）
- 曝光去重的存储与去重窗口（每会话一次，跨设备怎么算？）
- 五组件的最小起始集：教材给的是五个都做，本仓判断是两条，无实测支撑。
