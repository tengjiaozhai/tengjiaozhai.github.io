# 软删除与恢复边界

## 一句话定义

一次「删除」往往不是一种操作，而是**同一业务动作下按存储介质分裂出的多种操作**：关系表软删、向量索引硬删、对象存储硬删。恢复上限由其中最硬的删除方式决定，不由接口返回码决定。

## 我目前的判断

**「DELETE 返回 200」不含任何可恢复性信息。** 真正决定能不能救回的是三件事：目标表有没有 `deleted_at`、清理是不是异步的、清理跑到哪一步了。这三件事都得查，不能从接口响应推断。

WeKnora 的实例把这一点暴露得很干净 —— 同一个「删知识库」动作，在四张表上是软删，在 `embeddings` 表上是物理删（那张表根本没有 `deleted_at` 列），在磁盘上是 `DeleteFile`。**恢复方案因此被切成三段**：改标记、重算、重传。

**关键推论：软删除是「读取时过滤」，不是「数据还在某处」。** 只要清理任务还没跑到，软删就等价于「数据完好，只是看不见」；一旦清理跑过去，软删那部分也一起没了。所以**恢复的第一动作永远是查队列有没有残留**，而不是直接 `UPDATE`。

## 关键机制

**四步判定顺序，不能换：**

```text
① 查清理队列是否还有残留任务
     有 → 先取消，否则回滚后会被再删一次
     无 → 进 ②
② 查每张目标表有没有 deleted_at 列
     有 → 可软恢复（UPDATE ... SET deleted_at = NULL）
     无 → 数据已物理消失，只能重建
③ 查清理进度到了哪一步
     按源码里的删除顺序对照：先删的是最不可恢复的
④ 只有在 ① ② ③ 都明确后，才动第一条 UPDATE
```

**第 ③ 步的依据是源码顺序，不是猜。** 本例的 `ProcessKBDelete` 顺序是 `embeddings → chunks → file → wiki`，所以「embeddings 归零而 chunks 完好」这个观测本身就是进度刻度：清理跑完了向量那一步，还没来得及删 chunk。

**恢复的分级由删除方式决定，不由工作量决定：**

| 删除方式 | 恢复动作 | 是否保真 |
|---|---|---|
| 软删（改标记） | `SET deleted_at = NULL` | 100% 保真 |
| 派生数据硬删（向量、缓存、索引） | 从源数据重算 | 取决于源数据是否完整 |
| 源数据硬删（文件、正文） | 只能重新导入 | 取决于外部是否有备份 |

**中间那一层最容易被忽略。** 向量、缓存、全文索引都是从主数据派生的，「删了重算」听起来无害，但它有一个前提：**派生公式必须还原准确**。公式错了，算出的向量在库里但检索对不上，比空表更难发现。

## 我的实例

2026-10-28 误删 WeKnora 知识库，按上面四步走：队列已空 → 四张表都有 `deleted_at` → 清理只跑到向量那一步 → 才动 `UPDATE`。

结果：100 文档 / 13,901 分块 / 2,832 Wiki 页靠改标记全数回来；12,934 条向量从 chunk 文本重算；**100 个原始文件不可恢复**（目录还在、内容已空），只能从本地仓库重传。

**本次真正的运气不是恢复成功，是 `chunks` 表恰好有 `deleted_at`。** 如果那一层的实现是硬删，恢复就只剩一个空壳。

一手记录见 [[wiki/sources/weknora知识库误删复盘]]，详细链路与实测数字见 [[wiki/synthesis/误删weknora知识库的恢复链路]]。

## 取舍与边界

**软删不是免费的。** 它把「删除」变成「标记 + 后台清理」，代价是三件：①清理任务的可靠性和幂等性要自己保证（本例用 asynq 持久队列 + 重试）；②每张表都要记得加 `deleted_at` 并在所有查询里过滤，漏一处就是数据泄漏；③磁盘不会因为「删了」而立即释放配额。

**所以「哪些表软删、哪些不软删」往往是权衡的结果，不是设计疏忽。** 本例里 `embeddings` 不软删是合理的 —— 它体积最大（18 万行 / 1024 维）、可由 chunk 重算、留着只占空间。真正的问题不是「embeddings 该不该软删」，而是**这个区别在删除接口上完全看不出来**。

**失效条件：**

- 清理任务未完成时回滚，但队列里还有残留 → 恢复的下一秒被再删一次
- 表有 `deleted_at` 但清理是同步的（一个事务里既软删又硬删） → 软删形同虚设
- 派生数据重算时公式与原实现不一致 → 行数看着对，检索静默失效

**从事故侧出发的预防只有一条是有效的**：删除类接口的权限与查询类接口分开授。本例中一个用于「读内容」的 key 具备 `manage_kbs`，能执行 `DELETE` —— 这一条如果先做到，后面所有恢复动作都不会发生。降权、回收站、二次确认都只是这条的补丁。
