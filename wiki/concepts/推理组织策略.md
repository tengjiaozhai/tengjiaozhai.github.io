# 推理组织策略

## 一句话定义

**CoT、Self-Consistency、ToT、GoT 是同一族东西：四种把算力换成正确率的组织方式，不是四个模型。** CoT 沿单一路径求解；Self-Consistency 独立采样多次再投票；ToT 把推理当状态空间搜索，能剪枝回溯；GoT 把中间结果连成图，允许跨分支聚合、复用与反馈迭代。

判据只有一条：**错在哪、加哪层、多花的算力值不值**。

## 我目前的判断

四者按「状态可见性」递增，成本也同步递增：

| 方法 | 状态在哪儿 | 一次问题花几次推理 | 真门槛 |
|---|---|---|---|
| CoT | 模型输出里，代码拿不到 | 1 | 步骤是解释，不是验证 |
| Self-Consistency | 代码里（N 份采样结果） | N | 采样必须独立、答案必须可归一化 |
| ToT | 代码里（状态 + 父指针 + 评分） | 预算内多次 | 评估器质量决定上限 |
| GoT | 代码里（DAG + 来源 + 版本） | 预算内多次，可复用 | 收敛条件与冲突检测 |

三条我认为最容易被跳过的判断：

1. **Prompt 能模拟形状，不能实现语义。** 「请提出三个方案并评估」看起来像 ToT，但没有可回放的状态、没有预算、没有回溯点，失败后无法定位是生成错了还是评估错了。判断一段实现属于哪一档，看它有没有可回放的中间状态，不看 prompt 里写了什么。
2. **票数不是置信度。** 5 次采样 4 次一致，正确概率不是 80% —— 同一模型的采样错误是相关的，多条路径可能共享同一个偏差。Self-Consistency 降的是方差，不降偏差。
3. **默认答案是「什么都不加」。** 普通 Agent Loop 能稳定完成的任务，加搜索、加投票、加图调度都是纯成本。这条与 [[wiki/concepts/Plan-Execute]] 里「单步任务用 Plan-Execute 是过度设计」是同一个判断的不同场景。

## 关键机制

**CoT 的本质是「把中间量写出来」，不是「让模型更聪明」。** 它的收益来自把复合推理拆成串行的浅步骤，每一步的输入都变短。代价是早期步骤出错会被后续步骤当作既定事实继续推 —— 这就是「早期错误沿后续传播」，也是为什么它需要外部验证兜底。

**Self-Consistency 是三步，缺一步就失效：**

```text
独立采样 → 答案归一化 → 投票
sample_llm(question, n=5) → normalize(extract(...)) → majority_vote(...)
```

- 独立采样：必须是多次模型调用。一次回答里扮演五个角色不是五次采样。
- 归一化：`13` 与 `13.0` 判等，`日期范围` 与 `日期区间` 映射到同一类型。整段自由文本做多数投票没有意义。
- 投票：票数接近或无明显多数时，要交给验证器或人工，不能宣称可靠。

**ToT 是一个带预算的搜索循环：**

```text
frontier = [initial_state]
while frontier and budget_available:
    state = select(frontier)
    candidates = generate(state)
    scores = evaluate(candidates)
    frontier = prune_and_expand(frontier, candidates, scores)
return best_valid_result()
```

它能成立的前提是**状态可定义**：当前状态含什么、一次动作改变什么、什么算成功、何时提前终止。这四条写不出来，搜索就无法复现。每条分支至少留五项记录 —— 状态 ID、父状态、候选动作、评估结果、是否继续 —— 否则失败后只能猜。

**GoT 在 ToT 之上多了三种边之外的能力：聚合、精炼、复用。** 节点保持单一职责（提取约束 / 生成方案 / 校验兼容性各一个），聚合前先做冲突检测，反馈循环必须带停止条件（版本号、最大迭代数、收敛阈值、预算上限）。它解决的是「多个结论要合并成一个」，如果只是选一条路线，ToT 就够。

## 我的实例

**本仓的 agent 走的是「什么都不加」那一档。** `agent 开发学习笔记.md` 里的行程规划智能体用 ReAct + [[wiki/concepts/Plan-Execute]]，没有引入投票或搜索 —— 它的质量瓶颈在工具计算与方案评估，不在采样方差。这是选型而非遗漏。

**反向证据在 `thoughts/041`（登记于 [[wiki/sources/thoughts-路由与智能体协作]]）：为什么要关闭模型的深度思考。** 那里的论证是 ReAct 的 Reason→Act→Observe 循环已经把「思考」拆成多轮显式调用，每轮模型都能看到完整 history，不需要在单轮内做长链推理；再叠 thinking mode 等于「思考中套思考」，延迟从 10 秒膨胀到 40-60 秒，每轮多 1000-3000 tokens。**这条与本章不冲突，是同一判断的另一面**：CoT 类机制的价值在单次调用内组织推理，当外层循环已经替代了这一步调度，内层再展开就是重复付费。

**图解**：`output/llm-reasoning-strategies.html`（四张 SVG + 选型表，见 [[wiki/outputs/图解索引]]）。

**生成式 UI 的落地判据**（原文 §6，我认为是这章最可迁移的部分）：

| 环节 | 该用哪档 | 理由 |
|---|---|---|
| 字段类型判断 | Self-Consistency | 答案可归一化（日期范围 / 日期），投票有意义 |
| 整体 UI 方案 | ToT | 多方案可比，能用结构检查与交互测试当评估器 |
| 跨模块融合（字段 / 权限 / 审批 / 布局） | GoT | 模块间有真实依赖，需聚合后查冲突 |
| 简单表单生成 | CoT | 固定组件 Schema + 约束校验就够 |

关键边界：**不要对整页 UI 做简单投票**，只能对能标准化比较的字段或决策聚合。

## 取舍与边界

**评测方式决定这套东西有没有被真正用上。** 选型不能照搬论文结论，要跑对照实验，且必须做消融：去掉 Self-Consistency 的投票、去掉 ToT 的中间评估、去掉 GoT 的融合或反馈，看增益是否真的来自那个模块。指标分三组 —— 质量（任务完成率 / 准确率 / 约束满足 / 无效输出率）、效率（token / 端到端与 P95 延迟 / 工具调用数）、可靠性（多次运行稳定性 / 验证失败率 / 回退成功率）。这与 [[wiki/concepts/Agent评测]] 的口径一致，消融与 model swap 的分工见那里。最终结论应落在「多花的算力与延迟，换来的质量提升是否值」，而不是「准确率更高」。

**失效条件**：

- **评估器不可靠时，ToT/GoT 会放大错误。** 搜索深度越大，被错误评分器带偏的机会越多。可客观验证的环节（单测、编译、SQL 执行、约束校验）优先，LLM-as-a-Judge 只做辅助。
- **任务本身不确定时，搜索无意义。** 探索型任务连目标都在过程中才明确，没有可评估的中间状态。
- **现代推理模型上，强制长思维链可能有害。** OpenAI 推理模型文档明确写「避免 CoT 提示，`think step by step` 类指令可能无益甚至有害」，与「明确目标 / 约束 / 验收标准」相比是更差的默认。（按官方文档核对，2026-11 查阅；本仓无对照实验。）

**与相邻页的分工**：[[wiki/concepts/Plan-Execute]] 是**任务层**的调度（先拆计划再执行），本章是**单步推理内部**的组织方式；两者可嵌套 —— Plan 用 CoT 求解，Execute 内部照样是 ReAct。[[wiki/concepts/KV缓存与提示词缓存]] 是同一篇笔记的主章，讲同一次推理怎么算得更便宜；本章讲同样的模型怎么算得更准，两者是成本账的两端。

## 待澄清

- **本仓零实测。** 四种方法在仓库里一处都没跑过，全部是方法论搬运。上面所有判据都来自原文与官方文档，没有任务集上的数字。
- **N 的选择没有推导。** 「从 3 或 5 起步」是工程经验，不是理论最优；边际收益曲线要自己测。
- **「票数接近」没有阈值。** 3 次采样出现 2:1 算不算接近，原文没给判据。
- **GoT 的收敛条件没有量化。** 版本号 / 迭代数 / 收敛阈值 / 预算上限四选一以上，但本仓无实现可参照。
- **与 [[wiki/concepts/递归自我改进]] 的关系未拆。** RSI 的自我改进循环在多轮之间迭代，GoT 的反馈在单任务内迭代，两者边界我没吃透。
