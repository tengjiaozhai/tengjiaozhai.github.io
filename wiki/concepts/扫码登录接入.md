# 扫码登录接入

## 一句话定义

把「企业微信扫码登录」接进自有系统，接的不是一个按钮，而是**一次身份所有权的移交**：IdP 只负责证明「这个人是谁」，而**会话、归属、显示名、注销生命周期这四件事仍然全部归本系统**。判断一套接入是否成立，看的不是「能不能登进去」，而是这四件事有没有各自落到一个明确权威的地方。

## 我目前的判断

**1. 换票式和直取 token 式是两种架构，不是两种配置。** 接入前必须先问一句：IdP 除了「他是谁」，还给不给我「怎么代表他持续说话」。

- 给 token（`POST /sso/extral/auth` → `data` 即不透明 token）→ 会话权威在 IdP，本系统只做缓存，`validate` 可以随时回源戳穿。
- 只给身份（`GET /sso/checkTicket?ticket=` → 一个 loginId 字符串）→ 会话权威必须自己建，而且**建出来的东西 IdP 永不认账**，`validate` 只能查自己的表。

这两条路的差别不在代码量，在于**「会话过期」这件事由谁定义**。第一条能靠 IdP 单方面作废，第二条只有本进程说了算 —— 所以进程重启等于全员掉线，这必须当成设计前提写进文档，而不是当成 bug 后期再修。

**2. 同源要求是 host-only cookie 的物理结果，不是配置洁癖。** IdP 登录页会写一个「登录完回到哪」的 cookie，写法通常是 `document.cookie = 'sso_back=' + encodeURIComponent(location.href) + ';path=/;SameSite=Lax'` —— **没有 `domain=` 属性**，于是它只在该 host 下回传。所以「扫码页域名」与「回跳落地域名」不同，第一步就断：请求到了 IdP，但 IdP 读不到那个 cookie，会判成「客户端未启用扫码」直接 403。

这条推论有一个反直觉的验证法：**白名单已放行时，无 cookie 的请求也是 403**。所以看到 403 不能断定是域名没加白；要看有没有一个「cookie 在、但 code 无效」的 400 —— **400 才是白名单放行的证据**。把 403 读成「白名单拦截」是这条链路上最贵的一次误判。

**3. 回跳基准绝不能取请求的 Host 头。** 「登录完跳回本站」这件事里，「本站」如果从 `request.url.netloc` 推，攻击者伪造 `Host: evil.com` 调一次「给我登录地址」，就能拿到一个 redirect 指向 evil.com 的**合法** IdP 地址；受害者点它、正常登录、IdP 把 `?ticket=` 投到 evil.com，票据外泄。攻击者不需要控制受害者浏览器，只需要我们的接口愿意签发。

正确做法是把「本站」变成一个**配置项**（`PUBLIC_BASE_URL`），配置缺失就拒签（500），不做「智能推断」。推断这一层一旦存在，就必须回答「推断错了怎么办」，而唯一诚实的答案是「不能用推断兜底」。

**4. 换票必须绑 state。** 票据本身不绑浏览器 —— 攻击者可以用自己的账号取一张票，把 `https://本站/?ticket=<他那张>` 发给受害者；受害者同源换票成功，落到**攻击者账号**上，之后上传的文档、写下的历史全进攻击者归属。这是登录 CSRF 与会话固定的合体。

判据：**发起登录的人**和**完成换票的人**必须是同一个浏览器。实现只需一对：`start` 时 `secrets.token_urlsafe` 生成 state、写 HttpOnly cookie（`Max-Age` 短，如 900s）、并把 state 拼进回跳地址；`ticket` 时用 `compare_digest` 比对 body 里的 state 与 cookie，不符即 401 并清 cookie。**注意哪个参数进 URL、哪个进 cookie 不能颠倒** —— 两者都在 URL 里，攻击者拿到的链接就自带 state，等于没绑。

**5. 归属键与显示名必须拆开，且归属键要跨登录路径同形。** 同一个自然人可能从两条路进来（账密、扫码），如果账密路径把中文名写进归属字段、扫码路径把登录名写进去，那么历史列表 `WHERE owner = ?` 与埋点 `userName` 会把一个人劈成两份，互相看不见 —— 而且**不报错，只是查不到**。

判据：**归属键取 IdP 侧的稳定标识（`cn` / 邮箱前缀 / 工号），显示名单独一列传中文名，界面只读显示名。** 显示名改多少次都不影响归属。

**6. 一次性票据要求「重放」被当成正常路径处理，不是异常。** 票据被兑换即刻作废，所以任何「页面载入时会触发换票」的代码都可能被触发两次（本仓是 `mcp_client.js` 与 `batch_ui.js` 各自调了一次 `initGate()`）。第二个请求必然 401，而那条失败分支会把**已经进工作台的人**推回登录门禁。修法不是「别调两次」，而是把换票收敛成一个 promise（`ensureTicketExchange()`），第二次调用复用第一次的结果。

**7. 失败提示的落点要跟着用户当下的动作走。** 扫码失败的错误如果写进账密表单的错误行，用户会以为是密码填错了 —— 他根本没在填表单。错误必须落在扫码那条横条里，而且**票据一次性意味着重扫也过不去**，所以文案不该是「稍后重试」，应该直接给出能解决问题的人。

## 关键机制

六步链路，每步一个判据和一个易错点：

| # | 动作 | 判据 | 易错点 |
|---|---|---|---|
| 1 | 前端问后端要登录地址 | 后端返回的 redirect 前缀必须是**配置的对外根地址** | 从 Host 头推 → 伪造 Host 即可把票据投到任意域名 |
| 2 | 后端签发 state 并写 cookie | `HttpOnly` + `SameSite=Lax` + 短 TTL（≤15min）+ 只拼进 redirect 的 query | state 也塞进响应体让前端「一起回传」→ 攻击者拿链接即得 state |
| 3 | 浏览器跳 IdP，用户在那边扫码 | IdP 侧要不要把落地域名加进 enabled-hosts，与本系统无关 | 把 `qrEnabled:false` 读成「链路不通」，其实它只控制 Tab 显不显示 |
| 4 | IdP 302 回落地页，带 `?ticket=` | 只做一件事：**在首帧前把登录卡片挡住**，否则用户会看到一次登录页闪回 | 用异步 JS 遮 → 首帧已画出来了；必须同步内联脚本给 `<html>` 打标记 + CSS 兜 |
| 5 | 前端拿 ticket + state 换本地会话 | `compare_digest` 比 cookie 与 body；成功后**立刻从地址栏摘掉 ticket** | 不摘 → 用户刷新/分享链接就是一次无效换票 |
| 6 | 会话写入 + 跳工作台 | 归属键、显示名、TTL 三样都要落 | 只落 token → 后续所有「按人查」的功能静默空表 |

**「首帧」这件事值得单独说。** 服务端如果只做静态文件返回（不读 Cookie、不鉴权），页面给谁看完全由前端 JS 决定 —— 那么「登录后先闪一下登录页」不是二次跳转，而是**这一页的默认状态就是登录页**。实测数据：文档开始 261ms → 首屏绘制 584ms（登录页已画出）→ 换票 1421–1992ms → 面板切换 1997ms，登录页可见约 1.4 秒。判断依据不是猜，是 `Page.getNavigationHistory` 只有 2 条 entry、`performance.getEntriesByType('navigation')` 只有 1 条 `type=navigate`。

修法是**同步内联脚本 + `<html>` 属性 + CSS**：脚本在 `<head>` 里读 `location.search` 有没有 ticket，有就给 `<html>` 加 `data-sso-pending`，CSS `html[data-sso-pending] .login-card{display:none}` 与 `html[data-sso-pending] .pending{display:grid}` 一起生效。属性必须挂在 `<html>` 上，因为首帧前能改的只有它和已经解析到的 DOM。另加 20 秒兜底移除 —— 主脚本若抛错导致换票从未执行，登录卡片必须能自己露出来，否则用户面对的是永远空着的页面，连手动登录都没得选。

**注销是常被漏掉的第六件事。** 「退出后点扫码又自己进去了」的根因是只清了本地会话，IdP 侧仍认着。判据不能看状态码（多个端点都返 200），要看**会话还在不在**：带同一张 cookie 打 IdP 的登录页，302 = 仍登录，200 = 已注销。本仓踩到的两个端点：`/sso/logout` 恒返 `{"msg":"not handle"}`（21 字节，空壳），`/sso/signout?back=` 才真的注销并 302 回跳。参数也只认 `back=`，`redirect`/`url`/`callback` 都被忽略。

## 我的实例

2026-11-04 ~ 11-05 在 [[wiki/entities/letter-auto|letter-auto]] 上落地，IdP 是该司的 dora 统一认证（`https://dora.tinno.com/prod-api`）。

**取舍：选了 Ticket 模式**，因为 `checkTicket` 只回 loginId，`/sso/extral/user-info` 又只认 `Authorization: <token>` 且**忽略 `?loginId=` / `?userCode=` 等一切参数**（实测永远返回 token 本人，`/sso/extral/user`、`/sso/extral/user-by-login` 均 404）—— 换句话说，拿不到票据对应的 token，也就无从按 loginId 反查。于是自签 `secrets.token_urlsafe(32)` 作会话 token，`SessionStore` 是唯一权威。

**加固前后对比**（子代理只读 review 提出 3 阻塞 7 建议，全部认领）：

| 洞 | 加固前 | 加固后 |
|---|---|---|
| Host 伪造 | `_page_base`/`_safe_redirect` 用 `request.url.netloc` 当本站 | `_trusted_base()` 优先读 `PUBLIC_BASE_URL`，其次要求 host ∈ `MCP_ALLOWED_HOSTS`；非回环强制 https，推不出即 500 拒签 |
| 无 state | 换票只要 ticket | `start` 写 HttpOnly cookie，`ticket` 用 `compare_digest` 比对，成功/失败都清 |
| scheme 降级 | 只比 netloc，放行 http | 并入 `_trusted_base`：显式配置才允许 http，否则不签发 |
| 票据落进 fragment | 回跳地址带 `#x` 时 IdP 拼成 `#x?ticket=...`，前端 `searchParams` 取不到 | `_safe_redirect` 用 `urlunsplit(..., "")` 剥掉 fragment |
| 会话无 TTL | 只 pop/clear | `SessionUser.expires_at` + `add(ttl_seconds=12h)`，`get()` 命中过期即删 |

**归属键拆分**：原代码 `username = data.get("username") or data.get("cn")` —— 而 dora 的 `user-info` 根本没有 `username` 键（键集是 `['avatar','cn','difyToken','email','groupId','id','modelLimits','name','newApiToken','userCode']`），所以两条路径拿到的 `username` 一个中文名、一个登录名。改成 `username = cn`（跨路径同形，`mingjie.shen`）、`displayName = name`（`沈明杰`），界面读 `shown_name`。

**未解决的：工号恒空。** `checkTicket` 只回 loginId，`user-info` 又不能反查，所以 ticket 路径的 `staffNo` 只能是空串 —— 历史与埋点带 `userName` 但缺工号。这属于 IdP 接口面不足，不是本仓能补的。

**验证**：`pytest tests/ -q` 1149 passed / 7 skipped；真实 dora 八步端到端（走公网 `http://ailab.jstinno.com/letter`）全通，含同票重放 401、伪造 state 401、logout 后 validate 401。上线后 `journalctl` 无 error。

## 取舍与边界

**为什么不做 Redis 会话共享。** 本仓是单实例部署（systemd 单进程），进程重启即全员掉线是可接受代价；而在 ticket 模式下加 Redis 只是让「IdP 不认账」这件事跨进程一致，并不增加任何安全性。**边界**：一旦上多实例或滚动重启，会话表必须外置，否则用户在负载均衡两侧会被判成未登录 —— 这正是 [[wiki/concepts/会话并发互斥]] 里「逻辑所有权必须由中心仲裁」的同一个道理。

**为什么不直接改用「服务端读 Cookie 返回不同 HTML」。** 那能彻底消掉首帧闪回，但会引入新问题：`?ticket=` 残留（换票失败未摘票据）时，服务端此时还没有会话，只能返回登录页 —— 首帧问题依然存在，只是形态从「画错再遮」变成「先给占位页」。此时 `data-sso-pending` 那套遮挡就不该保留：它的前提是「这一页必然先画错」，而服务端一旦能决定首屏内容，这个前提不成立。

**开放重定向仍在 IdP 侧，本系统只能收窄自己。** `/sso/auth?redirect=` 对任意绝对 URL 都放行（`https://evil.example/pwn` 也带 ticket 回跳），本仓只能在**签发端**拒绝异站 redirect。这是单向收窄：任何人直接构造 IdP 的登录地址仍能绕过。**边界**：真正的修复点是被接入方的 redirect 白名单，接入方无法替代。

**归属键选 `username` 而不选 `staff_no`，与 [[wiki/entities/trail-production-agent|trail-production-agent]] 的选择相反。** 那边归属键是工号（`trial_project.owner_staff_no`），能覆盖「登录方式变了但人没变」；本仓没有这个条件 —— ticket 路径拿不到工号。代价是**任何人改了 IdP 侧的 `cn` 就等于换了身份，历史随之丢失**。若将来补到工号，迁移路径是「按 (cn, staff_no) 建映射表，回填历史」，不是直接换键。

**失败文案里的具体对接人不是装饰。** 票据一次性 + state 已作废意味着用户重扫也过不去，此时唯一出路是人工。写成「请稍后重试」等于把用户困在一个不会自愈的循环里。

**失效条件：**

- IdP 改了 `user-info` 的键名（`cn` → `loginName`） → 归属键静默变成空串，历史全空且不报错
- 部署改了域名却没同步 `PUBLIC_BASE_URL` / `MCP_ALLOWED_HOSTS` → `start` 恒 500，页面看起来「按钮点了没反应」
- 反代没透传 `X-Forwarded-Proto` 又没配 `PUBLIC_BASE_URL` → 推断出 http，被非回环强制 https 的规则拒签
- 把 state cookie 的 `Path` 设成 `/letter` 而落地页在 `/` → cookie 不回传，换票恒 401

## 待澄清

- **本页不满足 AGENTS.md §5 的验收标准**（至少 3 个断言落到 ≥2 篇 raw 的具体标题）。它是单项目、单次接入的实测沉淀，没有第二份独立来源可对照；`confidence: medium` 就是因此。等第二个项目也接一次，再来回填对照。
- **IdP 侧的 `enabled-hosts` 白名单是不是唯一入口条件，没查透。** 本仓观测到 `qrEnabled` 的判定键是「redirect 参数的 host、精确匹配、非后缀」（`foo.jstinno.com` → false），与请求 Host 无关；但这个开关**只控制登录页的 Tab 显隐**，Ticket 链路本身不依赖它 —— 两个结论来自不同证据（页面 JS 与实测矩阵），是否还有其他隐藏开关未探。
- **「首次扫码后补全工号」这条旁路要不要做，未定。** 思路是扫码进来后要求用户补一次工号并落映射表，代价是登录多一步且映射表会腐化（与 [[wiki/entities/trail-production-agent|trail-production-agent]] 的 `user_identity` 表同类问题）。
- **票据的熵与格式只在 dora 上验过**（64 字符 base64url、一次性、存储只归 dora，rd-sso 的 `checkTicket` 一律 500）。换 IdP 或换集群时这些前提都要重测，不能沿用。
