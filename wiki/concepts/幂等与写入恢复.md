# 幂等与写入恢复

## 一句话定义

崩溃恢复时，只读工具和已做成幂等的写工具可以安全重跑；其余工具必须交给模型判断「刚才走到哪了」，而不是自动重试。

> 分工：本页问的是「**崩溃后能否安全重跑**」；「**删了之后能救回多少**」是另一个问题，见 [[wiki/concepts/软删除与恢复边界]]。两者共享同一条顺序原则 —— 先判断状态是否可信，再决定动作。

## 我目前的判断

Durable Runtime 的恢复逻辑不是「把没做完的重做一遍」。写操作重做一次可能多扣一次款、多下一单。所以划分是**按工具安全性分**，不是按「有没有完成」分：

```text
只读工具          → 可标 safe，中断后可自动重跑
已做成幂等的写工具 → 可标 safe，重跑等价于跑一次
其他写工具        → 不标 safe，中断后交给模型：
                    先用只读工具查清写到哪了，再决定补写、重来或问人
高风险的          → 再加审批 hook
```

配套的机制是 **Effect 前先写 Intent，Effect 后再写 Result**（Harness 最核心的 Durability Rule）：

```text
准备执行 edit_file
  → Harness 先写 R tool_started（含 toolName / effectiveArgs / resultEntryId / replay）
  → 才 executeTool()
  → 成功后写 E tool_result
```

这个顺序保证：无论在哪一步崩溃，日志里要么没有这次执行（可以重做），要么有 intent 但没 result（说明执行中崩了，需要判定），要么两条都有（已完成，直接复用 result 不重跑）。

## 关键机制

**幂等的两种做法**：

1. **幂等键**：原文付款例子用 `payment-${task.id}` 作为 key，崩溃后重跑同一 phase 只扣一次款。提交里的 `requestId` 同理。
2. **状态机收敛**：像「取消订单」这类操作，目标状态是幂等的（已取消再取消仍返回已取消），实现里显式处理「已经处于目标状态」的返回。

**Replay policy 决定重跑行为**：工具在记录 `R tool_started` 时带一个 `replay` 字段，恢复时按这个字段决定「重跑 / 跳过 / 交给模型」。这是 [[wiki/entities/pi]] Durable Runtime 的设计要点之一。

## 我的实例

`thoughts/035_✅差旅单管理工具定义及开发` / `thoughts/029_✅行程管理智能体的功能介绍及开发` 是同一套做法在行程单上的应用。

**反例（值得记）**：`thoughts/063_✅预定时，为什么下单用skill，取消用工具？` 指出取消操作天然幂等（重复取消无害），下单操作不幂等（重复下单有害）。这直接决定了 063 的分工结论 —— 幂等性是选择 Skill 还是 Tool 的一个隐含判据。

**GoGo Python 的三个层次（应用层，2026-10-23 本地验证）**：retry_of 只把同一用户轮次的失败委派关联到同一 task_id，复用原始问题；confirmation_token 是后续用户轮次提交申请的签名凭据；稳定业务幂等键才防止重复创建申请。三者不能互相替代，也不能因为超时就推断此前没有业务效果。旧代码对任一 failed 都拒绝整轮，导致成功重试生成的令牌没有保存；现按显式重试链最终结果判定，并将回复与 AgentState 一起提交。依据：[[wiki/sources/agent-开发学习笔记|Agent 开发学习笔记]] §19；界面完成信号见 [[wiki/concepts/SSE流式推送|SSE流式推送]]。

## 取舍与边界

**幂等键的生成必须稳定**。如果用 `uuid4()` 每次生成新键，重跑会产生新键，幂等失效。正确做法是用业务上稳定的标识（task id、订单号、`requestId`）。

**幂等键的存储成本**：需要一张表存「已处理的键」。键的 TTL 要长于最大恢复窗口，否则键过期后重跑又会重复执行。

**不是所有写操作都能幂等**。比如「追加一条日志」重复执行就是两条。这类操作要么接受重复（日志重复无害），要么改成「带唯一约束的 upsert」。

**确认令牌不是消费凭据，聊天回滚也不是业务回滚。**GoGo 的无状态签名令牌没有独立消费表，成功或失败不会自动销毁；到期校验拒绝，字符串仍可留在历史中。它仍由 Manage 模型从恢复上下文中取出并传参，保存状态不保证模型永不漏参。聊天事务只覆盖回复与运行状态，不能撤销此前已提交的差旅单；重试前应查询结果，重复提交依赖业务幂等。该实例来自 [[wiki/entities/agentscope|AgentScope]] 上的 GoGo 应用，不是框架对任意写工具的安全承诺，也不授权新增自动重试循环。

**失效条件**：
- 外部系统不支持幂等键（很多第三方 API 不支持）→ 只能在本地做去重表
- 幂等键存储在恢复时不可用（存储本身崩了）→ 恢复流程必须能在幂等键缺失时退化为「问人」
