# 旁路缓存

## 一句话定义

应用自己管理缓存：DB 是权威源，缓存只是加速副本，且应用始终保留「绕过缓存直连 DB」的兜底能力，所以叫旁路。

## 我目前的判断

这个模式的两条规则各有一个必须理解的点，记不住就会写出长期脏数据：

1. **读 miss 必须回填**。这是「缓存可以随时删」的前提 —— 删了缓存系统还能跑，靠的就是这条回源路径。它是设计义务，不是缓存自带的属性。
2. **写是删缓存，不是更新缓存**。并发下两个请求交错更新缓存，可能把旧值写回去覆盖新值，DB 与缓存长期错位；直接删掉则副本不存在，下次读 miss 自然加载新值。代价是删后到回填前多一次 DB 读，可接受。

## 关键机制

```text
读：① get 缓存 → ② 命中返回（零 DB）
    ③ miss → 查 DB → ④ 回填缓存 → ⑤ 返回
写：① 先写 DB → ② 删缓存（不是更新！）→ 下次读自动拿新值
```

**写顺序必须是「先写 DB 再删缓存」**：

```text
推荐：先写 DB，再删缓存
  写 DB ──→ 删缓存 ──→ 下次读 miss 回填新值
  风险窗口：仅「DB 已新、缓存未删」的极短瞬间读到旧值

错误：先删缓存，再写 DB
  删缓存 ──→ (窗口) ──→ 写 DB
               └─ 窗口内并发读：miss → 查 DB 还是旧值
                  → 回填旧值 → 你的写 DB 才执行
                  → 缓存长期躺旧值，直到下次删除/TTL 才纠正
```

错误顺序的代价远大于正确顺序：正确顺序的最坏情况是「短暂读到旧值」，错误顺序的最坏情况是「缓存永久错位」。

## 我的实例

`gogo-agent` 的写工具在成功后置 volatile 字段为 null，就是 Cache-Aside 的删缓存版本 —— 因为同会话缓存的「删」等价于置 null，成本几乎为零。这个简化成立的前提是「写方拿得到同一对象」，一旦跨会话就必须换成 Redis `DEL`。

Redis 分布式锁的加锁/释放也是一次旁路写：锁本身不是权威状态，DB 才是。

## 取舍与边界

**旁路缓存不保证强一致**，它保证的是「最终会一致」。要求强一致的场景（余额扣减、库存扣减）不能只靠缓存，必须让 DB 的原子操作或分布式锁承担正确性。

**缓存穿透、击穿、雪崩三个问题这个模式本身不解决**，需要额外机制（空值缓存、互斥重建、TTL 抖动）。本仓记录的实现里未见这些防护。

**删缓存失败时没有补偿**：如果 `DEL` 因为网络问题失败，缓存会躺旧值直到 TTL。正确做法是删失败后重试或将删除操作投递到消息队列，本仓无此实现。
