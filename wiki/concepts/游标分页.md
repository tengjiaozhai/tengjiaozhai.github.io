# 游标分页

## 一句话定义

翻页不用 `OFFSET`，而用「上一页最后一条的排序键」当锚点：`WHERE sort_key < 游标 ORDER BY sort_key DESC LIMIT n`。代价是只能顺着一个方向翻、拿不到总数，换来的是深翻页不随页号变慢、翻页期间新增数据不重复不漏行。

## 我目前的判断

**游标分页的正确性不在 SQL 里，在「游标是什么」这个契约里。** 服务端只要做对三件事：排序键唯一且单调、多取一条判断有没有下一页、没有下一页时把游标置空。剩下的坑几乎全在客户端——游标是状态，状态就要有生命周期和竞态守卫。

三件事的判据：

1. **排序键必须唯一且不可变**。自增主键最稳；用 `created_at` 这种可能重复的列，必须退化成 `(created_at, id)` 复合游标，否则同一时间戳的几条记录在页边界上会被跳过。
2. **多取一条（`LIMIT n+1`）是判 `has_more` 的唯一廉价办法**。拿返回行数 == n 当「还有下一页」会**谎报**：最后一页刚好装满时前端会多请求一次空页。
3. **游标只在 `has_more` 为真时回传**。`next_before_id = rows[-1].id if has_more else None`，否则前端拿最后一页的 id 去翻，会得到一页空数组而不是明确的「到底了」。

## 关键机制

```text
请求第 1 页      GET /api/projects?limit=20
服务端           WHERE owner=%s ORDER BY project_id DESC LIMIT 21
                 取前 20 条 → 第 21 条存在 = has_more
                 响应 {rows:[...20], next_before_id: rows[-1].project_id}

请求第 2 页      GET /api/projects?limit=20&before_id=<上一页最后一条 id>
服务端           WHERE owner=%s AND project_id < %s ORDER BY project_id DESC LIMIT 21
                 同理回传新的 next_before_id

最后一页         返回不足 21 条 → has_more=false → next_before_id=null → 前端停止请求
```

**和 OFFSET 的差别不是「快一点」，是复杂度阶数**：`OFFSET 10000` 要求数据库扫过并丢弃前 10000 行，页号越深越慢；游标版每一页都是「从索引里定位到锚点，往后读 n+1 行」，第 1 页和第 500 页代价相同。

**和 OFFSET 的第二个差别是稳定性**：翻页期间有新记录插入时，`OFFSET` 会让原本第 2 页的第一条被挤到第 3 页（漏行），或者重复出现（重复行）。游标锚在具体 id 上，新插入的记录 id 更大，永远落在已经翻过的区域之外，不干扰后续页。

**前端的三个状态变量**，缺一个就会出竞态：

```text
cursor      = null      // 下一页锚点；null 同时表示「到底了」和「还没开始」
generation  = 0         // 切换账号 / 点刷新时 +1，响应回来先比对，不等就丢弃
loading     = false     // 防重复请求（滚动触发 + 手动点击可能同时打）
```

## 我的实例

[[wiki/entities/trail-production-agent]]（试产搭配工作台）的项目列表，2026-10-30 由「一次全查」改成游标分页，是这套机制在本仓唯一的落地。

**服务端**（`src/trail_production_agent/intake/db.py`）：

- `PROJECT_PAGE_SIZE = 20`（:13）、`PROJECT_PAGE_MAX = 50`（:14）、`project_page_limit()`（:17）把请求值夹到 1..50，缺失或非法退回 20
- `list_projects_page(owner=None, *, limit=None, before_id=None) -> tuple[list[dict], bool]`（:218）动态拼 `conditions`，`params.append(page_size + 1)`（:238），SQL 是 `... ORDER BY project_id DESC LIMIT %s`（:244），`has_more = len(rows) > page_size`（:250）

**路由**（`src/trail_production_agent/service/app.py`）：`_int_query()`（:550）把畸形参数吞成 `None` 而不是 500；`projects()`（:562）返回 `{"projects": rows, "next_before_id": next_before_id}`（:576）。

**前端**（`src/trail_production_agent/web/index.html`）：`HISTORY_LIMIT = 20`（:821）、`historyCursor` / `historyGeneration` / `historyLoading`（:822–824）、`loadHistory()`（:886）在 `generation !== historyGeneration` 时直接 return（:900）、`observeHistoryPaging()`（:919）用 `IntersectionObserver` + `{rootMargin: '0px 0px 160px', threshold: 0.1}`（:927）在按钮进入视口前 160px 就预加载。

**排序键换过一次**：原来是 `ORDER BY created_at DESC, project_id DESC`，改成单列 `project_id DESC`。依据是实测 14 条项目 `created_at` 倒序与 `project_id` 倒序完全一致（`project_id` 是自增主键，等价于创建顺序），而单列才能让游标保持一个整数。

**接口是破坏性变更**：响应从 `{"projects": [...]}` 变成 `{"projects": [...], "next_before_id": ...}`，`tests/test_app.py` 里的精确相等断言必须同步改，否则测试是假绿。

**两个我自己引入的回归，都属「客户端状态生命周期」这一类**：

- **切账号后残留上一个账号的行**：原实现是「请求成功后才 `replaceChildren()`」，所以切账号后首次请求失败时，上一账号的 20 行还在表里。改成 reset 时**先清表再请求**。
- **首屏没有加载反馈**：reset 时先把 `cursor` 置空，而 footer 的显隐条件是 `cursor === null && !error`，于是首屏/刷新期间整条 footer 被藏掉，用户看不到「正在载入」。改成 `footer.hidden = !hasMore && !loading && !error`，并把 `cursor === null` 从「没数据」里拆出来。

**边界用例（写进 `tests/test_app.py` 的三条）**：

- 最后一页刚好装满：`before_id=6` → `[5,4,3,2,1]`，`next_before_id is None`（不谎报还有下一页）
- 空页不回游标：`before_id=1` → `{"projects": [], "next_before_id": None}`，不会回一个 `0` 让前端死循环
- 非法 limit：`limit=999` 夹到 50，`limit=0` 退回 20

## 取舍与边界

**为什么不用 OFFSET**：本项目改之前根本没有 `LIMIT`，是全表全量返回，所以第一动机是「别一次把整表塞给浏览器」，不是「优化深翻页延迟」。但在「会一直增长的列表」上，OFFSET 的深翻页退化是必然要来的，一次做到位比以后再改便宜。

**失效条件：**

- **要跳页**（第 3 页 / 第 7 页直达）→ 游标只能顺序翻，做不到。管理后台那种带页码的表格不适合。
- **要总数**（「共 137 条」）→ 游标版拿不到，必须另发一次 `COUNT(*)`。本仓的选择是不显示总数。
- **排序键会变** → 用户改了某条记录导致它跳到列表头部时，游标会漏掉或重复它。只读的时间序列表没有这个问题。
- **排序键不唯一** → 页边界上同值记录被跳过，必须改复合游标。本仓靠自增主键绕开了，没实现复合游标。
- **改排序键 = 废掉客户端手上的游标** → 服务端换排序规则时，旧游标会指向一个在新排序下无意义的位置，需要版本化或让前端重新拉第一页。

**索引还没加**：`(owner_staff_no, project_id)` 复合索引没建，现在 14 行数据下 `filesort` 可忽略，等量级起来再加——加索引要另写迁移，不提前做。

## 待澄清

- 复合游标（`(created_at, project_id)`）本仓未实现，只留了「排序键必须唯一」这条判据。如果哪天要按「最后编辑时间」排序，这条得补成代码。
- 前端没有请求超时与取消。切账号时靠 `generation` 丢弃过期响应，但底层请求仍然发完，慢网络下会白占连接。
- `HISTORY_LIMIT = 20`（前端）与 `PROJECT_PAGE_SIZE = 20`（服务端）是两份真相源，靠前端每次都显式传 `limit` 维持一致。改一边忘另一边不会报错，只会悄悄变成两个页大小。
