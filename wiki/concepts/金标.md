# 金标

## 一句话定义

老系统在标准输入下跑出来的**全量确定性标准答案快照**。它把「我觉得重构得差不多了」变成「0 差异，100% 逐格吻合」。

## 我目前的判断

重构写完、架构变优雅、微服务搭好了，然后呢？怎么证明新系统算出来的业务结果跟老系统完全一样？

靠人肉对比几十张几千行的 Excel，或者问业务专家「这个料选得对不对」——业务体量一大就瞬间崩溃，耗时耗力且任何一处看漏都会酿成线上事故。金标就是为解决这个问题而存在的：**高考试卷的标准参考答案**，或者度量衡里的国际千克原器。

对 AI Agent 场景，金标的价值还多一层：如果连底层纯规则引擎算出来的格子都不能保证，AI 在上面做决策就等于在沙滩上建大厦。有了金标，先关闭 Agent 跑纯规则模式，确保底层规则引擎与金标 100% 逐格一致，才敢把上层决策交给 AI。

## 关键机制

生成金标看起来只是「跑一遍存个 JSON」，但要成为工业级基准，五条原则缺一不可：

| 原则 | 为什么 | 怎么落地 |
|---|---|---|
| **1. 零侵入老代码** | 提取基准时改动了老代码，基准本身失去公信力 | 脚本通过 `sys.path.insert` 只读挂载老系统源码，不改动老系统任何一个字符 |
| **2. 必须走 Web 真实路径** | 老工程常有 CLI 和 Web 两套逻辑，CLI 往往年久失修 | 严格调用 Web 核心流程（`generate → initial_state → evaluate`），只抓 PM 真正看到的数据 |
| **3. 杀掉所有易变字段（100% 幂等）** | 时间戳、随机 UUID、机器绝对路径会随时间变化 | 保存 JSON 前彻底剔除生成时间和临时路径，`sort_keys=True` 锁死键顺序 |
| **4. 自校验（连续跑两次比对字节流）** | 万一漏删了某个时间戳怎么办 | 脚本内部连续执行两次生成，**逐字节比较两次的二进制流**，差一个字节直接报错中断，绝不把有毒夹具写进仓库 |
| **5. 输入指纹可溯源** | 别人怎么知道是用哪几份文件跑出来的 | 夹具元数据完整记录三份输入文件、关键源码、profile 的 **SHA-256** |

原则 4 是最容易被跳过、也最关键的一条。没有自校验，金标里藏一个随机 UUID，后续所有断言都会随机失败，且失败原因看起来像业务 bug。

## 我的实例

金标生成后躺在 `tests/fixtures/golden/x6728/expected.json`。每次改了 compat 解析、映射表或重写引擎，跑：

```bash
uv run pytest tests/test_golden_fixture.py
```

0.06 秒内验证：组合数量是否仍等于 20、展开候选底稿是否仍等于 60、默认收敛初稿是否仍精确等于 28（一供 20，二供 4，三供 4）、每块料的每个字段候选列表是否完全吻合。

飘红时断言精确指出第几块板的哪个字段和老版本对不上。

## 取舍与边界

**金标只覆盖确定性部分**。Agent 的决策质量（选得对不对、说明是否清楚）金标测不了，那属于 [[wiki/concepts/Agent评测]] 的范围。两者的分工是：金标守规则引擎的地基，Agent 评测管上层判断。

**金标会过期**。业务规则变更时老金标必须重新生成，否则会拦住正确的变更。这不是金标的缺陷，而是它要求「业务规则变更必须是显式的」。

**适用范围有限**：
- 输入必须是有限、可枚举的（X6728 这类产品定义书）
- 输出必须是确定性的（同样的输入必须产出同样的输出）
- 对 LLM 参与计算的部分，金标只能锁住「LLM 之前」的那一段
