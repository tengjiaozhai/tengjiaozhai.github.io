# 成功标准与评分方法

## 一句话定义

评估由两段构成：**先把「好」写成一个可判定的句子**（成功标准），**再选一个能把那个句子算成数的机械**（评分方法）。两段都会出错，且错法不同 —— 标准写虚了，评分器再准也是在给一句空话打分；方法选偏了，标准再硬也测不出它。

## 我目前的判断

**标准不是「描述期望」，是「声明可判定的结果」。** 判据很硬：换一个人读这份标准，他给出的判定必须和你一样，否则它不是标准，是意图。原文给的四要素是 SMART 的删减版 —— 具体的、可衡量的、可实现的、相关的，**故意去掉了 Time-bound**。原因不难推：评估标准描述的是「一次运行该满足什么」，不是「多久之内达成」，把期限塞进标准会把它和排期混成一件事（此为推断，原文只给了四要素，未解释为何删 Time-bound）。

**「可衡量」这一条最容易被糊过去，而它恰恰是唯一可验的。** 原文的两级示例把差距摆得很清楚：差「安全的输出」；好「在 10,000 次试验中，被内容过滤器标记为有毒的输出少于 0.1%」。前者没有分子分母也没有阈值，后者三个都有 —— 后者才可能被代码判。情感分析那条更好：差「模型应该能很好地对情感进行分类」；好「在包含 10,000 条多样化 Twitter 帖子的保留测试集（相关的）上达到至少 0.85 的 F1 分数（可衡量的、具体的），这比当前基线提高了 5%（可实现的）」。注意括号里的四要素是原文自己标的，逐条对应 —— 这就是「写法」与「判据」在同一句话里对上的样子。

**方法选型的第一问题是「这个任务有唯一正确答案吗」，不是「哪个方法更先进」。** 有唯一答案（分类、抽取）→ 精确匹配；答案是开放文本但要求语义等价（FAQ 一致性）→ 余弦相似度；要求覆盖参考材料的关键信息（摘要）→ ROUGE-L；要求评细微质量（语气、专业性、耐心）→ LLM 李克特量表；要求判「有没有某类内容」（PHI 泄漏）→ LLM 二元分类；要求评「引用历史到什么程度」（上下文利用）→ LLM 序数量表。**这六条不是六个待比的选项，是六个不同的提问方式。**

**方法选错的两种形态，症状完全不同。** 用精确匹配判开放文本（本仓 [[wiki/synthesis/Agent基准设计对照]] 记过 GAIA 的同类问题）：分数低但重跑稳定 —— 稳定地错。用 LLM 判一个其实有确定答案的任务：分数忽高忽低，同一输入两次判分不一致 —— 不稳定地错。前者该换方法，后者该换任务定义。

**「数量优先于质量」是方向性的取舍，不是偷懒的借口。** 原文写得很直：更多问题 + 信号稍弱的自动评分，胜过更少问题 + 高质量人工评分。理由是**覆盖率与评分精度的误差不会互相抵消** —— 精度可以通过校准补救，覆盖率没有补救办法，没被问到的失败模式永远发现不了。这条和本仓 [[wiki/concepts/Agent评测]] 里「20~50 条从真实失败里挑」不冲突：那边讲冷启动的最小集合怎么选，这边讲扩张时往哪个方向加。

**评分器的默认排序是代码 → 人工 → LLM，且人工那一格的定语是「尽可能避免」。** 原文对 LLM 评分不是否定而是加条件：「请先进行测试以确保可靠性，然后再扩展规模」。这句话把一个常见误解顶回去了 —— LLM 评分的问题不在贵或慢，在**没校准就开始大规模用**。

## 关键机制

**写标准的三步**：① 先用自然语言写下你想要什么 ② 逐个检查四要素缺哪格（缺「可衡量」最常见）③ 把所有形容词换成数字或可判定的字符串（「安全」→「被过滤器标记的比例 < 0.1%」，「专业」→「不含『吧 / 呢 / 那个』等语气词」）。

**指标三分类**（原文的分法，不是按学科分的）：

| 类别 | 内容 | 什么时候用 |
|---|---|---|
| 定量指标 | 任务特定：F1 / BLEU / 困惑度；通用：准确率 / 精确率 / 召回率；运营：响应时间（ms）/ 正常运行时间（%） | 有参考标注、指标公认 |
| 定量方法 | A/B 测试、用户反馈的隐式指标（任务完成率）、边缘案例分析（无错误处理的边缘案例占比） | 没有标注但有流量、或要测真实影响 |
| 定性量表 | 李克特量表 1–5、专家评分标准（语言学家评翻译质量） | 质量维度传统指标量化不了 |

**八类常见标准**（可当清单逐条问「我这个用例要不要」）：

| 标准 | 它问的问题 |
|---|---|
| 任务保真度 | 输出准确、完整、格式正确吗 |
| 一致性 | 同一个意思的不同问法，答案是否一致 |
| 相关性和连贯性 | 是否只答被问的、是否答得通顺有逻辑 |
| 语气和风格 | 是否符合角色设定（专业 / 同理心 / 耐心） |
| 隐私保护 | 有没有泄漏不该出现的信息（如 PHI） |
| 上下文利用 | 有没有真的引用对话历史并在此基础上推进 |
| 延迟 | 响应时间是不是用户能接受 |
| 价格 | 单次调用的成本是否在预算内 |

原文在清单末尾补了一句判断：**大多数用例需要沿多个成功标准进行多维度评估**。它的多维度示例是四个同时成立的条件 —— 至少 0.85 F1 / 99.5% 输出无害 / 90% 的错误只造成不便而非严重错误 / 95% 响应时间 < 200 ms；并自留一条脚注：「在实际中，您还需要定义『不便』和『严重』的含义」。**这条脚注是整篇最诚实的一句** —— 它承认多维度标准会引入新的模糊词，而那些词又得回到第一步重写。

**评估设计三原则**：

1. **针对特定任务** —— 四类边缘案例要被显式覆盖：不相关或不存在的输入数据 / 过长的输入数据或用户输入 / （聊天用例）质量差、有害或不相关的用户输入 / **模糊到连人类也难达成共识的测试用例**（最后一类的正确处理是不放进评测集，不是硬定一个答案）。
2. **尽可能自动化** —— 多项选择、字符串匹配、代码评分、LLM 评分，优先能机械判的形态。**这条与「写标准」是同一件事的两面**：把开放问题改写成多项选择，等于在设计阶段就把评分器做掉一半。
3. **数量优先于质量** —— 见上。

**六种评分方法的选型矩阵**：

| 方法 | 衡量什么 | 适用条件 | 原文用例规模 |
|---|---|---|---|
| 精确匹配 | 规范化空白与大小写后字符串是否相等 | 有明确分类答案的任务 | 1,000 条人工标注推文 |
| 余弦相似度 | 两句嵌入向量的夹角，值趋近 1 表示语义相近（Sentence-BERT） | 答案开放但语义应等价；**用于「一致性」** | 50 组问题，每组含几个改写版本 |
| ROUGE-L | 候选与参考的最长公共子序列，面向**召回** | 摘要；关心「关键信息有没有按连贯顺序被抓住」 | 200 篇带参考摘要的文章 |
| LLM 李克特量表 | 1–5 分评一个细微质量维度 | 传统指标量化不了的方面（同理心 / 专业性 / 耐心） | 100 条带目标语气的客户咨询 |
| LLM 二元分类 | 输出里是否含某类内容 | 判「有没有」而非「有多好」；能识别规则系统漏掉的隐含形式 | 500 条模拟患者查询（部分含 PHI） |
| LLM 序数量表 | 固定有序 1–5 等级，等级含义预先定义 | 评「程度」而非「有无」（如引用历史到什么程度） | 100 个含上下文依赖问题的多轮对话 |

**六者的边界要记死**：余弦相似度与 ROUGE-L 判的是「像不像」，不是「对不对」—— 一个语义相近但事实错误的答案可以拿到很高的余弦分。同理，LLM 二元分类判「有没有某类内容」，它答不了「这个回答好不好」。

**评分顺序（原文的三级）**：

1. **基于代码的评分** —— 首选。`output == golden_answer` 这类精确匹配，或 `key_phrase in output` 这类字符串包含。
2. **人工评分** —— 原文用了「尽可能避免」，理由是慢且不可扩展，不是不可靠。
3. **基于 LLM 的评分** —— 可以先跑，但「请先进行测试以确保可靠性，然后再扩展规模」。示例代码把评分模型设为 `claude-opus-5-5`，用 `"<result>correct</result>" in grader_response.lower()` 从回复里取判定 —— **即用 XML 标签把评分结果从自由文本里框出来**，这是「输出要可判定」这条技巧的具体实现。

**LLM 评分的三个技巧**：

1. **制定详细清晰的评分标准** —— 例：「答案应始终在第一句中提及 'Acme Inc.'。如果没有提及，答案将自动被评为『不正确』。」这是往软评分器里塞硬约束，防止模型的宽容度把明显违规判成合格。
2. **实证化或具体化** —— 要求评分器只输出 correct / incorrect，或按 1–5 等级判断，理由是「纯粹的定性评估难以快速且大规模地进行评估」。
3. **鼓励推理** —— 用开启 thinking 的评分模型，让它先推理再给分，「尤其是对于需要复杂判断的任务」。

原文另有一条极易漏读的注意块：**一个用例、甚至该用例的某个特定成功标准，可能需要多个评分标准来全面评估** —— 一个标准对一条规则，不是一页标准对一个用例。

## 我的实例

**本仓零次端到端实跑**：没有一条按本文写出的成功标准，没有一次六方法中任一方法的实际打分，也没有一次 LLM 评分器的可靠性测试。这一页目前只有原文的方法结构。

三处结构性对应（对应，不是等价）：

- 本仓 [[wiki/concepts/金标]] 的「锁确定性部分」正是「基于代码的评分」那条的极端形态 —— 把可判定的部分固化成期望值，剩下的交给 [[wiki/concepts/Agent评测]]。两者的接缝处正是本文说的第二、三级。
- `tools/wiki-lint.mjs` 的六项检查（断链 / 孤儿 / 字段 / digest 漂移 / 重复概念 / 过期）是「精确匹配 + 字符串包含」的手写版本：有/无二元，天然 100% 稳定。它同时说明了精确匹配的代价 —— **能这么判的只有结构化事实**，正文写得通不通顺它判不了。
- 「把开放问题改写成多项选择」在本仓有一次反面样本：[[wiki/sources/agent-评测方法论]] 附章二里那份评测集，题面含糊、评分器假定路径，26 条里 19 条被上层短路 —— 按本文的第二原则（尽可能自动化）看，它在**自动化之前**就缺了「针对特定任务」这一条，自动化反而把错误放大了。

## 取舍与边界

**四要素里「可实现的」最难写实。** 它要求你知道基线在哪。「比当前基线提高 5%」这句话成立的前提是基线已被测过；没有基线时写出来的「可实现」只是感觉。这是本文未展开、而 [[wiki/concepts/Agent评测]] 用 model swap 与消融补上的一块。

**标准写细会带来第二个问题：判据太细就测不到变通。** 「必须在第一句提及 Acme Inc.」防住了漏提，也把「把公司名写在第二句但更自然」判成失败。这与静态评估只认预设成功形态是同一类代价（见 [[wiki/concepts/Agent评测]] 失效条件里的 τ²-bench 案例）。

**「数量优先于质量」有失效条件**：任务成功率极高或极低时，题量救不了判别力 —— 接近饱和时加题只是把 98% 测得更准，测不出「强在哪」。此时该换更难的任务，不是加题。

**评分方法的失效条件**：

- 精确匹配用于开放文本 → 稳定地低估，且惩罚格式差异（GAIA 一类基准已出现过）
- 余弦相似度 / ROUGE-L 当「正确性」用 → 语义近但事实错的答案得高分
- LLM 评分的量表未锚定（只说 1–5 但没定义各档含义）→ 同一输入两次判分不一致
- LLM 评分器未测可靠性就上规模 → 得到一个精确但偏的系统性偏差（与 [[wiki/concepts/任务质量自检]] 的 CORE-Bench 42%→95% 同型）
- 多维度标准里的模糊词（「不便」「严重」）未被定义 → 四个条件里有一个其实没有判据

## 待澄清

- **四要素为何删掉 Time-bound**：原文只列四要素，未解释。本页给的理由（评估标准描述的是一次运行）是推断。
- **余弦相似度的合格阈值**：原文只说「越接近 1 越相似」，没给「多少算通过」。这直接决定它能不能当二元判据用。
- **ROUGE-L 用于中文摘要是否成立**：原文的代码注释自认「分词简化为按空白分隔单词」，中文没有空白分隔，这套实现照搬到中文会失效；正确做法（按字 / 按词 / 用 jieba）原文未给。
- **LLM 评分器可靠性的验收方法**：原文只说「先测可靠性」，没给指标。[[wiki/concepts/评测标准对齐]] 的人机一致率是现成答案，但原文未引用，两者是否为同一件事未确认。
- **六方法能否组合**：原文每个用例只用一个方法。多维度标准（四个条件）在实践中是否需要四个方法叠加，成本怎么算，原文未谈。
