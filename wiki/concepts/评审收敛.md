# 评审收敛

## 一句话定义

评审的价值不是每轮都能发现点什么，而是**在有限轮次内达到不再有新增发现的状态**。两个 agent 互为作者与评审时可以无限循环 —— 必须有机制把它掐断，否则「多跑几轮总能发现新 bug」会变成自我实现的假象。

## 我目前的判断

**agent 作者 × agent 评审器会无限循环，这是结构性的，不是个例。** 一处实测：CLI 项目里一个 PR 一夜之间循环了 **50 多次**，靠人工叫停。原因是双方都在按规则执行 —— 评审器每轮都能报出新发现，作者每轮都老老实实改，于是永远收敛不了。人写代码时有天然摩擦（没人愿意改 20 遍），agent 没有。

**「多跑几轮」是假收益，有两个数字撑着。** ①对反复报出的问题跑 git blame，**约 59% 是首轮就已存在的代码** —— 评审器很少发现新 bug，只是每轮多翻出几个旧问题；②团队承认，因为「每轮可能发现不同的 bug」，养成了**默认跑好几轮**的习惯，而这让情况更糟。这两条合起来把「提高召回」这个动机打穿了：召回率的提升很大程度上是在重复计入同一批旧缺陷。

**所以指标要从「召回」扩到「通过所需轮次」。** 这是本仓最该记的一条度量经验：只看召回，多轮就是纯赚；加了轮次，多轮的成本立刻显形。**两个指标必须同时看，任何一个单独都能被刷。**

**agent 处理一条评论的代价高一个量级。** 人忽略一条 nit 只要一秒；agent 处理它要多一个 commit、多一轮评审，而这一轮又会带来新的 nit。同一句评论对人和 agent 的成本完全不同 —— 这解释了为什么「减少轮次」在 agent 团队里从优化项变成必需项。

**收敛不是放松标准，是改变报告的粒度。** 四条改法里最关键的是「**指定 bug 类别**」：让作者一次改掉一整类问题，而不是发现一个改一个。这条直接减少了「改 A 引出 B」的来回 —— 它把评审从逐点发现改成按类修复。

**事故本身就是最好的评估集，而且可以直接用、不必先归因。** 收集导致事故的 PR + 修复提交 + 回滚，让懂代码的工程师核实每条 bug 的位置与判定对不对，评审系统每天拿这个集合打分。这条与本仓 [[wiki/concepts/失败归因与回归任务]] 的「生产轨迹 → 归因 → 回归用例」是两条路：那边先归因，这边直接当打分集。**省掉归因成本，代价是只能问「能不能复现同样的判定」，问不出「为什么漏」。**

## 关键机制

**四条收敛改法**：

| 改法 | 做法 | 治什么 |
|---|---|---|
| 限轮次 | 三轮之后，评审系统要求作者重新评估**方案**（而不是继续改细节） | 在同一方案上反复打磨 |
| 限范围 | 初始几轮之后，重评审只看新增 diff | 每轮重扫全量、重复报旧问题 |
| 指定类别 | 报「这一类问题」而非某一行 | 改一个引出一个 |
| 不重复报 | 已报过的不再报 | 59% 的翻旧账 |

另外两条配套：评审 agent 夜间跑**整个现有代码库**（让历史 bug 在扩散前被发现，而不是混进某个 PR 的评论里）；以及干净样本上的噪音测量（见下）。

**噪音治理的两个手段**：

1. **按人的处理方式给每条评论分类** —— 修了 / 否了 / 说明是有意为之 / 判定不重要。这个分类同时是「误报率」的度量。
2. **在已知干净的 PR 上跑评审系统** —— 观察它多大概率报出一个「如果照做会造成有害变更」的问题。这一步买的是「没有 bug 时它是否沉默」，与召回率完全正交。

**优先级是明示的**：第一，发现真 bug；第二，减少评审轮次。顺序不能反 —— 先保召回再压轮次，否则会把真问题一起压掉。

**噪音为什么必须单独管**：「不在乎报多少非 bug 的话，把找 bug 率提上去太容易了」。这句话点破了单一召回指标的漏洞 —— 报一万条总有真的。所以噪音不是召回的副产品，是必须独立设限的对冲指标。

## 我的实例

**本仓没有评审轮次的概念** —— 一次 ingest 走一遍，lint 报 0 项就结束，没有「再来一轮」这个动作，也就没有循环风险。

但有一条**结构相同的循环**值得记：`tools/wiki-lint.mjs` 的过期检查（`confidence: high` 且 `as_of` 超 180 天）会反复报同一批页，而修法通常是更新 `as_of` —— 这正是文中那条「59% 是在翻旧账」的同构形态：检查在重复发现同一件事，而「修」只是把标记挪一下。真正的修法应该是重读那一页的证据，判断结论还成不成立（§2.1 对 digest 漂移的要求就是这条）。

**可搬运但暂不引入**：给 lint 加「上次处理过的问题不再报」的机制。本仓只有 6 类检查、运行频率约 4 次/月，收益不抵成本 —— 按 [[wiki/concepts/摄入流水线]] 的口径，依据是使用频率不是技术优劣。

## 取舍与边界

**限轮次会漏掉需要多轮才能挖出的问题。** 高风险变更确实值得多轮迭代（文中也承认）。所以「限三轮」配了出口：三轮之后转去重新评估**方案**，而不是硬停 —— 把「这个问题需要换做法」与「这个问题需要再改一次」分开。

**「事故即评估集」有幸存者偏差**：只覆盖出了事故的 PR。那些「评审器漏了但也没出事」的缺陷永远进不了集合，所以这套评估集的召回上限天然低于真实缺陷分布。

**失效条件**：
- 只压轮次不看召回 → 评审系统学会「少说话」，静默退化且指标好看
- 只报不改、或改完不重跑 → 轮次下降但缺陷没修，等于把错误往后推
- 事故集长期不扩 → 评审器针对历史事故过拟合，新类型缺陷全漏

## 待澄清

- 「通过所需轮次」的目标值是多少？文中只说开始跟踪这个指标、给了 FIG E 的下降曲线，没给绝对值。
- 夜间全库扫描的规模与成本未提。对一个大型代码库每晚重扫，成本可能不低于白天评审。
- 59% 这个数字的统计口径：是「被反复报的问题里首轮已存在的占比」还是「首轮代码占全部报出的比例」？原文措辞只能推出前者。
