# 评测标准对齐

## 一句话定义

「好不好」是主观判断，主观判断必须先对齐才可用。对齐的产物不是分数，而是两个一致性系数：**人人一致率**（人与人）与**人机一致率**（人与 Judge）。两者不达标，机器给出的只是「机器标注」，不是「自动化评测」。

## 我目前的判断

**1 个独裁者好过 10 个民主者。** 这不是权力集中，是标准收敛的机制：10 个人各自定义维度，跨域通过率就不可比，而且内部拉扯的损耗比标准本身的不完美更贵。独裁者的职责有三件 —— 多方征求意见、整合成一套体系、在项目方无法对齐时拍板。它的风险（个人偏见）由 Good/Bad Case 持续修正，不是靠换人解决。

**对齐的抓手是「下钻 + 二元化」，收益可测。** 把「大而模糊」的概念下钻成多个清晰维度，再把每个维度压成 是/否/未知（0/1/unknown）。Beam 用这套改造评测体系后人机一致率从 **62% → 92%**；数字站长做到 **99%**。对手写一句「请判断是否口语化并打 0–10 分」（反例），对改成三条二元项：「是否以『您』指代骑手」「是否使用『甭客气』这类非官方词汇」「是否含『吧/呢/那个』等语气词」。**分数变成判据，分歧才有落点。**

**unknown 是探针，不是漏洞。** 用 unknown 的占比反查 Rubric 是否定义合理 —— unknown 多通常说明维度没拆够，或证据不足却硬要评。这条比「调阈值」聪明：阈值只改变判定分布，unknown 反查会暴露定义本身的问题。同理，[[wiki/concepts/在线评测]] 的 CTX 层「证据不足即 N/A」是同一种克制在工程里的形态。

**一致率是门槛，不是结果。** 达到可信阈值（业内多取 85% / 90%）之前，机器结果不能进决策；达到之后也只能叫「自动化评测」，且要持续复验 —— Judge 换版本、业务变化，旧系数就失效了。

**专家分歧不该被抹平。** 共识部分进评测体系；非共识部分往往意味着业务本身存在多种优秀策略（电销的「老练激进派 vs 细水长流派」），正确处理是把它转成 Agent 的风格分支、在不同测试集上分别评，而不是取中位数。

**Rubric 要像代码一样管。** 版本 + changelog（日期、版本号、改了什么、判分影响预估），离在线快照同步，**在线 Prompt 直接从 Rubric 文件生成** —— 避免「文档写一套、Prompt 写另一套」。淘宝某个域的 Rubric 迭代了数十版，没有版本化就查不清「这次通过率变化是标准变了还是 Agent 变了」。

## 关键机制

**对齐流水线**：定「独裁者」→ 下钻出维度 → 每个维度二元化 → 背靠背标注 → 算人人一致率 → 训 Judge → 算人机一致率 → 用 unknown 占比回查定义 → 迭代。

| 环节 | 判据 | 不达标的表现 |
|---|---|---|
| 人人一致 | 不同标注员在同一套 Rubric 上背靠背，一致率 ≥ 阈值 | 同一份回答有人判过有人判不过，跨域通过率不可比 |
| 人机一致 | Judge 与人工标注的一致率 ≥ 阈值 | 只能叫「机器标注」，不能进决策 |
| 定义健康 | unknown 占比低且稳定 | unknown 堆积 = 维度没拆够或证据不足 |

**两个必须分开的问句**：一致率只回答「评得稳不稳」，不回答「评得对不对」。Rubric 本身偏了的时候，人与人、人与机器可以高度一致地一起偏。「对」只能靠 [[wiki/concepts/任务质量自检]] 里的专家同判 + 参考解来验，两者不能互相替代。

**组织侧的配套**：数科（或评测团队）负责「怎么评」（pipeline、Prompt、指标计算），测试与产品负责「评什么」（标准与严格程度），两端通过打标闭环持续对齐。这条分工在淘宝那篇里写得很实，也是本仓此前没有的角度 —— 评测不只是技术活。

## 我的实例

**本仓零次人工标注对齐**：没有多标注员、没有一致率、没有 unknown 占比统计。

两处结构性类比（类比，不是等价）：

- `tools/wiki-lint.mjs` 的六项检查是「二元化」的极端形态：断链有/无、孤儿有/无、digest 漂移有/无。它一致率天然 100%，因为它不评主观质量 —— 这也说明二元化的代价：**能二元化的都是结构化事实，主观维度二元化要靠人先下钻**。
- 各页的「待澄清」段是 unknown 的容器，但没有统计，所以拿不到「unknown 占比」这个探针。

## 取舍与边界

**二元化会丢程度差异。** 「回复是否得体」压成 0/1 之后，无法区分「勉强得体」与「非常得体」。缓解是分维度（得体 / 准确 / 完整各一项），而不是把量表从 1–10 缩到 1–2。

**独裁者的偏差要显式对冲。** 用 Bad Case / Good Case 反向修正体系（美团：履约数字站长从 20 多个指标扩到近 200 个，扩的过程就是被 case 修正的过程），并在冷启动时选出最懂业务的人定标准。

**冷启动的取舍**：种子评测集 vs 小流量灰度直接收集 case。判据是「业务容错率」与「建种子集的成本是否超过线上试错的负面反馈」；美团推荐的落地方式是人工写少量、AI 辅助扩写。

**失效条件**：
- 只对齐一次 → Judge 或业务变了，系数早失效
- 一致率高但标准偏 → 一起错得很整齐（最常见的自欺形态）
- 标注员培训不足 → 背靠背变成各凭经验，一致率测的是运气
- 跨域硬套同一套 Rubric → 框架可以统一（漏斗层），子项必须分域（淘宝的「统一框架 + 分域子项码」是正解）

## 待澄清

- 85% / 90% 这两个阈值的出处与适用条件，两篇材料都只当常识引用，没给依据。
- 「框架统一、子项分域」的边界：什么算同一套框架？（淘宝答：漏斗层与取值口径统一；美团答：遵循同一套评测体系）两者口径不完全一致，本仓暂按「层可统一、项必分域」记。
- 背靠背标注的人力成本与最小可运行规模，本仓无数据。
