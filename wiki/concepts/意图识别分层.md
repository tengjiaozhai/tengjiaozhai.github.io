# 意图识别分层

## 一句话定义

把意图识别做成一条**短路流水线**：先用最便宜最快最确定的手段试，试不出来再逐级升级到更贵但更聪明的手段。

## 我目前的判断

「把用户的话丢给大模型，让它输出分类 JSON」能跑，但在企业里用起来有三个致命成本：

1. **慢**：一次 LLM 分类 300ms～2s，而「你好」「查一下审批进度」这类高频模板化的话本不该付大模型延迟
2. **贵**：每句都过一次大模型，token 成本随流量线性增长，其中相当大比例是「闭眼都能判对」的简单意图
3. **不稳定**：LLM 偶发漂移，同一句话今天判 A 明天判 B，难回归测试

分层正是为这三个成本设计的。

## 关键机制

| 层 | 手段 | 命中场景 | 目标延迟 | 调大模型 |
|---|---|---|---|---|
| **L0** | 规则 | 多意图识别 | < 50ms | 否 |
| **L1** | 规则 / 关键词（正则） | 高频、模板化、表达清晰（「报销」「你好」「查审批」） | < 50ms | 否 |
| **L2** | 向量相似度（RAG 检索） | 口语化、换了说法但语义清晰（「垫付的钱帮我弄回来」） | < 100ms | 否（只做 embedding） |
| **L3** | LLM 兜底 | 模糊、多意图、跨领域、信息不足 | 数百 ms～数 s | 是 |

设计哲学：**L0/L1 求快、L2 求全、L3 求准**。前两层能拦下的绝不惊动大模型。上线后通过日志观察各层命中率，持续把 L3 的流量往 L1/L2 迁。

**贯穿三层的硬约束：输出必须同构**。无论哪层命中，最终都产出同一个 JSON schema（`intents` / `primary_intent` / `multi_intent` / `overall_reason`），下游调度（MasterAgent 路由、子智能体直跳）完全不需要知道「这次是第几层判的」。

这个同构落在 `IntentRecognitionResult` 上，它是 L1/L2/L3 共同的产物类型，也是下游唯一认识的数据结构。`Source` 字段（`RULE` / `VECTOR` / `LLM`）只用于排障和日志。

## 我的实例

`IntentCategory` 是整个体系的公共词表 —— L1/L2/L3 都引用它，包含 `category` 与 `defaultTargetAgent` 两列。意图决定了路由目标，所以词表变更等于路由变更，改动面比看起来大。

`thoughts/018` 记录了引入 L1/L2 之后意图识别准确率下降的实际问题与修复。这是分层设计的代价：**新增的廉价通道会偷走本该走 L3 的模糊请求**，必须靠置信度阈值和 fallback 修正。

**GoGo 确认提交误判（2026-10-23，已做旧新规则对照）**：原句“确认提交”被改写成只含方案和酒店明细的句子；旧 L1 首命中酒店词，GoGo 本轮未开放管理工具。修复让缺对象的确认先承接历史，并要求命中片段覆盖本轮动作：旧错误改写现在弃权，补全“差旅申请”的句子才识别成 travel_application。这个意图进入管理工具开放条件后，才可调用 itinerary_manage_agent。实现存在、工具注册和实际委派是三件事。依据：[[wiki/sources/agent-开发学习笔记|Agent 开发学习笔记]] §18。

## 取舍与边界

**为什么不用 ReAct Agent 做意图识别**（`thoughts/010`）：意图识别的输出是固定 schema 的分类结果，不需要工具、不需要多轮探索。用 ReAct 会引入不必要的循环和不可预测性。

**为什么不放在主智能体里**（`thoughts/009`）：意图识别必须在主智能体**之前**完成，否则主智能体已经消耗了一轮上下文和工具调用预算，才知道「这问题根本不该进来」。做成 Skill 同理 —— Skill 是给已选中的执行者读的手册，不是路由层的组件。

**失效条件**：
- 领域词表变化频繁时，L1 正则要跟着改，维护成本转移到规则上
- L2 的向量库需要持续灌入新的说法（embedding 质量决定覆盖率），冷启动期 L2 命中率低
- 用户表达极度口语化或含错别字时，L1/L2 都会漏，最终仍落到 L3 —— 分层不降低最坏情况的延迟

## 冲突

**已澄清的范围差异**：旧判断“前两层能拦下的绝不惊动大模型”以表达清晰、对象明确为前提；§18 的确认句虽然命中背景名词，却没有明确业务对象，不能据此短路。新处理先补历史，仍不明确就请求上下文，不让向量近邻强行补单标签。依据分别是 [[wiki/sources/thoughts-意图识别三层|意图识别三层笔记]] 与 [[wiki/sources/agent-开发学习笔记|Agent 开发学习笔记]] §18。旧新规则差分已经区分两者：真实酒店查询保持 hotel_search，确认申请不会只因含酒店明细而走酒店查询；不意味着所有短句都必须调用模型。
