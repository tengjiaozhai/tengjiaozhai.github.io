# 在线评测

## 一句话定义

对**全量生产会话**做日级自动判定，把质量从「月度人工抽检」变成「每天一条可解释的曲线」。离线评估回答「发版前对不对」，在线评测回答「今天线上到底怎么样」。

## 我目前的判断

**可信度的瓶颈不在 Judge 模型，在数据质量与评测标准的持续校准。** 这是淘宝那句最反直觉的结论，也是本仓现在最认的一条。它的证据不是论证而是现象：流程类域早期通过率极低，逐层排查后发现根因是「Prompt 不适配线上数据」，不是 Agent 差；把数据清洗做对之后，同样的 Agent、同样的 Judge，通过率就上去了。换句话说，**早期低通过率测的往往是评测系统自己**。

**离线通过率与线上体验是两件事，不能互为替代。** 离线用例是被构造的（query 精心设计、工具返回完整可控），线上是脏的（表达模糊、带情绪、工具返回缺失或异常、数据分布持续漂移）。所以离线门禁守不住线上体验；反过来在线观测也不能当门禁 —— 它慢一天。两者是**闸门与仪表**的关系，缺一不可。

**数据清洗是四层工程，不是一步去重。** 格式修复、语义对齐、屏蔽干扰、入口过滤，每一层都对应一类只在线上才有的脏。其中最有信息量的是第三层：`tool_calls_json` 里带着工具接口的内部提示词（系统指令、开发注释），Judge 会把它误读成 Agent 的回复 —— 这种坑在离线数据里根本不存在。

**归因必须先排除评测自己。** 数据层 / Prompt 层 / Rubric 层 / Agent 真实质量，四层。淘宝的原话很扎：早期没有这层机制时，看到通过率下降第一反应是调 Prompt，有时越调越差 —— 因为根因在数据层或 Rubric 层，改 Prompt 只是在掩盖。这条与 [[wiki/concepts/失败归因与回归任务]] 是**上下两层**：先判「这次判定是否可信」，再判「Agent 哪一步错了」。

**跨轮上下文不是越多越好。** 把全对话的工具调用链都喂给 Judge，反而更差：前一轮的金额会被当成当前轮的事实依据。只传当条 `tool_calls` 后通过率显著跃升。这是「给足上下文」这条直觉在裁判场景的**反例**。

**样本量是可以算的，不该凭感觉抽。** ±1pp 需要约 4k 样本、±0.5pp 约 15k（纯随机采样保证无偏）。通过率波动远超 CI 宽度时，该怀疑 Rubric 或模型变了，而不是抽样噪声。

## 关键机制

**五阶段链路**：采集 → 清洗 → 推理 → 解析聚合 → 人工校验闭环。评测不是一次性交付，是「抽样打标 → 一致性校验 → 归因 → 改 Prompt/Rubric → 重跑 → 再抽样」的持续收敛。

**四层数据清洗**（对应四类线上脏数据）：

| 层 | 问题 | 手法 |
|---|---|---|
| 格式 | 各 skill 卡片协议独立、字段解析各异（离线 Prompt 直接复用会大量解析为空） | 逐域重写解析、补字段映射、超长文本截断 |
| 语义 | 用户说「已揽收」、系统字段是英文枚举，两者对 Judge 并不天然等价 | 在 Prompt 里显式建立用户语义 ↔ 系统语义的映射表 |
| 干扰 | `tool_calls_json` 里有工具接口的内部提示词，被 Judge 当成 Agent 回复 | 正则剔除，只保留实际调用参数与返回值 |
| 入口 | query 过滤规则过宽，不属于该 skill 的 query 混进分母 | 按 skill 标识精确过滤 |

**CNT 六层漏斗**（判定的结构，让「低在哪里」可回答）：

| 层 | 问什么 | 特性 |
|---|---|---|
| CTX 上下文门控 | 证据够不够评 | **唯一产生 N/A 的层**：证据不足即标记不可评，不进通过率分母 |
| OOSR 越界拒答 | 不该这个 skill 接的，是否拒答或交回上层 | 串行，可短路 |
| OOC 能力边界诚实 | 在范围内但超出能力的，是否诚实说明而非编造 | 串行，可短路 |
| TCC 工具链路 | 工具选对没有、参数是否匹配意图、链路是否自洽 | 串行，可短路 |
| CNT 内容与文本 | 回复的正确性、完整性、表达质量 | 串行，可短路，按域差异最大 |
| RED 安全红线 | 内部信息外泄 / 隐私 / 敏感词 / 违规引导 / 编造政策 | **与串行层并联、恒评**，前面判 0 也独立核查 |

短路的后果是「后续串行层记 N/A、整体判 0」（短板原则），而 RED 不受短路影响 —— 于是同一次判定同时给出**主因定位**和**安全兜底**。这个设计比「加权求和」好，因为它保住了「哪一层坏的」这个信息。

**单 case 的四层归因**（评测结果存疑时，先问「是谁错了」）：数据层（输入本身有问题）→ Prompt 层（规则理解偏了、缺边界示例）→ Rubric 层（标准与技术认知不一致）→ 只有排除前三层，剩下的才是 Agent 真实缺陷。

**两条稳定性细节**：**时间锚点**（Judge 没有「现在」的概念，把用户提问的时间戳拼进输入，否则「明天到」「近一年」全判不了）；**temperature=0.1**（0 会偶发输出僵死，高了同一 case 多次判定不一致）。

**架构分工**：数据在数仓（SQL）、推理在推理平台（workflow），两端解耦 —— 改 Prompt 不用改数据逻辑，改过滤规则不用重跑推理；中间加一个 check 节点比对输入表与输出表条数（公共资源池会超时丢数据、回刷是 append 不是覆盖，不比对就会把通过率算错）。按域拆独立 workflow，避免短板效应与故障扩散。

## 我的实例

**本仓没有在线评测，一天都没跑过。** 目前唯一的自动检查是 `tools/wiki-lint.mjs` 的六项结构校验，它查的是「页面之间是否自洽」，不查「内容对不对」；`output/` 里的成品也没有任何量化评测。

两处结构性类比（类比，不是等价）：

- CTX 层的「证据不足就 N/A」与本仓 `AGENTS.md` §6.2「先汇报后落笔」是同一种克制 —— **宁可不出结论，也不硬给一个数**。
- 本仓各页的「待澄清」段是 unknown 的容器：把判不了的显式记下来，而不是猜一个结论写进去。

## 取舍与边界

**全量 vs 采样**：全量贵但无覆盖率焦虑；淘宝的现实答案是先全量跑通再谈采样科学化（自评里「采样科学化」尚未使用）。本仓判断：日活低于数千条时全量比采样更简单，采样是规模问题的解不是精度问题的解。

**大 Judge vs 小 Judge**：大模型 + Prompt 先把效果天花板摸出来，再用沉淀的人工标注 SFT 蒸馏小模型 —— 前者的产出不只是分数，还是后者的对齐目标与训练集。轻量模型在「多条件复合判定 / 边界 case / 跨轮一致性」三类场景明显不如大模型，**Judge 的难度不在语言理解，在按规则做复杂判断**。

**成本是入场券，精度是护城河，闭环是复利**（淘宝的优先级判断，本仓认同）。三期顺序反了会先破产：先降本再补精度，等于低成本产出错误结论。

**失效条件**：
- **N/A 过多**：CTX 层把不确定样本踢出分母，若踢得太多，通过率会「虚高且不可比」——这条淘宝未讨论，本仓判断它是最隐蔽的失真源
- **Rubric 偏了但 Judge 和人一致**：一致率高只证明「评得稳」，不证明「评得对」；两者要分开验
- **Judge 版本漂移**：换模型或换 Prompt 后不重跑一致性校验，曲线会假性跳变
- **长尾**：头部模板 query 可以精细评，长尾只能给底线规则；如果长尾占比高，通过率的含义会稀释

## 待澄清

- 三类已知偏差（位置 / 冗长 / 宽松）的系统性治理：淘宝自评「尚未启动」，本仓也无方案。
- 通过率收敛到什么程度才算「真实线上水位」？淘宝说「靠多轮迭代逼近」，没有停止判据 —— 这可能是本轮所有材料里最大的方法论空洞。
- 坏样本自动回流训练（SFT / GRPO）未打通，本仓也无。这与 [[wiki/concepts/失败归因与回归任务]] 的「回归任务」是两条不同的回路（一个回训练、一个回测试）。
