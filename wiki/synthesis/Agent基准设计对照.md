# Agent 基准设计对照

## 问题

要自建评估集的人真正能借的不是**分数**（任务分布不同，公开榜单排名与业务成功率无必然关系），而是**设计手法**。但六个基准散在各自的论文与仓库里，没人把它们并排放过。这份对照要回答一个具体问题：**自建集时，哪几条设计手法必须先抄，哪几条抄不起。**

## 对比

**结构对照**（教材表 7-2 的骨架）：

| 基准 | 被测能力 | 任务来源 | 环境扮演者 | 验证器 |
|---|---|---|---|---|
| τ²-bench | 客服人机交互 + 工具调用 | 人工编写 + 组合生成 | 用户模拟器 + 业务数据库 | 四层检查，按 `reward_basis` 聚成二元 |
| SWE-bench Verified | 软件开发（coding） | GitHub 真实 issue，人工筛选 | 代码仓库 + 测试套件 | FAIL_TO_PASS / PASS_TO_PASS 双命题 |
| AndroidWorld | 操作 Android GUI | 参数化模板实例化 | 真实 Android 模拟器 | 最终 UI 状态断言 |
| OSWorld | 操作 Linux 桌面 GUI | 从预置中间状态启动 | 真实虚拟机 | 134 个独立评估函数 |
| Terminal-Bench | 操作 Linux 终端（coding） | 人工编写 | Docker 容器 | 文件系统检查 + 真实执行 |
| GAIA | 通用信息搜集 | 人工编写 + 专有附件 | 开放互联网 | 精确字符串匹配 |

**验证深度**（我的排序，依据是「能否发现表面完成而实质错误」）：

| 深度 | 基准 | 凭什么 |
|---|---|---|
| 最深 | OSWorld | 有完整系统访问权：查文件系统、进程、网络连接、DB 里 SQL 是否真执行、DOM / cookie / localStorage |
| 次深 | Terminal-Bench | 验证不可伪造的物理过程（从源码构建内核、加自定义 printk、在 QEMU 里启动看日志） |
| 分维 | SWE-bench Verified | 把「修复完成」拆成「已修」（FAIL_TO_PASS）与「未破坏」（PASS_TO_PASS）两个各自可证的命题，并排除 flaky 测试 |
| 细而浅 | τ²-bench | 过程维度最细（终态 / 关键动作 / 告知 / 自然语言断言四层），但被二元奖励聚合抹平 |
| 最浅 | GAIA | 精确字符串匹配：答案对就对，路径不可见 |

τ²-bench「细而浅」这条值得单独记：704 次带信息告知要求的运行里 240 次失败，其中 162 次是信息告知出错，**80 次（占全部失败三分之一）终态全对但告知错** —— 四层检查抓到了，聚合规则把它折进了同一个 0。这不是实现疏漏，是二元奖励的固有代价。

**防泄漏的四手法**：

| 手法 | 代表 | 效果 |
|---|---|---|
| 多源组合 + 专有附件 | GAIA | 单一网页给不出答案；部分任务配互联网上不存在的 PDF / 音频 / 图片 |
| 参数化实例生成 | AndroidWorld | 每次评估随机生成参数，回放固定操作序列失效 |
| 金丝雀标识符 | Terminal-Bench | 不阻止泄漏，但**使泄漏可被检测**（能输出 canary GUID 即说明数据进了训练集） |
| 动态生成任务实例 | τ²-bench | 同时改善覆盖率与抗泄漏 |

**质量维护的真实成本**：

- SWE-bench Verified：从 2294 个任务里抽 1699 个，93 名 Python 开发者逐条核查（描述是否清晰、测试是否覆盖边界、是否稳定、参考 patch 是否引入新错、难度是否合理），最终 500 个通过 —— 即被评估任务的 71% 被淘汰。换来的是更高信噪比与**评估成本下降约 80%**。
- OSWorld：2024-04 发布，15 个月内暴露出 300 余个问题，四类（环境反爬/CAPTCHA、任务描述歧义、验证过严过松、初始状态不完整）。约 10 人小组与多家机构合作两个月系统修复。

## 我的结论

1. **先抄验证深度，再抄题库**。题库可以自己写，验证器写不深是自建集最常见的病 —— 六个基准的分水岭几乎都在「验证器能看到多深」上，而不是任务数量。
2. **参数化生成是性价比最高的一招**（AndroidWorld 式）：一个模板派生大量实例，顺带解决抗泄漏与「精确测量单因素」两件事，成本远低于人工扩题。
3. **泄漏做不成防御就做检测**（canary）：承认猫鼠游戏没有终局，但让泄漏留下指纹。这一条比「设计一个不可泄漏的基准」现实得多。
4. **公开基准只用于粗筛与借鉴，不用于产品决策**。它的任务分布与业务分布不一致，在 GAIA 上提升两个百分点与退款成功率之间不存在必然关系。
5. **验证越深越贵**：OSWorld 的 134 个函数是拿 15 个月维护换来的。自建集应把深度压在「业务里真正会错的那几维」，而不是追平基准 —— 追平一个公开基准，等于替它付一次维护费。

## 适用范围

- 要在本仓或业务里自建评估集：用「验证深度 / 参数化 / 泄漏标记 / 维护流程」四条做设计检查表。
- 要选公开基准做粗筛：按「验证深度」列挑，而不是按榜单分数挑。
- 要评估一个基准本身是否可信：先看它的维护历史（OSWorld 的 300 余个问题就是一份可信度证据）。

不适用的地方：这份对照只覆盖**结果验证**这一个维度，交互协议与工具设计见 [[wiki/concepts/评估环境设计]]；错误定位见 [[wiki/concepts/失败归因与回归任务]]。

## 未定论的分歧

- **二元奖励的替代方案**：教材把它称作「固有代价」但没有给方案。过程颗粒度与跨模型可比性是否真的不可兼得，未定。可能的方向是分层报告（终态 + 过程两列），本仓无证据。
- **猫鼠游戏有终局吗**（教材思考题 2）：公开基准数据很快进训练集，是否需要「每次评估现场生成任务」的极端路线，无结论。
- **精确匹配对格式的惩罚**：GAIA 的字符串精确匹配会把「答案对但格式偏」判死，这类失败是否该归入能力缺口，教材未表态。
