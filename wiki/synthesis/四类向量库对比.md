# 四类向量库对比

## 问题

选型讨论容易陷在「哪家检索更准」和「哪个规模更大」。四个库实际回答的是不同层的需求，需要一个按形态与一致性划分的判断依据。

## 我的结论

四个库不是同一类东西，**形态决定运维成本、一致性模型和规模上限**。多数选型讨论搞错了焦点：规模不是主要决策点，一致性光谱和运维负担才是。

需要同库事务 → pgvector。几天出 demo → Chroma。千万级以内生产 → Qdrant。亿级以上 → Milvus。

## 形态与规模

| | 形态 | 语言 | 部署 | 规模上限 | 运维 |
|---|---|---|---|---|---|
| **Qdrant** | 独立专用服务 | Rust | 单容器起步 | 单机千万 / 集群亿级 | 1 个容器 |
| **Milvus** | 分布式专用服务 | Go + C++ | etcd + 对象存储 + MQ + 多类节点 | 十亿级 | 最重 |
| **pgvector** | PostgreSQL 扩展 | C | 无新服务 | 单机千万 | 复用现有 PG |
| **Chroma** | 嵌入式客户端库 | Python | 进程内 | 百万级以内 | 零配置 |

对数刻度看每格差一个数量级，但绝大多数业务 RAG 落在 100 万~1000 万区间，四个库都覆盖。

## 对比

### 分水岭一：混合检索（稠密 + 稀疏 + 重排）
稠密向量懂语义不懂字面，稀疏向量精确命中词但不认同义词，互补才有完整召回。

```text
Qdrant   原生：稀疏向量 + 命名多向量 + Query prefetch，RRF 融合
Milvus   原生：sparse/dense 字段 + Ranker（RRF/加权）
pgvector 无原生；0.7+ 有 sparsevec 类型，需自行拼 BM25 + vector 再融合
Chroma   无
```

### 分水岭二：元数据过滤

Qdrant 的过滤与 HNSW 集成（过滤感知遍历，payload 过滤是招牌）；Milvus 有倒排/位图标量索引和表达式过滤；pgvector 过滤就是 SQL `WHERE`，最灵活但 KNN 非过滤感知，强过滤时查询计划会退化；Chroma 无专用过滤索引，过滤越强越接近暴力扫描。

### 分水岭三：一致性（最容易被忽略）

```text
pgvector 完整 ACID ──→ Qdrant 单机强一致 ──→ Milvus 近似最终 ──→ Chroma 无事务
  （同库事务、         （WAL 崩溃恢复，    （TSO 时间戳，删除/       （单写进程，
    与业务数据原子提交） 集群 Raft 复制）      索引生效有延迟）          崩溃丢未落盘段）
```

向量数据「看起来查到了」时错误不明显，但删改是否即时生效、能否和业务数据原子提交，在生产里会踩实坑。

## 决策树

```text
① 向量要和业务数据同库 JOIN / 同一套事务、备份？
   需要 → pgvector（别家都做不到同库事务）
② 几天内出 demo / 本地工具？
   是 → Chroma；要平滑转生产可直接用 Qdrant 内嵌/小容器起步
③ 规模与扩展预期？
   千万级以内单机够 → Qdrant
   亿级以上/多副本/GPU → Milvus
   已有大规模 PG、不引新组件 → pgvector（接受混合检索自建）
```

## 手头服务器的实际盘点（2026-10）

```text
已有：Milvus standalone（Dify 依赖，19530 端口，~3.6G 内存）
      PostgreSQL 容器（Dify 内部网络，未映射宿主机）
没有：Qdrant / Chroma / Redis
空闲：Qdrant 6333 端口
```

AgentScope `main.py`：Redis 是硬依赖（`RedisStorage` 存会话/凭据/agent 状态），向量层默认 `QdrantStore(location=":memory:")` —— 进程内嵌，零外部依赖。

**结论**：演示级 RAG 不用装任何向量库；要持久化时新开独立 Qdrant 容器（6333 端口空闲），比往共享的 Dify Milvus 里灌数据更安全 —— 隔离、可卸载。

## 三条经验法则

1. **记忆层起步用进程内嵌或单容器**，量到百万级以上、过滤与混合检索成为硬需求时再上专用服务
2. **先上「必须件」（Redis），后补「可选件」（向量库）**，避免为一个演示需求引入一套分布式运维
3. **「已经有 Milvus 了所以用它」是陷阱** —— 共享实例的运维风险由所有使用方共担

## 未定论的分歧

- **Qdrant 集群版（Raft 复制）的实际运维体验**本仓无记录，当前只用到单机。所以 Qdrant 与 Milvus 在亿级场景下的对比，本页只能靠文档描述推断。
- **各库的中文/中英混合检索效果差异**未实测。混合检索能力表列的是「有没有原生支持」，不是「支持得好不好」。
