# ReMe 镜像构建断流排障

## 问题

2026-11-08 在服务器 121.43.231.155（阿里云 ECS，x86_64，Docker + buildkit）从源码构建 ReMe（agentscope-ai 的长期记忆服务，[[wiki/entities/agentscope]]）镜像。构建链路要过四类国际下载：ghcr.io 预构建镜像、Docker Hub 基础镜像、Debian apt、PyPI 包文件。四类全部反复断流，构建阻塞约 2 小时。本文沉淀：判「慢还是死」的方法、可复用的国内源清单、两个操作级坑。

## 对比

| # | 现象 | 根因 | 证据 | 解法 |
|---|---|---|---|---|
| 1 | ghcr.io 拉 `agentscope-ai/reme:main` 运行 20+ 分钟，0/8 层完成，自动重试 15 次 | 到 ghcr.io 的大文件长连接反复断 | `journalctl -u docker` 18:27–18:53 五次 `Download failed: connection reset / unexpected EOF`；`reme-pull2.log` mtime 停更 | 放弃拉取，改源码构建 |
| 2 | 每次 `docker pull` Docker Hub 镜像都先慢一轮 | `/etc/docker/daemon.json` 把 docker.aityp.com 配成 registry-mirror，但该站是查询站不是加速器 | journalctl 19:18–19:29：先 aityp 报 `no basic auth credentials` → 再 1ms → 再直连超时 | 移除 aityp；`kill -HUP <dockerd pid>` 热加载，不重启 dockerd（`Live Restore: false`，重启会连带停 `redis-gogo`/`qdrant-gogo`） |
| 3 | 带 aityp 账号拉取仍被拒 | 站点规则：只许网页查询，禁止当 registry 用 | 拒绝原文 `Please do not configure this site as an accelerator address`；帮助页 docker.aityp.com/article/10 | 用站点详情页官方列出的华为云源 `swr.cn-north-4.myhuaweicloud.com/ddn-k8s/docker.io/<repo>:<tag>` 拉取后 `docker tag` 还原；注意 python 类路径不带 `library/`、node 类带 |
| 4 | 构建卡 `apt-get install` 约 5 分钟；换 `--network=host` 后 update 过了、install 下载又断 | 容器内到 deb.debian.org 的传输断流（宿主机 curl 该源 1.8 s 返回 200 正常；IPv6 curl 秒失败——假说未证实，见「未定论」） | apt `methods/http` 与 `gpgv` 睡眠态 5 分钟、CPU 时间不涨；日志 mtime 停更 | 两个 Python 阶段 FROM 后插一行 sed 把 apt 源换成 `mirrors.aliyun.com`（Release 实测 0.065–0.069 s，官方源 1.8 s），加 `--network=host` 重建 |
| 5 | pip 装 `jieba`（19.2 MB sdist）卡 7+ 分钟；`openai_codex_cli_bin`（183.2 MB wheel）换源后仍断过一次 | PyPI 文件走 Fastly CDN，大文件长连接断流；换阿里云源后断流率大降但未归零 | **`/proc/<pip pid>/io` read_bytes 两次采样 delta=0（8 s）**；openai_codex 三个 5 s 窗口 307200 / 307200 / 0；`ss -tnp` 见 ESTAB 但零传输 | pip 加 `-i https://mirrors.aliyun.com/pypi/simple/`；断流包重启重下约 1 分钟完成 |

结果：`reme:local`（1.83 GB）构建成功；容器 healthy；公网 `0.0.0.0:2333` 匿名 `POST /health_check` 返回 200（`ReMe v0.4.2.3 - healthy`）。

## 我的结论

**判停三步法（日志停更 ≠ 卡死）**：

1. 看日志 mtime / 行数是否停更；
2. 看进程状态（睡眠态且 CPU 累计时间不涨）；
3. **测数据流**：`grep read_bytes /proc/<pid>/io` 两次采样求 delta，配合 `ss -tnp` 看连接。**delta=0 才杀**。pip 在非终端下下载大文件不逐行输出，只看日志会把「慢」误判成「死」。

**国内源清单（大文件优先换源；小请求实测一直正常，不必全换）**：

- 基础镜像：`swr.cn-north-4.myhuaweicloud.com/ddn-k8s/docker.io/<repo>:<tag>`，拉完 `docker tag` 还原原名
- apt（Debian bookworm）：`sed -i 's|deb.debian.org|mirrors.aliyun.com|g; s|security.debian.org|mirrors.aliyun.com|g' /etc/apt/sources.list.d/debian.sources`
- pip：`-i https://mirrors.aliyun.com/pypi/simple/`
- `daemon.json` 的 registry-mirrors 只放真正支持匿名拉的站；改完 `kill -HUP` 热加载，不重启 dockerd

**操作守则**：

- 远端杀进程时 `pgrep/pkill -f` 的模式必须自不匹配（写 `docker.buil[d]` 而非 `docker build`），且 kill 与重启拆成两条命令——当晚两次 exit 255 都是模式匹配到命令自身。
- BuildKit 层缓存 + Dockerfile 自带的 pip cache mount 让重试只重下未完成部分：断流重启的经济学成立，别怕重启。
- 长任务套后台监控（30 s 采样日志行数 + 停滞阈值 + 总时长上限），监控只负责唤醒，杀/重试按证据决定。
- `--network=host` 的额外收益是可观测：容器内进程的 TCP 连接在宿主机 `ss -tnp` 里可见，bridge 网络下看不到。

## 适用范围

- 适用：阿里云等国际出口服务器；大文件长连接（实测 ≥19 MB 即可断流）；`docker pull/build`、apt、pip。
- 不适用：能直连 ghcr / Docker Hub 的网络环境（先试官方源，别无脑换源）；小文件高频请求。
- `--network=host` 主要用于构建期排障；运行期容器网络按业务需要选择。

## 未定论的分歧

- **IPv6 假说未证实**：`deb.debian.org` 解析出 IPv6 地址且本机 `curl -6` 秒失败（退出码 7），但 IPv4 大文件同样断流，IPv6 不一定是根因。
- **断流的链路层原因未定位**：Fastly CDN 与 Debian 官方源都断，阿里云基本不断但 pip 的 183 MB 包仍断过一次；未做抓包，只能说「与国际长连接相关」。
- **bridge vs host 网络对断流率的影响未对照**：bridge 构建断（apt）、host 构建也断过（apt 下载、pip openai_codex 各一次），样本不足以区分网络模式与运气。
