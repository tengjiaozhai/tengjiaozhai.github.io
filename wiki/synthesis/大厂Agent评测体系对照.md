# 大厂 Agent 评测体系对照

## 问题

2026 年下半年同时出现三篇大厂评测实践（美团图灵、京东、淘宝淘天），加美团的 VitaBench 基准。它们讲的**不是同一层的东西**，混着读会得出矛盾结论：

- 美团说「起步阶段让数据飞轮转起来，别设计复杂体系」
- 京东说「先立一套业务结果金字塔，再谈指标」
- 淘宝说「先做四层数据清洗和六层漏斗，不然数字不可信」

这三句并不冲突，但读起来像三种主张。本页的目的是把它们放到同一张图上分层，回答两个问题：**评测该先投哪里？六模块里哪些能直接抄？**

## 对比

**一、通用六模块 × 三家覆盖**

| 模块 | 美团（图灵） | 京东 | 淘宝（淘天） |
|---|---|---|---|
| 指标体系 | 三层桥：模型能力 ↔ 桥梁指标 ↔ 业务结果 | 业务结果金字塔：业务 / 体验 / 应用 / 研发 | 三层漏斗复合指标：路由准确率 × 回复正确率 |
| 评测集治理 | 种子集 + Bad/Good Case 喂养（20 → 近 200 指标） | 真实数据 + 专家逐条验证 + P0–P3 诚实分级 | Rubric 版本化 + 离在线快照同步 + 代码仓库托管 |
| 分层归因 | 五环节里的分析归因 + 评测维度拆解 | 归因即分层兜底：多智能体角色边界、NL2SQL 四级 | 四层：数据 / Prompt / Rubric / Agent 真实质量；CNT 层定位 |
| 评估器 | 客观 + 主观并行，主观校准客观 | 性价比阶梯：能算的不问模型 | 大 Judge + Prompt 先摸天花板，规划 SFT 小模型 |
| AgentOps | 长程评测基建七能力（回放 / Case / 沙箱 / 引擎 / 归因 / 回归 / 门禁） | 三条业务线各自的飞轮，行为数据当信号 | 五阶段 pipeline + 数仓/推理解耦 + check 节点 |
| 安全红队 | 未展开 | 200+ 手法 / 31 类风险 / 三路研判互证 | RED 恒评层（五条红线，短路不影响） |

**二、指标体系的三种切法**

| 切法 | 起点 | 好处 | 代价 |
|---|---|---|---|
| 桥（美团） | 承认能力指标与业务指标不可直映，造中间层 | 能回答「为什么业务变差」 | 桥梁指标本身要定义，且跨团队维护 |
| 金字塔（京东） | 从生意倒推四层 | 评测和经营说同一套话，跨部门零折算 | 应用层以下的分数不直接对外，全靠行为数据兜 |
| 漏斗（淘宝） | 定义「执行成功率」为复合指标 | 可拆到「路由坏了还是回复坏了」 | 只适用有明确 skill 路由的产品形态 |

**三、归因其实是三层，不是一层**

| 层 | 问什么 | 代表 |
|---|---|---|
| 评测自证 | 这次判定本身可信吗（数据/Prompt/Rubric 有没有错） | 淘宝四层归因 |
| 评测归因 | 失败集中在哪一层、哪个子项 | CNT 六层 + 子项码拆解 |
| Agent 归因 | 轨迹里第几步开始偏、属于哪类错误、责任方是谁 | [[wiki/concepts/失败归因与回归任务]] 的九类与首错；VitaBench 的推理 61.8% / 工具 21.1% / 交互 7.9% |

## 我的结论

**1. 三家在同一个问题上收敛了：拒绝「模型分数 → 业务结果」的直接映射。** 差别只在桥怎么搭 —— 显式造桥梁指标（美团）、让评测说经营语言（京东）、把端到端成功率拆成复合指标（淘宝）。这条收敛值得单独记：本仓此前把「公开基准分数不能指导产品决策」当结论，现在有了三种落地方案的样本。

**2. 归因要做三层，本仓此前只有第三层。** 最贵的一课是淘宝那句「早期看到通过率下降第一反应是调 Prompt，越调越差，因为根因在数据层或 Rubric 层」。**评测结果存疑时，先怀疑评测自己** —— 这与 [[wiki/sources/demystifying-evals|Anthropic 原文]]「先查评测系统再动 Agent」是同一条结论，但淘宝给了它一个可执行的四层分类。

**3. 「自建基准」是战略问题，不是技术问题。** 京东的三种战略（参评 / 内嵌 / 立尺）比任何指标细节都更有决策价值：立尺派的前提是行业颗粒度足够深、且愿意付公信力成本（方法全透明、第三方同测、不回避对自家不利的结论）。没有这三道对冲，「运动员兼裁判」会直接把结论作废。

**4. 成熟度阶梯比「有没有评测」更好用。** 淘宝的 L1 能评 → L2 评得准 → L3 省又全 → L4 自动闭环 → L5 自运营，配美团的长程基建七能力，可以合成一张「你现在在第几级、下一级需要什么」的表。本仓对照自评：**L1 都没到**（没有 Judge、没有一致率、没有日级观测，只有结构 lint）。

**5. 五个共同盲区，三家都没解决**：坏样本回流训练（淘宝自认未打通）；三类偏差的系统性治理（淘宝自认未启动）；「真实水位」的停止判据（只靠多轮迭代逼近）；长尾 query 的评法（只能给底线规则）；评测结论到修复的自动化（淘宝仍是人工排期）。写在这里是为了防止以后把「大厂这么干」当成「这么干就对」。

## 适用范围

- 要从零搭评测：先按 L1→L3 排投入（能评 → 评得准 → 省又全），别一上来做六模块全覆盖。
- 要选「指标怎么搭桥」：产品有明确 skill 路由走漏斗（淘宝），重经营结果走金字塔（京东），跨团队口径打架走桥（美团）。
- 要判断「要不要自建基准」：先看行业颗粒度与公信力成本，见 [[wiki/synthesis/Agent基准设计对照]]。

不适用：本页只覆盖「有线上流量 + 多业务域」的大厂形态。单产品、日活几百条的团队，直接抄 L1 + 四层归因即可，六模块里 AgentOps 与安全红队可以延后。

## 未定论的分歧

- **起步该先做什么**：美团说先让飞轮转（少指标、多 case），淘宝说先做数据清洗与六层框架（不然数字不可信）。分歧原因是**阶段不同**（美团讲 0→1，淘宝讲 1→N 的放大），但两条路径在小团队会抢同一份预算，没有取舍判据。
- **过程评测的边界**：美团把「过程层」列进四层内容，Anthropic 原文强调「只评产出不评路径」。两者不冲突（前者评稳定性与效率，后者反对固定路径断言），但「过程层具体评什么不算评路径」没有可操作判据，见 [[wiki/concepts/Agent评测]] 的取舍段。
- **领域规则放哪里**：τ²-bench 用 Policy 文档，VitaBench 主张编码进工具图 —— 这是一处真实的设计分歧，记在 [[wiki/concepts/评估环境设计]] 的「冲突」段。
