# WeKnora 知识库误删复盘

## 这一篇覆盖什么

一份**待落盘的原始记录**占位页：2026-10-28 对自建 WeKnora v0.8.3 误删知识库、只读核查、四表回滚、向量重建的完整过程。边界是「一次操作事故的一手记录」，不含 WeKnora 的能力评测，也不含横向对比。

- 覆盖：删除实现的两段结构（同步软删 + 异步清理）、清理顺序、表结构差异、向量化文本公式、恢复实测数字。
- 不覆盖：其他版本的行为差异、其他知识库产品的删除语义、原始文件的取证价值（已确认物理删除）。

## 与其他笔记的重叠点

- **与 [[wiki/concepts/幂等与写入恢复]] 的分工**：那页讨论「崩溃后哪些工具能安全重跑」，本页讨论「删了之后能救回多少」。共享的是一条顺序原则 —— 先判断状态是否可信，再决定动作。
- **与 [[wiki/synthesis/copy-from-program处置]] 的对照**：同为 incident，方向相反。那边是外部入侵、处置对象是正在运行的恶意进程；这边是操作失误、处置对象是数据库里的删除标记。共同点是**处置前必须先确认真实状态**（那边先 `ps` 看进程，这边先查队列）。
- **与 [[wiki/concepts/向量库选型]] 的接口**：向量库选型关注「存哪、能不能混检」，本页补充一条选型时不会问的指标 —— **删除语义**。四类向量库在「删一条数据是软删还是硬删」上的行为差异，选型对比表里没有。

## 本篇独有、别处没有的

1. **一次真实删除在关系表 / 向量表 / 对象存储上的行为分裂**，带表结构与源码双证据。
2. **「接口返回 200 不含恢复信息」这条判据的完整推演** —— 从 DELETE 响应到四张表的 `deleted_at` 差异。
3. **派生数据重算的公式还原方法**：不照抄代码，而是从未损坏的库里取真实行逐字比对。
4. **软删设计的三项代价**（清理幂等、查询过滤易漏、配额不释放），以及「`embeddings` 不软删其实是合理权衡」这个反直觉判断。
5. **从事故侧唯一有效的预防**：读权限与删权限分开授。降权、回收站、二次确认都是补丁。
