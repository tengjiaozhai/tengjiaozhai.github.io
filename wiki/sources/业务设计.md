# 业务设计

## 这一篇覆盖什么

`letter-auto`（承认书智能检测）**一个项目的业务设计**：检测对象分几类、规则怎么排、判定边界在哪、agent runtime 为什么只做薄薄一层。

边界：

- 讲的是**一个已上线项目的当前形态**，不是跨项目方法论。文中出现的四层并发数字、八次引擎切换都是该项目的事实，换到别的项目要重新验证。
- **不覆盖**规则的具体判定口径（22 条规则各自的阈值与反例散在 24 个 Evolution 节点里）；也不覆盖前端、鉴权、部署。
- 文首挂了 `output/letter-auto-architecture.html` 完整图解，正文另嵌四张分节 SVG（瓶颈迁移 / 资源槽嵌套 / 引擎时间线 / 观测三条线）。**图解不是独立证据源**，它是这篇 raw 可视化后的副本。

- **`agent 开发学习笔记.md` 全篇** 讲 letter-auto 与 gogo-agent 的**代码实现复盘**，本篇讲**设计取舍**。同一系统的两个切面，不冲突。
- **`Agent 评测方法论.md` / [[wiki/concepts/Agent评测]]** 的「三种真相」（嘴上说完成 / 真完成 / 做了一半越界）与本篇「缺失 ≠ 不存在」是同一个问题的两侧：评测关心 agent 有没有真做到，检测关心取证有没有真取到。**推断**：两者可以共用一套「证据不足要有独立出口」的原则，但本文与评测方法论都没有交叉引用这一点，需另行验证。

## 本篇独有、别处没有的

1. **四种结果状态的分法与理由** —— 只认 PASS / FAIL 会让「大量没看清」呈现成「大量不合格」。这是本库唯一一处明确写出「INCONCLUSIVE / NOT_CHECKED 不是失败」的设计说明。
2. **两个 gate 的边界** —— 文件名料号（前置于循环）与封面身份（`gate=True`），取最后一个 gate 作为串行/并行分界线。全库只此一处记录了这个实现细节。
3. **模型输出跑偏的四种形态与各自的 reason_code** —— 网关包装（键名不固定，用结构判据而非白名单）、空对象（pydantic 会用默认值造出假 FAIL）、与 schema 字段集完全不相交（BUG-014）、SDK 会话内重试的两类失败（JSON 写坏 vs schema 不符，修法相反）。
4. **「接口没动过，实现换了八次」的引擎演进** —— Paddle 云端 → MinerU 云 → registry → MinerU 内网 → paddle-local → MinerU 唯一 → vlm-engine → 云端适配器；两次判断被自己推翻（EV-009 扩成唯一引擎、EV-012 的 paddle-local 两天后被删）。
5. **最危险的一种失败** —— EV-027 的漏检没有变成 FAIL，而是因为目录列全了仍 PASS，导致整块检查**静默跳过**：取证失败被伪装成「这条规则不存在」。
6. **三组「不做什么」** —— 不把规则槽位从 4 调到 8；不把全尺寸页并发当作文档质量的页并发；不拿 12 份封面实验当完整容量结论。
