# thoughts 簇 · 工具家族定义

## 这一簇覆盖什么

差旅业务十一个工具/数据模型的具体定义与实现：数据模型（030 / 064）、政策工具（032 / 034）、联系信息（033）、差旅单读写工具（035）、冲突检测（036）、预订管理（037）、方案计算（045）、实时联网查询（046）、最终审核（054）。

边界：这是**同一条业务线的工具逐一铺开**，每篇单看是一个工具的设计记录，合起来才构成「一套业务系统怎么把能力切成工具」的完整答案。

## 十一个工具的分工

| # | 工具 / 模型 | 形态 | 关键设计 |
|---|---|---|---|
| 030 | 差旅业务数据模型 | 数据 | 两个业务单据：差旅单 + 预订 |
| 064 | 预定业务数据模型 | 数据 | 第三方平台出票，本系统也落一条记录 |
| 032 | 差旅政策工具 | 读 | 政策不是静态文档，是「职级 × 城市等级」的查找表 |
| 034 | 差旅政策知识库 | RAG | **为什么政策要同时有 Tool 和 RAG** —— 语义问题查数字答不了 |
| 033 | 用户联系信息工具 | 读 | 姓名/手机/身份证/邮箱，可推断出发地 |
| 035 | 差旅单管理工具 | 读写两个 Bean | **「查」和「改」物理拆开** |
| 036 | 行程冲突检测工具 | 计算 | 不检测会怎样（并发冲突、日期重叠） |
| 037 | 预订管理工具 | 读 + 取消写 | 创建在 BookingAgent，本工具只管查询与取消 |
| 045 | 行程方案设计工具 | 计算 | plan itinerary 的「计算大脑」 |
| 046 | 目的地实时联网查询 | 外部 | 强依赖当下外部世界状态（天气、活动、签证） |
| 054 | 行程方案最终审核工具 | 计算 | 交给用户前的最后一道工程校验 |

## 可抽出的原子

- **政策要 Tool + RAG 双通道**（032 / 034）：数字类问题查工具，语义类问题查知识库。这是本仓最清晰的一个「同一领域需要两种检索形态」的论证 → 待抽：结构化查询与语义检索的边界
- **读写工具物理拆成两个 Bean**（035）：好处见原文，是工具设计的一条硬规则 → 待抽
- **为什么单独做冲突检测工具**（036）
- **精确计算必须落 Tool 而不是 Skill**（045）→ [[wiki/synthesis/Skill-vs-Tool判据]]
- **实时外部状态的工具定位**（046）：与知识库检索的区别在于时效性 → [[wiki/concepts/工具缓存]] 的「不该缓存的工具返回值」
- **最终审核的四类检查**（054）→ 待抽：输出前的工程校验
- **第三方平台 + 本地落库的双写**（064）
