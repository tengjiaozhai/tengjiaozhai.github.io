# thoughts 簇 · 上下文工程

## 这一簇覆盖什么

六篇「怎么把一个会话的 token 花得更值」的具体手法。它们是同一目标的六个方向：瘦身（079 / 084）、裁剪（080）、缓存（082）、卸载（083）、记忆（085）。

边界：**记忆自动压缩**（`thoughts/078`，88 行）讲的是 `AutoContextMemory` 框架机制而非应用侧手法，单独成 A 层页；**系统提示词利用 KV 缓存**（`thoughts/081`，126 行）是另一条主线，也单独成 A 层页。

## 可抽出的原子

- **Skill 不一定省 Token**（084）：这是本簇最反直觉的一篇。渐进式披露听起来省，但正文折叠策略不对反而更贵 → 待抽：渐进式披露的真实成本
- **第三方 Skill 瘦身的四项改造**（079）→ 与 `thoughts/058`（[[wiki/sources/thoughts-第三方skill生产化]]）互补：058 讲功能可用，079 讲体积
- **工具返回裁剪**（080）：十几次工具调用，每次原文入 memory → [[wiki/concepts/工具缓存]] 的另一面（缓存是「不重复查」，裁剪是「查了也不全留」）
- **显式缓存 vs 隐式缓存**（082）：百炼的隐式缓存（`thoughts/081`）零改造成本但控制力弱；显式缓存要手工标记断点 → [[wiki/concepts/KV缓存与提示词缓存]]
- **中间文件卸载**（083）：与 [[wiki/concepts/上下文压缩]] 的「大消息卸载到 map + UUID 回查」是同一思路的不同实现（落盘 vs 内存 map）
- **长期记忆的读写时机**（085）：语义召回 vs 关键词匹配、手动管理个人偏好 → 待抽：长期记忆的工程实现
