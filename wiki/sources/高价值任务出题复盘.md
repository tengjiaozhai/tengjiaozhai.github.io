# 高价值任务出题复盘

## 这一篇覆盖什么

一次完整的「按交付门槛出题」过程记录：素材是一条 88.6 分钟 / 176 步的真实工程会话，成品是一道 100 项评分、19 条判定口径、5 个 CSV 附件的业务裁定题，实测三轮考生（v10 / v11 / v11.1）。

- 覆盖：交付门槛的三条判定怎么落地、题目四层（口径 / 数据 / 判分 / 可复现）的设计、为什么必须把代码素材换壳成业务、难度为什么长在分支数上、子代理实测闭环与轨迹度量、判分未命中的归因分流。
- 不覆盖：题目内容本身（那份题在 `/Volumes/PortableSSD/questions/kgviz-task/`，不进 wiki）；多模型横评（只测了 `deepseek-v4.1-flash` 一个）；「怎么想出业务场景」的创意方法。

## 可抽出的原子

| 原子 | 去向 |
|---|---|
| 代码题有可执行 oracle、业务裁定题没有 → 前者靠测试收敛（步数短、得分率高），后者错得安静 | [[wiki/synthesis/高价值任务出题方法]] |
| 输入素材换壳的三条映射：坐标空间 → 双时点、多轮 QA → 多时点复算、并行 review → 独立产能 | 同上 |
| 难度是分支数不是算力：5×7×2=70 格乘法结构 + 带符号结果 + tie-break 两处相反 + 上层再套敏感性 | 同上 |
| **长而不难**：70 格机械重复拉步数拉时长，也让强模型一次写对就 100 分 | [[wiki/concepts/任务质量自检]] 的「满分是坏信号」补一条实测 |
| 判分未命中先分「算错」与「没写清」，后者改题面不改答案键 | [[wiki/concepts/成功标准与评分方法]] |
| 评分脚本必须先用标准答案自测满分 | [[wiki/concepts/任务质量自检]] 已有「参考解」，本篇给的是**脚本自测**这一具体形态 |
| 闭卷考场的搭建规范：只放 prompt + 附件、grep 越界两路核查（文件 + 事件流）、每轮清残留 | [[wiki/concepts/评估环境设计]] 的「可重置环境」补一条实测做法 |
| 派考生用 spawn_teammate 不用 subagent；等待用 wait_agent + bash 轮询不用 run_code 内 setTimeout | 同上（执行协议） |
| 三条门槛是「或」关系，过一条即达标；但过形式门槛 ≠ 过能力门槛 | [[wiki/synthesis/高价值任务出题方法]] |

## 与其他笔记的重叠点

- [[wiki/concepts/任务质量自检]]：那页的判据是「分数不对时先证明题目是对的」，本篇给的是它在**自建题**场景下的完整实例（v10 → v11 → v11.1 的两次刻意加难）。那页的 CORE-Bench 42%→95% 是外部基准的自检，本篇是自家出题的迭代，方向一致。
- [[wiki/concepts/成功标准与评分方法]]：那页讲「标准怎么写实」（四要素、六方法、代码优先的评分顺序），本篇补的是**标准在自建题里怎么被考生误读**——精度约定没写死会持续扣分，这一条那页没有。
- [[wiki/concepts/评估环境设计]]：那页的五要素里「可重置环境」与「执行协议」，本篇给了具体形态（闭卷考场目录 + 残留清理 + 越界双证据）。
- [[wiki/synthesis/Agent基准设计对照]]：那页的「验证深度」排序（OSWorld 最深 → GAIA 最浅），本篇的「有没有可执行 oracle」是同一个梯度的另一种切法 —— 代码题 = 深验证，业务裁定题靠答案键 = 中等深度。
- [[wiki/synthesis/大厂Agent评测体系对照]]：都是「自建评估」的实践侧，那页是高层的团队打法（参评派 / 内嵌派 / 立尺派），本篇是一个人的出题流水线。

## 本篇独有

- **「长而不难」这个失败形态的实测数据**：70 格机械重复 → 226 步 / 36 分钟 / 100 分。步数与时长都过了门槛，分辨力却是零。本库此前没有这个具体形态的记录。
- **换壳映射表**：原始素材的每个工程细节如何一对一映射成业务分支（坐标空间→双时点、QA→多时点、review→独立产能），以及换壳的验收标准是「每个业务分支都能在旧素材里找到结构同源的对应物」。
- **三类判定失真源**：复用上一轮中间产物（`work_D.pkl`）导致轨迹跨轮、静默改题面导致考生按旧版作答、subagent 被用户插队打断导致无产出。
- **精度约定作为题面条款**：把「分钟/件数整数、金额/百分比 1 位小数、禁区间禁约」写成题面第 6 节，而不是靠评分键宽容。
