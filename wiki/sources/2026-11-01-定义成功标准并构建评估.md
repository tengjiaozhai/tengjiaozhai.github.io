# 定义成功标准并构建评估

> 外部裁剪件。原文 <https://platform.claude.com/docs/zh-CN/test-and-evaluate/develop-tests#tips-for-llm-based-grading>，作者 Anthropic，2026-11-01 落盘（3,698 行，digest `3698-c154a419`）。
> 这是 Claude 平台文档「测试与评估」一章的**产品侧**版本，与本仓 [[wiki/sources/demystifying-evals|Demystifying evals]] 那篇**研究方法侧**的文章不同：那篇讲「评估一个 agent 该注意什么」，这篇讲「一个开发者在控制台里怎么把评估搭起来」。

## 这一篇覆盖什么

- 覆盖：成功标准的四要素与写法、八类常见标准（任务保真度 / 一致性 / 相关性与连贯性 / 语气与风格 / 隐私保护 / 上下文利用 / 延迟 / 价格）、多维度标准叠加、评估设计三原则、**六种自动评估方法**（精确匹配 / 余弦相似度 / ROUGE-L / LLM 李克特量表 / LLM 二元分类 / LLM 序数量表）各配七种语言实现、以及评分顺序（代码 → 人工 → LLM）与 LLM 评分的三个技巧。
- 边界：**方法教材**，不是效果报告。每个方法都给「衡量什么 / 适合什么 / 一个用例规模」，但**没有一个方法给出在本仓可复现的实测分数**。
- 不覆盖：统计显著性、非确定性下的 pass@k / pass^k、失败归因、评测集维护与饱和。这四块在 [[wiki/concepts/Agent评测]] 与 [[wiki/concepts/失败归因与回归任务]] 里，本文不提。
- 形态：官方中文文档，经页面源文件（MDX）完整抓取，代码块 49 个逐行比对无差异；1 张示意图已落 `raw/assets/2026-11-01-定义成功标准并构建评估/`。

## 与其他笔记的重叠点

- **与 [[wiki/sources/demystifying-evals|Demystifying evals]]（2026-01）是同一组织的两份文档，层级不同**：那篇的三类评分器（代码 / 模型 / 人工）与本文的评分三级排序**结论一致但方向相反地表述** —— 那篇是「三类评分器各有强弱，按任务挑」，本文是「优先代码，其次人工，最后 LLM」。两者不冲突：本文是给单个开发者的**默认优先级**，那篇是给评估设计者的**选型框架**。
- **与 [[wiki/concepts/评测标准对齐]] 分工**：那页问「评得稳不稳」（人人一致率 / 人机一致率 / unknown 占比），本文的「评分标准要细」只给了一条**写法**层面的建议（「答案应始终在第一句中提及 Acme Inc.，否则自动判不正确」），没有一致率概念。本文落在**标准怎么写成可判定的样子**，那页落在**写完之后怎么证明它被一致地执行**。
- **与 [[wiki/concepts/Agent评测]] 分工**：那页的核心口径（pass@k / pass^k、能力集 vs 回归集、只评产出不评路径、统计显著性）本文一条都没有。本文补的正是那页缺的两块：**标准从哪来**（怎么把「好」写成可测的句子）与**方法怎么选**（六个具体算法的适用条件）。
- **与 [[wiki/concepts/任务质量自检]] 相邻**：那页问「评分器自己有没有错」，本文的「先在小规模上测 LLM 评分器的可靠性，再扩规模」是同一个告诫在产品文档里的形态，但**没有给出任何验收方法**（没有参考解、没有 pass@100、没有审计清单）。

## 本篇独有、别处没有的

1. **成功标准的四要素是 SMART 的删减版** —— 具体的 / 可衡量的 / 可实现的 / 相关的，**故意去掉了 Time-bound**。这解释了为什么本仓此前从别处看到的「SMART 五要素」放进评估语境总有一格填不上：评估标准描述的是**一次运行该满足什么**，不是**多久之内达成**。
2. **「数量优先于质量」被写成明确取舍**：更多问题 + 信号稍弱的自动评分，胜过更少问题 + 高质量人工评分。这条与本仓 [[wiki/concepts/Agent评测]] 的「20~50 条从真实失败里挑」并不矛盾 —— 那边讲冷启动的最小集合，这边讲**规模扩张的方向**（扩题量而不是扩评分精度）。
3. **四类边缘案例**是可执行的清单：不相关或不存在的输入数据 / 过长的输入数据或用户输入 / （聊天用例）质量差、有害或不相关的用户输入 / 模糊到连人类也难达成共识的测试用例。最后那类尤其少见 —— 它承认有些题**不该进评测集**。
4. **六个方法各配七种语言（python / typescript / csharp / go / java / php / ruby）的可运行示例**，每段都带「这个分数怎么读」。这是本仓唯一一份**多语言对照的评分器实现**，此前所有评分器讨论都停在概念层。
5. **余弦相似度与 ROUGE-L 的具体分工**：余弦相似度用 Sentence-BERT 句嵌入、值趋近 1 表示语义相似，适合「一致性」（同一问题应产生语义相近的答案）；ROUGE-L 用最长公共子序列、面向**召回**，适合摘要（高 ROUGE-L 表示以连贯顺序抓住了关键信息）。两者都不是「对不对」的判据，是「像不像」的判据。
6. **LLM 序数量表 vs 李克特量表的区分**：李克特量表是「1–5 分打分」，序数量表是「固定有序的 1–5 等级且等级含义预先定义」。原文用前者评语气（细微、传统指标难量化），用后者评上下文利用（是否引用历史、是否基于历史推进）。
7. **评分器的「自动降级」规则**：「答案应始终在第一句中提及 Acme Inc.，如果没有提及，答案将自动被评为不正确」—— 这是把一条**硬约束**塞进软评分器，避免 LLM 的宽容度把明显的违规判成合格。

## 待处理

- **没有任何实测结果**：六个方法只有示例代码与用例规模（1,000 条推文 / 50 组改写问题 / 200 篇文章 / 100 条咨询 / 500 条患者查询 / 100 个多轮对话），**没有一条分数、耗时或成本**。所以本文只能支撑「方法长什么样」，不能支撑「哪个方法更准」。
- **示例代码未在本仓运行过**：七语言 × 6 方法共 49 个代码块全部原样落盘，一行未改，但也没有执行验证（需要对应语言的 SDK 与 API key）。
