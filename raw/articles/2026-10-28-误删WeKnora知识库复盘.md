# 误删 WeKnora 知识库复盘

> 内部记录，非外部裁剪。`url` 留空是因为没有外部出处 —— 这份记录本身就是一手材料。
> 记录对象：自建 WeKnora `v0.8.3 / 3e22822`，PostgreSQL `paradedb/paradedb:v0.25.11-pg17`。

## 事故经过

为一个 API key 验证写权限，向生产 WeKnora 发出：

```text
DELETE /api/v1/knowledge-bases/3da0dd27-5b0b-4002-9e1d-0f4478809865
→ 200 {"message": "Knowledge base deleted successfully", "success": true}
```

目标库「字段字典」：100 个文档、13,901 个分块、2,832 个 Wiki 页。该 key 具备 `manage_kbs`，因此通过 `OwnedKBOrAdmin + KBAccessWrite` 两层鉴权。

删除后即时观测：

```text
GET /knowledge-bases          → 只剩自建的 probe-temp
GET /knowledge-bases/{id}     → 404 knowledge base not found
GET /chunks/{doc_id}          → 404 Knowledge not found
POST /knowledge-search        → 0 hits，meta.rerank.outcome = "no_candidates"
```

一度误判为「异步清理已完成、数据不可恢复」。查库后推翻。

## 删除实现

`DeleteKnowledgeBase`（`internal/application/service/knowledgebase.go:799-801`）注释原文：

```go
// This method marks the knowledge base as deleted and enqueues an async task
// to handle the heavy cleanup operations (embeddings, chunks, files, graph data)
```

两段结构：

1. 同步：`s.repo.DeleteKnowledgeBase(ctx, id)`（第 830 行）—— GORM 软删
2. 异步：`asynq.NewTask(types.TypeKBDelete, ...)`（第 893 行）入队

`ProcessKBDelete`（第 909 行）的清理顺序：

```text
1020  retrieveEngine.DeleteByKnowledgeIDList   ← embeddings，物理删
1041  chunkRepo.DeleteChunksByKnowledgeID     ← chunks，软删
1051  fileSvc.DeleteFile                      ← 磁盘文件，物理删
      cleanupWikiForKnowledgeBase             ← wiki_pages，软删
```

## 表结构差异（恢复上限的依据）

查 `information_schema.columns where table_name='embeddings'`，13 列：

```text
id | created_at | updated_at | source_id | source_type | chunk_id |
knowledge_id | knowledge_base_id | content | dimension | embedding |
is_enabled | tag_id
```

**没有 `deleted_at`**。而 `knowledge_bases` / `knowledges` / `chunks` / `wiki_pages` 四张表都有。

|---|---:|---:|

| `knowledges` | 100 | 0 |
| `chunks` | 13,901 | 0 |
| `wiki_pages` | 2,832 | 0 |

## 恢复前的检查

```text
asynq:kb_delete  pending=0 active=0 scheduled=0 retry=0
task_pending_ops (scope='knowledge_base') = 0
```

队列已空 → 回滚后不会被再删。这一步是动手前提。

## 恢复动作

四张表一个事务，先只读导出 16,834 行主键作备份：

```sql
BEGIN;
UPDATE knowledge_bases SET deleted_at = NULL WHERE id='<kb>';
UPDATE knowledges      SET deleted_at = NULL WHERE knowledge_base_id='<kb>';  -- 100
UPDATE chunks          SET deleted_at = NULL WHERE knowledge_base_id='<kb>';  -- 13901
UPDATE wiki_pages      SET deleted_at = NULL WHERE knowledge_base_id='<kb>';  -- 2832
COMMIT;
```

## 向量重建

**不走重解析**：`POST /knowledge/{id}/reparse` 会重跑 docreader、可能改 `chunk_id`、重新触发 Wiki 生成。

**从 chunk 文本重算**。关键是还原向量化公式：

```go
// internal/application/service/knowledge_index_content.go:12-20
func buildKnowledgeIndexContent(knowledge *types.Knowledge, content string) string {
	title := strings.TrimSpace(knowledge.Title)
	if title == "" { return content }
	return title + "\n" + content
}

// internal/types/chunk.go:225-233
func (c *Chunk) EmbeddingContent() string {
	body := strings.TrimSpace(c.Content)
	if c.ContextHeader == "" { return body }
	return c.ContextHeader + "\n\n" + body
}
```

合并：`embeddings.content = title + "\n" + context_header + "\n\n" + content.trim()`

**验证公式的方法**：从未损坏的库取一行真实值逐字比对。

```sql
SELECT e.content, c.context_header, c.content, k.title
FROM chunks c JOIN knowledges k ON k.id=c.knowledge_id
JOIN embeddings e ON e.chunk_id=c.id
WHERE c.chunk_type='text' LIMIT 1;
```

实测结果一致（`T客户测试策略拉通(手机).xlsx` + `\n## 大版本升级\n\n| 测试项目 | ...`）。

**只取 text 类型**：源码 `knowledge_process.go:612` 过滤 `chunk.ChunkType == types.ChunkTypeText`，`parent_text` 不参与向量化。

## 实测数字

| 项 | 值 |
|---|---|
| 待嵌入 chunk | 12,934（13,901 中 text 子集） |
| text chunk 长度 | 最长 875 / 平均 321 字符 |

| 嵌入服务批次上限 | **20**（超限 400 `InvalidParameter: batch size is invalid`） |
| 实际批次 | 16 |
| 结果 | 12,934 / 12,934，`missing = 0` |

批次上限是二分测试出来的：32 报 400，20 通过，21 失败。

## 损失

**100 个原始文件不可恢复。** `STORAGE_TYPE=local`，文件位于 `/data/files/10001/<knowledge_id>/`。实测目录还在、内容为空（`ls` 返回 0 项）。

源文件在本地仓库 `changelog/10.27-material`（153 个文件）完整保存，可重传；但解析、Wiki 生成、自动标签需重跑。

## 判据小结

| 判据 | 内容 |
|---|---|
| 可恢复性从哪看 | 查目标表有没有 `deleted_at`，不从 DELETE 返回码推断 |
| 恢复第一步 | 查清理队列有无残留，不是直接 UPDATE |
| 清理进度怎么判断 | 按源码删除顺序对照表行数（先删的最不可恢复） |
| 派生数据重建前提 | 还原准确的派生公式，否则行数对但检索静默失效 |
| 唯一有效的预防 | 读权限与删权限分开授 |
