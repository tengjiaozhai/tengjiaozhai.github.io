# Claude Code 团队怎么做代码评审

> 中文译文。原文 *How the Claude Code team does code review*，@addyosmani 转述 Anthropic 团队实践，2026-10-26。
> 原文是该团队 claude.dev 文章的重写版，并经 Pangram 核查。

我们之前提过，Claude 写了 Claude Code 大约 90% 的代码。那么在这个量级上我们怎么做代码评审？还有谁在读代码？如果代码出了问题会怎样？

本文讲我们团队在 Claude Code 的代码评审流程，以及我们是怎么改进它的。6 月到 9 月，合并进 Claude Code 代码库的 PR 数量翻了一倍多，而需要回滚的 PR 占比下降了 40% 以上。

我们并没有停止做代码评审。我们做的是把**大部分阅读自动化**，并把它调优到以人的时间和精力为优化目标。我们还大量投入，让回退错误变得更快更容易。

## 重新思考代码评审的目标

当 agent 开始写代码，变更量会迅速膨胀。在我们的 monorepo 里，5 月每天大约合并 2,500 个变更，到今年 9 月已经超过 30,000 个。

Claude Code 不在这个 monorepo 里，但它承受的压力同样大。节奏到了这个程度，逐行人工评审变得越来越难，甚至不可能。

**代码评审有两个目的：**

1. 在发布前发现并修正缺陷
2. 建立对代码库的共同理解

本文主要讲第一个目标，第二个放到文末讨论。

我们认为「有没有人读过这段代码」是一个不精确的度量。真正该问的是：**这个变更有哪些地方可能出问题，哪一个检查 —— 自动的还是人工的 —— 才是抓它的正确工具？**

这个问题同时改变了评审的时机。传统上，代码评审是事后检查：代码写完、PR 提了，然后等别人来看。我们把评审**织进了工作流**，它更像写作过程中一直在跑的拼写检查。

大多数变更在交给人看之前，已经被 Claude 至少评审和修正过一次。这样我们拦住了绝大多数例行缺陷，把人的注意力留给更高层的判断。

## 人的时间与注意力

我们要把人的时间和注意力留给只有人能做判断的事，同时确保自动化能覆盖其余部分。即便按现在的节奏，人要做的事依然极多，团队几乎每天都在遇到新的、没见过的问题。

因此，人的时间是**双向成本**。我们既统计人花在评审上的时间，也统计人花在修烂代码引入的缺陷上的时间。只降前者不降后者，并没有真的省下人的时间。

所以我们的目标是：Claude Code 各仓库（CLI、桌面端、Web 应用、移动端）里大多数 PR，**最多一个人过手就能合并**（这个人可以就是作者本人），同时回滚率和事故率不上升。

我们衡量人力投入用三个指标：每个 PR 的人工批准中位数（含 95 分位）、人工评论数、PR 等人所花的时间。回滚率和事故率作为护栏：这两个指标一升，说明我们没有减少人力，只是把它挪了位置。

## 一个变更的旅程

一个典型变更，无论来自工程师的笔记本还是 Slack 里的 Claude 会话，都要经过多层评审。

上图是 Claude Code 里一个典型变更从作者环境到生产的路径。大部分流程是自动的，人的注意力集中在有风险的部分。

我们有**六层检查**，外加一套回滚机制来处理漏网的问题。

每一层都会抓到一些缺陷、漏掉另一些。很少有缺陷能穿过全部层；万一穿过去了，我们有回滚机制。

### 1. 建 PR 之前的验证

我们大部分的评审在创建 PR 之前就做完了。我们要求 Claude 做**可运行的事**，比如跑测试、跑构建、把截图和设计稿对比，而不是只说「任务完成」，我们要求它**把结果拿给我们看**。然后由一个子 agent 用全新的上下文评审 diff。这两个策略都写进了团队的最佳实践指南。

开 PR 之前，我们中很多人还会跑几个内部 skill：找 bug、缩减 diff、端到端验证，以及按设计规范检查 UI 改动。

据 Claude Code 的创建者 Boris Cherny 说，给 Claude 配上**验证流程**大概是提升产出质量最大的关键。他估计验证流程能把 Claude 的输出质量提升 2 到 3 倍。

不同领域的验证流程可以差别很大：有时只是跑一条 bash 命令，有时是跑一整套测试，有时是在浏览器或手机模拟器里测这个应用。

如果自动评审器反复报同一个问题，我们就**从源头修**：改 skill 本身、加一条 lint 规则，或者更新文档文件，比如：

**CLAUDE.md** —— 项目描述文件，用来给 Claude 提供项目上下文（技术栈、约定、目标、非目标）。Claude Code 每次评审都会读这个文件，所以在大代码库里我们把它写得很短，其余部分引用到别处文档。当代码违反了这个文件里的约定，或者某个更新让文件内容过期了，评审器会指出来。

**REVIEW.md** —— 代码 owner 告诉评审器「我这块什么最重要」的文件。我们会单独验证评审器是否真的遵守了这些准则。好的 REVIEW.md 都很短，聚焦在：

- 定义项目层面的失败（文档不该说谎；配置不该错路由）
- 限制吹毛求疵
- 定义忽略路径
- 要求给出文件 + 行号引用，不许猜文件名
- 要求顶层摘要包含问题数量，并明确写出「无问题」

### 2. 每个 PR 都跑 AI 评审

每个 PR 在人工评审之前都先过一遍 Claude 评审。

diff 会被放到**整个代码库**和 **PR 作者声明的意图**两个背景下分析。它检查：这个变更是否真的解决了那个问题；这个变更是否契合更大的系统；这个变更有没有破坏代码库的其他部分。

评审 bug 修复时，机器人会尝试定位根因。

团队的公开产品 Code Review for Claude Code 现在对所有 Team 和 Enterprise 客户开放，本地也有轻量版 /code-review。

从研究预览版发布以来，内部拿到**实质性评审意见**的 PR 占比从 16% 升到 54%。Code Review 能在**超过 1,000 行**的 PR 里发现大多数 PR 的问题，而对较小的 PR 大多返回干净结果。仓库管理员可以配置 Quick、Standard、Deep 三档；当「漏掉一个 bug 的代价高于评审耗时」时，用 Deep。

在交给人之前，发现要经过多个其他 agent 的审核：

- 多个 agent 并行找 bug
- 一个独立的投票决定某条发现是有效还是误报，只有票数足够的才确认
- 只跟风格、诊断、清理相关的发现被过滤掉（这些过滤器在他们的 PR 上做过 A/B 测试才上线）

剩下的发现以行内评论呈现，按严重程度排序，并标记为：

- Important（重要）
- Nit（小问题）
- Pre-existing（既有问题）—— 这样不会因为不是本 PR 引入的 bug 而冤枉作者

所有发现都必须处理：要么修掉，要么在讨论串里写明理由后关闭。很多情况下，agent 会在夜里把问题修掉，作者第二天回来时 PR 已经又过了一轮评审。

### 3. 能阻断合并的安全评审

他们还跑自动安全评审。只要有未关闭的发现（来自代码评审或安全评审，任一），PR 就不能合并。作者可以修掉问题，也可以用简短理由关闭讨论串（这样处理误报）。

如果后续提交解决了问题，发现会被自动关闭。同样的能力可以用开源的安全评审 GitHub Action 或 /security-review 命令搭出来。

### 4. 能阻断合并的自动检查

标准检查：lint、类型检查、全平台测试、构建。一个典型的 CLI PR 在有人看之前会跑几十项检查。PR 模板里有几个问题：这个变更怎么测的、怎么回滚。Claude 可以替你回答，但作者要为这些答案负责。

### 5. 按风险分级的人工批准

有些变更有风险，有些没有（比如改文档 vs 改自动更新器），它们需要的评审级别不同。

![图 C](https://pbs.twimg.com/media/HVf_D--bcAAPXY-?format=jpg&name=large)

FIG C

**分级由变更决定，不由作者决定。** 一个分类器根据变更内容判定风险级别；另一个分类器判定某个变更是否**即使级别不够也必须再加一次批准**。有些路径永远需要额外批准：owner 标记为敏感的路径，以及任何 CI workflow 文件。

只有在仓库「可信名单」上的作者才能享受放宽的评审要求，这个名单一般就是拥有该仓库的团队。其他所有人一律需要第二个人批准。**agent 的批准不算人工批准。** 自动评审可以放行低风险变更，但在需要人工时必须由人顶上。

变更的作者对它负责，所以如果某个 PR 是 agent 写的，**agent 的操作者始终被计为必需的评审人之一**。一次 PR 批准只对一个 commit 有效：如果有新的、不可信的 commit 进来（比如 agent push 了东西，或者有人手工解了冲突），PR 必须重新批准。

### 6. 合并队列、特性开关与分阶段放量

合并队列确保所有检查都是**带上这个变更**在 main 上跑的，避免两个各自成功的 PR 合起来把 main 弄坏。新特性通常在特性开关后面放量，Anthropic 员工先拿到。因为团队自己大量使用这个产品，经常比用户更早发现回归。

公开发布时，变更先进 latest 通道，stable 通道跟在后面。

### 7. 快速反馈与回滚

总有一些坏合并会漏过去。这是最后一道防线，专注于尽快识别它们。特性开关后面的变更可以不部署就关掉。

Claude Code 有每周轮值的 on-call，任何事故复盘都会回看**哪一层本该拦住它**。发现坏合并仍然要靠作者和 on-call，除了看回滚与事故看板之外没有别的机制。目前还没有根据这些指标自动调整批准要求的熔断机制，但正在研究，方向是让合并需要的人工干预更少。

有位团队成员指出，放慢速度、减少产出确实能提高准确率，但那主要是因为做的事情变少了。真正的优先级是**提升快速识别和修正问题的能力**。

## 怎么让评审器变得更好

评审流程是一个持续改进的循环。

**把事故当作评估集。** 团队收集了导致事故的 PR，以及它们的修复提交和回滚，让懂这块代码的工程师逐条核实每个 bug 的位置和判定是否正确。评审系统每天都会拿这个集合来评估。

![图 D](https://pbs.twimg.com/media/HVf_nM4aIAAKyCq?format=jpg&name=large)

FIG D：历史事故就是评估集

每发生一次事故，集合就多一条；评审系统的每次改动都要拿整个集合重新评估。

**为衡量噪音，观察人对评审评论的反应。** 如果不在乎报多少非 bug，把找 bug 率提上去很容易，所以这一点必须被约束。每条评审评论按 PR 上那个人的处理方式分类：修了、否了、说明是有意为之、判断为不重要。此外还会把评审系统跑在**已知干净的 PR** 上，观察它多久会报出一个「如果照做会造成有害变更」的问题。

声明的优先级是：第一，发现真 bug；第二，减少评审轮次。

**当作者是 agent 时，处理一条评论的代价更高。** 人忽略一条 nit 只要一秒，但 agent 必须处理它时，就要多一个 commit，多一轮评审。

**评审过程必须收敛。** agent 作者和 agent 评审器之间的来回可以永无止境。CLI 项目里曾有个 PR 一夜之间循环了**五十多次**，原因是 agent 作者和 agent 评审器互相来回。这次循环是人工叫停的，否则可能一直跑下去。

对评审系统反复报出的问题跑 git blame，发现**约 59% 是第一次评审时就已存在的代码**。本质上，评审系统很少发现新 bug，只是每轮多发现几个旧 bug。

而这件事变得更糟：因为每一轮都可能发现不同的 bug，团队养成了**默认跑好几轮评审**的习惯。对高风险变更多轮迭代是有用的，但不是每个 PR 都需要。于是开始跟踪「通过所需轮次」这个指标（此前只看召回率），并把重评审改成：

- **限制轮次**：三轮之后，评审系统要求作者重新评估方案
- **限制重评审范围**：初始几轮之后只评审新增 diff
- **指定 bug 类别**：让作者一次改掉一整类问题，而不是一行
- **不再重复报已见过的问题**
- 评审 agent 也会在夜间跑整个现有代码库，帮助在历史 bug 扩散前发现它们

![图 E](https://pbs.twimg.com/media/HVgAB3aaYAApPEZ?format=jpg&name=large)

FIG E：会收敛的评审

引入收敛机制后，内部 PR 平均评审轮次的下降。

## 人在环路里

让一位资深工程师停下手上的活去评审一个常见错误，成本远高于把这件事自动化。但人工评审在一些任务上仍然不可替代：

- **要不要做这件事**：决定是否构建、设定产品愿景、品味与目标。有个声称已解决代码评审瓶颈的团队，对外部进来的变更仍然做人工评审，就是为了确认「要做的是对的东西」。
- **审计危险代码**：计费、自动更新器、CI workflow。
- **架构评审**：这类选择会成为别人遵循的约定。
- **验证证据**：测试输出、跑过的命令、截图、评审意见。**如果你说不出这些检查会漏掉什么，那就别要一个赞，你需要的是真评审。**
- **承担责任**：每一个上线的变更都要有人负责，不管是谁打的字。

## 团队上下文

代码评审一直兼有「同步代码库变更」的职能。读同事变更的 diff，是人们理解改了什么、代码怎么工作的常规方式。如果大部分阅读由机器完成，那**学代码库**要靠什么？

团队没有任何正式机制。没有人脑子里装着 Claude Code 的完整心智模型，也不认为需要。谁想了解某块代码，就让 Claude 针对那个切片生成一份讲解，几分钟就出来，而且永远是最新的。

![图 F](https://pbs.twimg.com/media/HVgAZymawAAx2IG?format=jpg&name=large)

FIG F：如果大部分阅读由机器完成，人怎么学代码？

有些人还会多做一步：让 Claude 生成一个可视化这个区域、并按自己喜欢的风格讲解的小 artifact。

这比逐行读琐碎的 diff 更能聚焦人的注意力。读一行文案改动学到的东西极少，而为你要改的模块生成一份讲解，学到的很多。

另外，团队默认开放：工作在公开的 Slack 频道里，能看见别人正在建什么。

## 「你合并的，你负责」

如果你的中小变更合并后出了问题，一般预期是**你自己修**。这不会失控，有几个原因：

- 小变更容易评审、调试、回滚
- 一切都能回退：特性开关、revert、分阶段放量可以在几分钟内逆转大多数错误
- **影响半径决定门槛**：越贵的代码越要更多验证
- 遥测和内部使用会很快暴露回归
- **这不是追责游戏**：修问题的人负责，是因为他上下文最多；事故复盘看的是系统
- 团队很多人通过公开频道共担责任，任何人都能看见别人在建什么、插进对话、或者让 Claude 找缺口。反馈也来自非代码 owner。这种开放是质量能在没有逐行闸门的情况下保持高水平的重要原因

## 改变方向

有 agent 之后，开新活的成本很低，但有时候不该开。典型情形是：频道里有人指出这个提议的变更方向不对（援引以前的决定，或建议更好的路径），于是作者要么关掉 PR，要么改实现。

因为代码本来就好写，关掉 PR 不会有「损失感」。关键是**在讨论串早期就转向**，而不是等到最后在一个已定稿的 PR 上留一条阻断性评论。

## 怎么落地

这套做法的大部分组件，现在就能用。

**建 PR 之前**

- 给 agent 一份它能跑的检查清单，写在简短的 CLAUDE.md 里
- 用 hooks 让 agent 调用格式化和 lint 工具
- 本地跑 /code-review 和 /security-review，或者让一个全新上下文的子 agent 评审变更
- 建一个 REVIEW.md，用来跟踪反复出现的评审问题

**每个 PR 上**

- 强制 CI
- PR 模板里加上「怎么测的」「风险」「怎么回滚」
- 先在一个仓库上接入 AI 评审器（Code Review for Claude Code，或 Claude Code GitHub Action），花几周迭代 REVIEW.md，再推广到更多仓库
- 加自动安全评审
- 要求合并前所有评审讨论串都已解决
- 按风险施加评审强度：例行变更快速过一遍，高风险区域（bug 代价高）彻底评审
- 限制评审轮次；几轮之后只评审新增 diff

**批准**

- 定义风险级别，按变更而非作者定级。**从严开始，看到证据再逐步放宽**
- 放宽的批准路径只留给可信作者
- 机器人批准不能顶替必需的人工批准；有新 commit 推上来时撤销已有批准
- 把认证、计费、CI、发布 workflow 和安装器相关的代码与策略指定人工审批人，用 CODEOWNERS 和分支保护实现

**合并与合并后**

- 搭合并队列
- 试验特性开关
- 先发给内部用户
- 分阶段放量
- 做一键回滚机制
- 通过记录事故与回滚，建起一套评估集
- 每次改动评审器的 prompt、工具或模型，都重新给它打分
- 跟踪人力投入，用回滚率和事故率作为护栏

## 这件事要往哪走

Code Review 发布时的定位是：最终批准决定仍然由人做，产品只负责发发现。但在团队自己的仓库里走得更远：**owner 们在决定哪些低风险变更可以在自动检查通过后自动合并**。这条边界还会继续移动。

所以每当评审器漏掉什么，就问自己：**模型上下文里缺了什么**，然后把它变成一份 CLAUDE.md、一个 skill 或一项新检查。目标一直没变：减少每个变更需要的人力，同时让回滚率不高于现在。
