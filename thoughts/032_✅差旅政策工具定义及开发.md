# ✅差旅政策工具定义及开发

> 来源: https://thoughts.aliyun.com/workspaces/6963289eb0fc2e001bb052eb/docs/6a6a0bc274e4030001f38f47

差旅政策不是一份静态文档，而是**"用户职级 × 目的城市等级"** 两个维度共同决定的一张查找表：
* 同一个人去北京 vs 去昆明，酒店上限不一样。
* 同一个城市，P6 vs P8 的舱位/上限也完全不同。


所以 Agent 不能只靠 RAG "语义近似"就回答"我去 X 城市的住宿标准是多少"——**必须走一个能拿到用户身份、能查数据库的确定性工具** ，这就是 PolicyTools 存在的理由。


> InfoAgent 系统提示词里显式声明了"双通道"：
> 通道 1（RAG）：处理"差旅制度对超标是怎么规定的？"这类**语义/规则性** 问题，召回内容是参考。
> 通道 2（Tool）：处理"我去上海的住宿标准？""我这单超标吗？"这类**精确/可校验** 问题。（ _https://thoughts.aliyun.com/workspaces/6963289eb0fc2e001bb052eb/docs/6a6af563d31fed0001d7646b_ ）


### 为什么需要这个工具


先把"如果没有 PolicyTools 会怎样"想清楚，价值就自然浮现。


**方案 A：全都塞进 system prompt** ——把 12 条政策规则、几十个城市列表全部拼进提示词。缺点很直接：token 恒定膨胀；换职级/加城市要改代码；LLM 还有可能算错"P7 去昆明属于哪一档"。


**方案 B：全部走 RAG** ——把政策文档灌进向量库让模型语义检索。缺点是 RAG 精度不足以给出"具体数字"，且**用户身份（"我"是谁、职级几档）无法向量化** ，模型很容易把别人的政策当成"你的"标准回复出去，合规风险高。


**方案 C（当前实现）：定义一对确定性工具，把"查询 + 校验"下沉到业务代码里** ——
* 用户身份从 AgentSessionContext（框架注入，不进对话上下文）取；
* 城市等级、职级映射走配置和数据库；
* LLM 只负责"识别这是政策类问题 → 决定调 query 还是 check → 组织自然语言输出"。


这样得到的三个直接好处：
1. **数据永远最新** ：DB 改一条规则立即生效，不用改代码/重训。
2. **对模型透明** ：LLM 看到的接口只有 city 和 order_summary，不用管"用户是谁"，减少幻觉。
3. **合规可审计** ：所有政策计算发生在 Java 侧，日志里能追到 userId + city + tier + policy，出问题能复盘。




### 工具类定义：PolicyTools

```
@Componentpublic class PolicyTools {
private static final Logger logger = LoggerFactory.getLogger(PolicyTools.class);
@Autowired private TravelPolicyService travelPolicyService; // 政策计算引擎
@Tool(name = "query_travel_policy", description = "查询指定用户和目的城市的差旅政策标准（餐标、酒店标准、交通补贴等）") public String queryTravelPolicy( AgentSessionContext sessionCtx, // ← 框架注入的隐式参数，无 @ToolParam @ToolParam(name = "city", description = "目的城市") String city) {
// 1) 优先命中会话内缓存：同一次对话里反复问"我去 X 的标准"直接返回，避免重复查库 String travelPolicy = sessionCtx.getTravelPolicy(city); if (travelPolicy != null) { logger.info("[TOOL][query_travel_policy] hit cache, city={}", city); return travelPolicy; } else { logger.info("[TOOL][query_travel_policy] miss cache"); String userId = sessionCtx.getUserId(); logger.info("[TOOL][query_travel_policy] userId={}, city={}", userId, city); // 2) 未命中缓存 → 走 service 完整链路（职级 + 城市等级 + DB 规则） TravelPolicy policy = travelPolicyService.getPolicy(userId, city); // 3) 统一序列化成 JSON 返回给 LLM——工具返回值必须是可读文本 String result = JSON.toJSONString(policy); logger.info("[TOOL][query_travel_policy] result={}", result); // 4) 回填缓存 sessionCtx.setTravelPolicy(city, result); return result; } }
@Tool(name = "check_travel_policy", description = "校验行程或订单是否符合差旅政策，返回合规结果和超标说明") public String checkTravelPolicy( AgentSessionContext sessionCtx, @ToolParam(name = "city", description = "目的城市") String city, @ToolParam(name = "order_summary", description = "订单摘要JSON，例如 {\"type\":\"HOTEL\",\"amount\":450}") String orderSummary) {
String userId = sessionCtx.getUserId(); logger.info("[TOOL][check_travel_policy] userId={}, city={}, orderSummary={}", userId, city, orderSummary); // 注意：这里没有走缓存 —— 见 2.2 末尾的说明 TravelPolicy policy = travelPolicyService.getPolicy(userId, city); PolicyCheckResult result = travelPolicyService.checkCompliance(orderSummary, policy); String json = JSON.toJSONString(result); logger.info("[TOOL][check_travel_policy] done"); return json; }}
```

### TravelPolicyService
工具本身只是薄壳，真正干活的是 service。

```
@Servicepublic class TravelPolicyService {
@Autowired private UserProfileRepository userProfileRepository; // 查用户职级 @Autowired private TravelPolicyProperties travelPolicyProperties; // 读 city-tier.yml @Autowired private TravelPolicyRuleRepository travelPolicyRuleRepository; // 查政策规则表
public TravelPolicy getPolicy(String userId, String destinationCity) { String level = resolveUserLevel(userId); // ① 拿职级 String cityTier = resolveCityTier(destinationCity); // ② 拿城市等级 return buildPolicy(level, cityTier); // ③ 查规则表拼装 }
// ① 用户职级：不存在/未配置就直接抛，绝不给默认值——避免"P0 走 P8 政策"这种静默事故 private String resolveUserLevel(String userId) { if (userId == null || userId.isBlank()) { throw new IllegalArgumentException("user_id 不能为空"); } UserProfile profile = userProfileRepository.findByUserId(userId) .orElseThrow(() -> new IllegalArgumentException( "用户档案不存在，无法获取差旅政策：userId=" + userId)); String level = profile.getLevel(); if (level == null || level.isBlank()) { throw new IllegalStateException( "用户未配置职级，无法获取差旅政策：userId=" + userId); } return level; }
// ② 城市等级：从 city-tier.yml 读取，未列出的城市默认"其他" private String resolveCityTier(String destinationCity) { if (destinationCity == null || destinationCity.isBlank()) return "其他"; String city = destinationCity.trim(); if (travelPolicyProperties.getTier1Cities().contains(city)) return "一线"; if (travelPolicyProperties.getNewTier1Cities().contains(city)) return "新一线"; if (travelPolicyProperties.getTier2Cities().contains(city)) return "二线"; return "其他"; }
// ③ 组装政策：这里有个隐蔽的收敛动作——DB 规则表只区分 3 档（一线/新一线/其他）， // 所以本地识别到的"二线"会在这里被折叠成"其他" private TravelPolicy buildPolicy(String level, String cityTier) { int levelNum = parseLevelNum(level); String policyTier = ("一线".equals(cityTier) || "新一线".equals(cityTier)) ? cityTier : "其他";
TravelPolicyRule rule = travelPolicyRuleRepository .findByLevelAndCityTier(levelNum, policyTier) .orElseThrow(() -> new IllegalStateException( String.format("未找到匹配的差旅政策规则：level=%s(num=%d), cityTier=%s", level, levelNum, policyTier)));
// 从 DB 实体拷贝到对外 DTO；不直接返回 TravelPolicyRule 是为了解耦持久化字段 TravelPolicy policy = new TravelPolicy(); policy.setUserLevel(level); policy.setCityTier(cityTier); // 注意这里存的是识别到的原始 tier（可能是"二线"） policy.setFlightClass(rule.getFlightClass()); policy.setTrainSeatClass(rule.getTrainSeatClass()); policy.setHotelLimit(rule.getHotelLimit()); policy.setHotelStarLimit(rule.getHotelStarLimit()); policy.setDailyMealLimit(rule.getDailyMealLimit()); policy.setDailyTransportLimit(rule.getDailyTransportLimit()); policy.setApprovalThreshold(rule.getApprovalThreshold()); policy.setAdvanceBookingDays(rule.getAdvanceBookingDays()); return policy; }
private static int parseLevelNum(String level) { String digits = level.replaceAll("[^0-9]", ""); // "P7" → "7" if (digits.isEmpty()) { throw new IllegalArgumentException("职级格式无效，无法解析数字：" + level); } return Integer.parseInt(digits); }
// 合规校验：按订单 type 分派 —— 目前 3 种业务 public PolicyCheckResult checkCompliance(String orderSummaryJson, TravelPolicy policy) { PolicyCheckResult result = PolicyCheckResult.compliant(); JSONObject order = JSON.parseObject(orderSummaryJson); if (order == null) return result;
String type = order.getString("type"); double amount = order.getDoubleValue("amount");
if ("FLIGHT".equalsIgnoreCase(type)) { String flightClass = order.getString("flightClass"); // 用 contains 是刻意的：DB 里 P7 存的是 "经济舱/商务舱"，可以匹配两种 if (flightClass != null && !policy.getFlightClass().contains(flightClass)) { result.setCompliant(false); result.getViolations().add("机票舱位超出政策标准：允许 " + policy.getFlightClass()); } } else if ("HOTEL".equalsIgnoreCase(type)) { if (amount > policy.getHotelLimit()) { result.setCompliant(false); result.getViolations().add("酒店金额超出政策上限：" + policy.getHotelLimit()); result.getSuggestions().add("建议选择 " + policy.getHotelLimit() + " 元以下酒店"); } } else if ("TRAIN".equalsIgnoreCase(type)) { String seatClass = order.getString("seatClass"); if (seatClass != null && !seatClass.equalsIgnoreCase(policy.getTrainSeatClass())) { result.setCompliant(false); result.getViolations().add("火车座位超出政策标准：允许 " + policy.getTrainSeatClass()); } } return result; }}
```


三个可对比的装配决策：
* **PolicyTools****没有挂在****TOOL_CIRCUIT_BREAKER_GROUP****里** （destinationLiveTools 挂了），意味着它不参与"外部实时数据熔断降级"——因为政策查询是本地数据库调用，重试/降级由业务侧异常来处理即可，不需要 Hook 参与。
* **政策工具和政策 RAG 知识库并存** ：这就是"双通道"能存在的技术基础，工具和 knowledge 是 InfoAgent 同时具备的两个能力。
* **ragMode(RAGMode.AGENTIC)** ：让 LLM 自己决定"要不要检索、检索什么"，与 GENERIC 模式（每轮自动注入）相对；这样在纯政策工具就能回答的场景，不会浪费一次 embedding 查询。


InfoAgent 从 BaseSubAgent 继承来的 @Autowired protected PolicyTools policyTools;（BaseSubAgent.java 第 60-61 行）就是 Spring 把单例 bean 传进来的入口。


### 让 LLM 知道什么时候用工具
工具挂上去只完成了"能力"这一半，另一半是"教会 LLM 什么时候用"。src/main/resources/prompts/info-agent-system.md 里有一段专门讲双通道：

```
## 政策查询双通道说明
差旅政策类查询**必须**根据场景选择正确的通道，**严禁混用、错用**：
### 通道 1：政策知识库（RAG 通道）- **适用场景**：用户询问**通用差旅规则**的语义类问题 （如"差旅管理制度对超标住宿是怎么规定的？""差旅报销要走什么流程？"）- **重要约束**： - 召回内容是**参考**，不要复述为权威标准 - 召回为空时直接告知用户"暂未收录该政策"，**不要编造**
### 通道 2：政策工具 `PolicyTools`（工具调用通道）- **适用场景**： - 用户问"**我**去 X 城市**的**住宿标准"——需要与用户身份绑定的精确数据， 走 `query_travel_policy` - 用户问"我订的酒店超标吗？""帮我检查这个行程"——走 `check_travel_policy` 做实时合规校验
### 通道决策速查| 用户问题特征 | 优先通道 ||---------------|----------------|| "差旅制度里关于 X 是怎么规定的？" | 政策知识库 || "我**去 X 城市**的住宿标准？" / "我**的**差旅标准？" | `PolicyTools.query_travel_policy` || "我订的酒店超标吗？" / "帮我检查这个行程"| `PolicyTools.check_travel_policy` |
### 冲突解决如果用户问题同时满足多个通道的适用场景，请优先选择通道 2 ...如果两个通道都未返回结果，则返回"暂未收录该政策"。请用户联系 HR 团队。
Plain Text

```

三个我认为写得好的地方：
1. **锚点词很具体** ："我""我的""我去"这些第一人称词是明确的身份信号，LLM 拿来做通道选择非常准。
2. **给出冲突仲裁规则** ：不留模糊——两个通道都能答时优先工具。这条如果不写，LLM 遇到"我去上海的酒店有什么规定？"这种双意图问题会左右摇摆。
3. **兜底话术显式规定** ：都拿不到时说"暂未收录该政策"，避免编造。


同一提示词还有一条全局约束值得注意（第 78 行）：
> **禁止向用户暴露内部实现细节** ：面向用户的回复中不得出现工具函数名（如 query_travel_policy 等 snake_case 名称）……
也就是说，@Tool.name 是给 LLM 用来路由的、写代码用来注册的，**不是给终端用户看的字符串** ——回复里必须换成"差旅政策查询"这样的自然语描述。
