# ✅上下文工程——记忆自动压缩

> 来源: https://thoughts.aliyun.com/workspaces/6963289eb0fc2e001bb052eb/docs/6a5a09b2c71a8900017abe69

为了精简上下文，gogo-agent 引入了 AgentScope 框架的 AutoContextMemory——一个**在 LLM 推理前自动检测 token 膨胀、按六级策略递进压缩、且保留原文可召回** 的记忆引擎。应用侧无需手动管理何时压缩、压哪些，只需配好参数，剩下的交给框架。下面看它到底怎么工作。


原理在这里：

##### ✅AgentScope Java特性：智能上下文压缩
ASJ中在多轮对话、持久化对话以及长期记忆之外，还提供了个内置的上下文自动管理的机制，能实现自动的上下文压缩和卸载。用来解决长会话或者多轮 ReAct 工具调用中出现的token 爆炸、上下文窗口溢出问题。 这部分能力靠AutoContex
LLMentor


gogo-agent 通过一个工厂类统一配置压缩参数，所有子智能体共享同一套调优值AgentMemoryFactory.java：

```
public final class AgentMemoryFactory {
/** 单条消息超过该字符数即卸载。 */ private static final long LARGE_PAYLOAD_THRESHOLD = 4 * 1024L;
/** 卸载后保留的预览长度（字符），足够 LLM 判断是否需要重新拉取完整内容。 */ private static final int OFFLOAD_SINGLE_PREVIEW = 300;
/** 上下文窗口 token 上限。 */ private static final long MAX_TOKEN = 128 * 1024L;
/** 达到 MAX_TOKEN * TOKEN_RATIO 即触发压缩。 */ private static final double TOKEN_RATIO = 0.75;
/** 消息条数阈值：超过即触发压缩。 */ private static final int MSG_THRESHOLD = 60;
/** 保留最近多少条消息不被压缩/卸载，保证近期上下文完整。 */ private static final int LAST_KEEP = 20;
public static AutoContextConfig tunedConfig() { return AutoContextConfig.builder() .largePayloadThreshold(LARGE_PAYLOAD_THRESHOLD) .offloadSinglePreview(OFFLOAD_SINGLE_PREVIEW) .maxToken(MAX_TOKEN) .tokenRatio(TOKEN_RATIO) .msgThreshold(MSG_THRESHOLD) .lastKeep(LAST_KEEP) .build(); }
public static AutoContextMemory create(Model model) { return new AutoContextMemory(tunedConfig(), model); }}
Plain Text

```

MSG_THRESHOLD=60 和 TOKEN_RATIO=0.75（即 96K token）是两道并行的触发线——任一条达到即开始压缩；
LAST_KEEP=20 保护最近 20 条消息不被动，保证 LLM 对"当前正在做什么"有完整记忆；
LARGE_PAYLOAD_THRESHOLD=4KB 意味着单条超 4096 字符的大消息（如完整的工具返回 JSON）会被优先卸载为 300 字符的摘要预览。


使用方式如下：



```

```



首先，带`_hash` 后缀的不是业务数据，是存储层的优化元数据。它的作用是: `_hash` 存的"上次写库时，那份列表长什么样"的指纹。下次保存前拿它比一比，判断能不能只追加尾巴、还是必须整段推平重写。


另外几个key的含义如下
| state_key | 含义 |
| --- | --- |
| `autoContextMemory_workingMessages` | **工作集** ：压缩/卸载后的消息，是真正喂给 LLM 的那份 |
| `autoContextMemory_originalMessages` | **原始集** ：完整未压缩的历史，append-only，用于审计/还原 |
| `autoContextMemory_offloadContext` | `Map<uuid, List<Msg>>`，被"卸载"消息的原文 |
| `autoContextMemory_compressionEvents` | 每次压缩操作的审计记录 |
**
**
**offloadContext 是关键** ：压缩时大消息会被替换成提示语"用 context_offload_tool 以 uuid xxx 回捞完整内容"，原文存在这个 map 里。不持久化它，会话恢复后那些 uuid 就指向空数据，agent 再也捞不回来。


**compressionEvents** 每条记录 CompressionEvent：`eventType`（6 种压缩策略之一，如 `TOOL_INVOCATION_COMPRESS`、`LARGE_MESSAGE_OFFLOAD`、`PREVIOUS_ROUND_CONVERSATION_SUMMARY`）、`timestamp`、`compressedMessageCount`、压缩区间前后的 `previousMessageId`/`nextMessageId`/`compressedMessageId`，以及 `metadata` 里的 `tokenBefore`/`tokenAfter`/`inputToken`/`outputToken`（压缩本身消耗的 token）。排查"上下文为什么丢了"时主要看这张表。
