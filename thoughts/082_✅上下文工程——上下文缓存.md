# ✅上下文工程——上下文缓存

> 来源: https://thoughts.aliyun.com/workspaces/6963289eb0fc2e001bb052eb/docs/6a5c868f3fb9180001cba54b

关于利用百炼的隐式缓存的方案前面讲过了，这里讲另外一种——显示缓存



##### ✅上下文工程——优化系统提示词利用KV缓存
我们在前面讲Manus的上下文工程实践的时候，讲过KV Cache 大模型是自回归的：生成第 N 个 token 时，要「看到」前面所有 token。Transformer 的注意力机制里，每个历史 token 都会被算成一对 Key /
LLMentor


隐式缓存是服务端自动的，但框架可以显式给某些消息打「cache_control」标记，提示服务端「这几段值得缓存、按缓存规则处理」。在 AgentScope 里就是 GenerateOptions.cacheControl(true)——开启后框架会自动在每次请求时给**系统消息** 和**最后一条消息** 加上 cache_control 标记。可以把它理解为「主动告诉服务端：请对我的固定前缀和最新增量做缓存优化」。



![](images/ai/thoughts-082-img_001.png)


（ _需要注意的是，显示缓存和隐式缓存不会同时生效，如果开了显示缓存了之后，隐式缓存就没必要了，但是这两个方案我们都给大家讲一下）_


项目中，所有 Agent 构建 GenerateOptions 时都开了缓存。



```
// BaseSubAgent.java:174-188public GenerateOptions getEnableThinkingGenerateOptions(Integer thinkingBudget) { return GenerateOptions.builder() // 开启缓存，框架会自动在每次请求时对 system messages 和 最后一条消息 加上 cache_control（…bailian…） .cacheControl(true) // 深度思考模型有时会生成冗长的推理过程…通过 thinking_budget 可设推理过程的最大 Token 数 .thinkingBudget(thinkingBudget) .build();}
public GenerateOptions getGenerateOptions() { return GenerateOptions.builder() // 开启缓存，框架会自动在每次请求时对 system messages 和 最后一条消息 加上 cache_control（…bailian…） .cacheControl(true) .build();}
Plain Text

```

`cacheControl(true)` 的语义：框架自动给系统消息和最后一条消息打缓存标记。


在做这个方案的时候，我踩过一个很隐蔽的坑：行程规划 Agent 会在「规划阶段（开思考）」和「执行阶段（关思考）」之间切换，切换靠**重建****GenerateOptions** 。而一旦重建，如果新的 options 忘了带 cacheControl(true)，缓存标记就丢了、前面的稳前缀白稳了。后来在PlanAwareThinkingHook.java 在两处重建里都显式重申：

```
// PlanAwareThinkingHook.java:59-75private void enableThinking(PreSummaryEvent event) { // 最终总结阶段：开思考 event.setGenerateOptions(GenerateOptions.builder() .cacheControl(true) .thinkingBudget(thinkingBudget) .build());}
private void disableThinking(PreReasoningEvent event) { // 执行阶段：关思考，快速跑 event.setGenerateOptions(GenerateOptions.builder() // 保住隐式缓存 .cacheControl(true) // 关闭思考 .additionalBodyParam("enable_thinking", false) .build());}
Plain Text

```
