# ✅行程方案最终审核工具定义及开发

> 来源: https://thoughts.aliyun.com/workspaces/6963289eb0fc2e001bb052eb/docs/6a6a0d41c71a8900018a2c93

gogo-agent 在「把方案交给用户」之前，专门插了一道**最终审核** 。它要解决三个工程问题：


第一，**审核必须是客观的、可复现的，不能又交给大模型"感觉一下"** 。如果让规划的大模型自己审自己，等于让考生给自己判卷——它会倾向于说"我这方案挺好"。所以审核的五个维度（完整性、时间、出发目的地、预算、路径）全部用**确定性的 Java 规则引擎** 算，同样的输入必然得到同样的 pass/warning/fail，不依赖大模型的临场发挥。


第二，**审核要能驱动一个修复闭环，而不只是打个分就完事** 。审核结果不是终点，而是要反过来告诉规划环节"哪个方案该淘汰、该换成什么"，让规划重跑一遍，直到方案干净为止。这就要求审核的输出不能是一句"还行"，而必须是结构化的、带 best_proposal_id 和可执行 suggestions 的报告。


第三，**审核和规划要解耦，不能靠传一坨大 JSON 互相喂** 。一套行程方案的 JSON 很大，多套方案叠起来更大，如果通过工具参数在大模型的上下文里传来传去，既烧 token 又极易触发 JSON 解析失败。gogo-agent 的做法是让规划结果落 Redis，审核工具自己按用户去读，参数里一个字节的方案数据都不传。


理解了这三点，就理解了这套审核体系的全部设计动机：**客观规则引擎 + 结构化报告 + Redis 解耦** 。


审核能力由三层构成：真正干活的「审核」既不是一个纯工具、也不是一个纯智能体，而是**工具 + 子智能体的组合** ：



```
规划主智能体 ItineraryPlanAgent │ 以「子智能体作为工具」方式调用（toolName = itinerary_review_agent） ▼ 审核子智能体 ItineraryReviewAgent（stableModel，负责编排 + 生成 Markdown 报告） │ 调用 @Tool ▼ 审核规则引擎 ItineraryReviewTools.review_planner_result（纯 Java，五维确定性校验） │ 从 Redis 读 ▼ 规划结果 ItineraryPlanStore（planner:result:{userId}，由 plan_itinerary 写入）

```

### 五维校验


最开始设计这个校验的时候，其实我设计了6维，在当前的5维之外，还增加了一个偏好匹配度。但是实际运行下来，发现经常无法满足偏好，因为我们的行程有时候就无法完全满足用户偏好的。


比如用户想做头等舱，但是他的出差预算是不够的。比如用户想要早上出发，但是现在已经是中午了。


所以，这个维度我们就在审核中去掉了，但是不代表我们的方案设计不考虑偏好了，在设计的时候我们还是把偏好的权重设置为比较高的 0.5的，详见前面设计部分。


单方案审核 reviewSingle 就是顺序跑五个 check* 方法，每个往 checks 里塞一个 CheckResult，往 issues/suggestions 里追加文字。注意全项目**没有** ReviewResult/ReviewReport 这种实体类，唯一的强类型是一个私有 record：

```

**维度② 时间安排合理性（****checkTimingValidity****）**


三类时间校验，用常量兜底：到达后到首个活动的缓冲（MIN_ARRIVAL_BUFFER_MINUTES = 60）、最后活动到返程出发的缓冲（MIN_RETURN_BUFFER_MINUTES = 60）、中转时间（国内 60 / 国际 90 分钟）。这里有个关键的 warning 与 fail 分级——**"缓冲不足"只是 warning，但"返程出发早于最后活动"是硬冲突判 fail** ：

```

**维度④ 预算合规性（****checkBudgetCompliance****）**


这是唯一依赖外部输入（policy）的维度。**没传 policy 时不是跳过就算了，而是判 warning 并主动建议去查政策** ，把"缺数据"这件事显式暴露出来：

```

Plain Text

```

有政策时，逐晚比对 hotel_limit_per_night，累加交通+住宿算总价再比 total_budget_limit，超标项进 issues 并判 warning。


**维度⑤ 路径规划合理性（****checkRouteRationality****）**


单日/短途（days < 2）直接 pass；多日则抽出住宿城市序列，检测 A→B→A 折返（checkCityBacktrack），并对每晚酒店距主要活动场所超过 MAX_HOTEL_DISTANCE_KM = 15.0 公里告警。


**汇总规则**


清晰而保守——computeOverallStatus：任一维 fail 则整体 fail，否则任一 warning 则 warning，全 pass 才 pass。选最优用 computeEffectiveScore：拿规划阶段的客观分 planner_scores.overall 乘以状态权重（pass=1.0 / warning=0.7 / fail=0.0），意味着**一个失败的方案 effectiveScore 直接归零，永远不会被选为 best** 。


### ItineraryReviewAgent


规则引擎只会吐 JSON，把 JSON 翻译成 Plan Agent 能消费的 Markdown 报告、并决定调用顺序的，是这个子智能体。它 extends BaseSubAgent，build() 很短：



```
@Bean(name = "itineraryReviewAgent")@Scope("prototype")public ReActAgent build() { Toolkit toolkit = new Toolkit(); toolkit.registration().tool(policyTools).apply(); // query_travel_policy / check_travel_policy toolkit.registration().tool(itineraryReviewTools).apply(); // review_planner_result
return ReActAgent.builder() .name("ItineraryReviewAgent") .description("行程方案审核专家，对规划好的行程进行五维结构化审核（完整性/时间/出发目的地/预算/路径），输出审核报告和具体修改建议") .model(stableModel) // 关键：审核用 stableModel，不用带思考的强模型 .toolkit(toolkit) .toolExecutionContext(createToolCtx()) .memory(AgentMemoryFactory.create(stableModel)) .longTermMemory(createLongTermMemory(memoryFactory)) .longTermMemoryMode(LongTermMemoryMode.AGENT_CONTROL) .hooks(List.of(new AutoContextHook(), executionLoggerHook, progressNotifierHook)) .sysPrompt(PromptLoader.load("itinerary-review-agent-system.md")) .toolExecutionConfig(getToolConfig()) .maxIters(MAX_ITERATIONS) // 8 .build();}
Plain Text

```



系统提示词（itinerary-review-agent-system.md）把执行流程钉死成固定两步：先 query_travel_policy(city=目的地) 拿政策，再 review_planner_result(policy=...) 一次性批量审核全部方案。


并且明确要求**即使方案"看起来明显合理"，这两个工具调用也一个都不能省** ——杜绝大模型偷懒直接下结论。


输出必须是固定结构的 Markdown（审核概况 + 多方案对比表 + 各方案独立详情 + 结论），结论段落还编码了修复策略：全通过→可推进；有 warning→建议调整后重跑再审；有 fail→必须剔除违规候选、重跑修复、最多 2 轮。
