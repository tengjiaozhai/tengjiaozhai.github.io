# ✅差旅政策知识库定义及开发

> 来源: https://thoughts.aliyun.com/workspaces/6963289eb0fc2e001bb052eb/docs/6a6af563d31fed0001d7646b

假设我们**只有** PolicyTools（前一篇讲过的工具），会出什么问题？
* 用户问："差旅管理制度对超标住宿是怎么规定的？"——这是语义问题，答案在几百字的段落里，工具返回的 JSON 数字根本回答不了。
* 用户问："差旅报销要走什么流程？"——完全跟"我是谁 / 去哪座城"无关，走工具查库没意义。
* 用户问："出差期间发生医疗紧急情况怎么处理？"——这是**行为准则** ，不在政策表格里。




这类问题的共性是：**语义 + 长文本 + 与用户身份无关** 。这时把政策 Word 文档灌进 RAG，用 embedding 做相似度检索、把最相关的几段丢给 LLM 组织语言，比任何工具都自然。


而反过来，"我 P7 去深圳的住宿标准是多少？"——RAG 的回答只能是"根据政策文档，一般在 X 元左右"，而没法直接给出精确的 500 元/晚——**这时才是工具通道的活儿** 。


一句话概括：**知识库补齐了 LLM 对"公司政策语料"的缺失，而工具补齐了 LLM 对"实时业务数据"的缺失** 。


RAG接入详见： _https://thoughts.aliyun.com/workspaces/6963289eb0fc2e001bb052eb/docs/6a5a07f53fb9180001cb12f6_


使用RAG进行检索的知识，我们直接放到了代码中：

```
src/main/resources/dataset/├── business_travel_policy.docx 21,064 B ← 差旅政策└── business_travel_guidelines.docx 18,353 B ← 差旅注意事项 / 行为准则
Plain Text

```



ataset/ 直接放在 classpath 下、进版本管理。这样做的三个隐含好处：
1. 语料修改和代码提交挂在同一次 PR 里，review 时能一眼看到"改了政策 X"。
2. 部署包自带语料，没有额外的资源同步流程。
3. 单测/CI 环境天然可用，不依赖任何外部索引服务。


代价也很直接：**语料一改就必须发版** ——不适合"政策频繁变动、非技术同学也要能改"的场景。


知识库的初始化流程如下：

```
Spring 启动 ↓容器扫到 @Configuration RagKnowledgeConfig ↓调用 corporateTravelPolicyKnowledge(Resource) ↓ ├─ new DashScopeTextEmbedding(...) // 只是拿到客户端句柄 ├─ new SimpleKnowledge(InMemoryStore, embedding) // 空的内存向量库 ├─ reader.read(policyFile.toPath()).block()// ← 解析docx→List<Doc> └─ knowledge.addDocuments(docs).block() // ← 对每个chunk做embedding ↓返回 Knowledge，作为 Spring bean 缓存 ↓运行期：LLM 触发 RAG 时，调 embedding 把 query 也转向量，去 InMemoryStore 做 cosine 相似度 top-k
Plain Text

```
