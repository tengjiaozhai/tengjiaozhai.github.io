07OCR / VLM 引擎选型史：六次切换，两次被推翻

这条线与并发无关，但同样能复用 —— 它记录的是怎么证伪一个引擎，而不只是最后选了谁。真正稳定的只有 OcrProvider 这一层接口，引擎在它下面换了六次。

灰条带 ✕ 的是被删掉的实现，绿条是当前唯一路径，蓝条是适配器、没接默认路径。09-02 一天落了四个决策 —— 这条线是压缩式推进的，不是匀速演化。

起点~ 09-01
Paddle 云端原始双轨
正文与材料表都走云 PaddleOCR。两个硬伤：材料表跨页合并时把页 25 的表并进页 24、中段 NO.41-63 三列错乱成行号；印章压在表格上时 seal 检测框只出现在 layout_det_res，被表格块吸收丢掉 → SEAL_BOX_NOT_FOUND，盖章检查形同虚设。
EV-00909-02
MinerU 云 vlm材料表专用通道
只给材料宣告表扫描页开 MinerU，其他扫描页维持 Paddle。跨页合并成 70 行 × 21 列单表，68 行全量提取（Paddle 只有 53–54 行且中段错乱）。关键设计：失败 fail-open 回退 Paddle，不阻断检测。
EV-01009-02
registry 抽象换引擎 = 改 .env
把「换引擎」从代码动作变成配置动作。修掉一个真 bug：进程级 LRU 缓存 key 不含引擎/通道维度，Paddle 全文（promptLabel=ocr）与材料表（table）结果会互串 → 缓存上移为 CachedOcrProvider(inner, engine_id)，key 变成 (engine_id, PDF 指纹, 页集)。
EV-01109-02
MinerU 内网自部署172.22.22.67:8000
走内网 v3.1.6，数据不出内网、无鉴权。踩到的坑：服务端默认 backend=hybrid-auto-engine 核心初始化失败，必须显式 pipeline；content_list 的 bbox 是 0-1000 归一化坐标（换算回像素误差 <2%）。
EV-01209-02
paddle-local+ seal 检测层捞取
接内网 9001。真正的价值不是换引擎，是从 layout_det_res.boxes 里把 score ≥ 0.5 的 seal 框捞回，补成 OcrBlock(label="seal")。M206 全 8 页实测四枚真章全部找回，p3 的灰色「订」图标由视觉判非红滤掉。
EV-01309-04
Paddle 全部删除唯一引擎
MinerU 作为唯一真实 OCR 引擎，删掉 Paddle 云端与 paddle-local 两条运行时路径。先证伪再删：P104 122 页全覆盖 992 块全带 bbox、N706 材料表 68/68、M206 8 页 18s。回滚方式是上一版制品或 Git tag，不接受把 OCR_PROVIDER=paddle-local 当回滚开关（实现已删）。
EV-02709-15
pipeline → vlm-engine后端切换
真实件 M721 第 19 页暴露 pipeline 两个盲区：页面顶部标题条带整块漏检（y<78pt 一个块都没有，discarded_blocks=0，不是我们丢的）；表头被拆成与数据行错位的列位 → 整张材料表不被识别，ROHS 与材料声明静默跳过，报告上看不到失败。
同页换 vlm-engine 即恢复。小语料 13 份：正文总字数 7710 → 12296，缺章节 109 → 107。
EV-03009-16
MinerU 云端适配器非默认路径
mineru.net 标准 API 作溢出通道。实测结论是不能无缝替换：解析层可整体复用（抽出 facts_from_content_list 共用），传输层三段必须新写（Bearer 鉴权 / 预签名上传 / zip 结果）。
代价明确：云端不返回 version，3.4.5 契约漂移校验失效，只剩「zip 里必须是 content_list v1」这一条替代约束；且没有 effort，EV-027 的质量结论未复测。
被推翻的两次判断：EV-009 的「MinerU 只做材料表通道」被 EV-013 推翻（扩成唯一引擎）；EV-012 的 paddle-local 被 EV-013 直接删除。
推翻不等于否定 —— 每一步的实测数据（68/68、992 块、四枚真章）都变成了下一次的判断依据。
真正沉淀下来的不是引擎，是判据：① 引擎选型靠消融，不靠文档；② 换引擎必须是配置动作，否则接第二家要改代码；③ 缓存 key 必须含引擎身份，否则同 key 互串；④ 删掉旧实现后，回滚只能靠制品，不能靠开关。
一条反直觉的教训：EV-027 那个「页面顶部标题条带漏检」，最危险的地方不是漏检本身，而是 章节完整性因为目录列全了仍然 PASS，导致整块材料宣告检查静默跳过，报告上看不到任何失败。取证失败没有被伪装成 PASS，而是被伪装成了「这条规则不存在」。

08观测与可靠性：三条独立的线

这三件事经常被混为一谈，但在 letter-auto 里它们是三条各自独立的演进线，解决的是不同的问题。

三条线不是并列推进：trace 先到，才暴露出数字不可比；口径定下来，才敢动手消融红章。虚线是依赖，不是时间顺序。

看得到：trace

EV-002 · 08-21

用 Langfuse + OTel 替换 Claude Agent SDK 的 beta telemetry。因为 agent_runtime.py 是手写的 tool_use 循环，压根不走 SDK，所以「等 SDK 自动注入」这条路本来就不成立。

  • auto：opentelemetry-instrumentation-anthropic hook 住 messages.create()，零代码改动覆盖所有 LLM 调用
  • 手动：tracing.py 埋业务结构 inspection.run → rule → agent.turn → tool
  • 禁用时全为 no-op，离线测试保持纯净
自部署 Docker，数据不出本机。trace 全量记录含 PDF 文本片段。

看得准：口径

EV-015 + 票01 + 票09

有 trace 不等于能解释。三条纪律叠起来才让数字可用。

  • 发布不等历史（EV-015）：报告已生成不等于历史已保存，COMPLETED/FAILED 的含义不因保存失败改变
  • 对上身份（dfa5813）：成功检测要能对上 Git / 页 / attempt / 重试，否则只能猜 version 为空的旧 trace
  • 先说口径（c2a6b8a）：离线展开可靠性 Langfuse 子树，核对 15 vs 27 的口径差再冻结基线
EV-017 后续追加：票09 是 T_user、票10 是 T_sse，口径不同不得互相换算。

判得对：证据契约

EV-016 → EV-022

可靠性报告的红章要求，从「必须有」改成「不要」，靠的是消融实验而不是口味。

  • EV-016 原本补齐：像素颜色/清晰度观察 + 完整范围作为 PASS 前提
  • EV-022 取消红章要求：印章与结果列的通过语义没有因果关系，维持它只是每次多 2 次像素视觉调用
  • 消融证实：去掉后范围内结果行、页码引用、scope_complete 全都不变
  • 仍然现行：不删除有效行、不裁续页、不用未知颜色推定缺章
这是「证据契约」而非「观测」：它约束的是 judge 消费什么，不是采集什么。
