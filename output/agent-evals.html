先回答：这次谁讲得更好？

若选一份作为主讲解，我选 grok4.6；数学图解选 v4-flash。

grok4.6 的知识结构更完整；v4-flash 在概率示例和分步路线图上更扎实。这个结论按概念准确性与覆盖优先，再看教学组织，不用没有依据的百分制总分。

另一个细节：grok4.6 把“测 harness 和模型一起工作”放在 Evaluation harness 卡片中，仍有指代歧义。这里应明确是模型 + Agent harness；Eval harness 是执行和测量它们的基础设施。

两个版本都值得纠正的地方

  • 别把结果优先，简化成完全不看过程。授权、必要澄清、禁止操作等明确约束，本来就可能发生在执行过程中。
  • 别把成功率图只画成一个大致趋势。grok4.6 的静态曲线在 k=3 处与约 42.2% 不符。本页曲线按公式计算，并写清独立试验假设。
  • 别把一次样本当模型排名。这次 grok4.6 的覆盖更好，不能推出它在其他文章、提示词或重复生成中始终胜出。

评估要回答的，是“真的办成了吗”

我的理解：评估是一份可以执行的成功约定。

拿一个原创例子贯穿全篇：用户请 Agent 把测试空间里的文档《接口草案》从“收件箱”移到“项目甲”，并保留原来的阅读权限。

同一句“已完成”，三种真相

切换结果，观察为什么不能只给最终回复打分。

这里“保留阅读权限”是题目明确要求，因此属于必须通过的条件。若并未规定具体点击顺序，Agent 用菜单移动或拖拽移动都可能正确。结果检查与必要的过程约束，要分别写清。

把一轮评估拆开，就不神秘了

下面用同一个文档移动案例翻译常见术语。这些对象各有职责，混在一起就很难定位问题。

术语直白解释在案例里是什么
Task一道题：输入、起始状态、成功条件移动指定文档，保留权限
Trial从初始环境开始，实际做一遍相同题独立运行第 1 次、第 2 次……
Transcript / trace这一遍可记录的过程查找、工具参数、返回值、重试、最终回复
Outcome结束时实际留下的状态文档的父目录、访问列表、文件数量
Grader检查某一方面的裁判程序比对目录 ID、权限；量表评价说明是否清楚
Suite围绕能力或行为组织的一组题移动、重命名、同名文件、无权限场景
Agent harness让模型能够行动的运行系统提示词、工具接口、状态管理、停止条件
Eval harness组织考试、保存证据、汇总判分的系统重置空间 → 调用 Agent → 收集记录 → 检查结果

被测对象是完整 Agent 系统

即使模型不变，换工具说明、上下文裁剪策略或可用时长，也可能改变结果。比较模型时，需要说明哪些条件固定、哪些条件不同。

工程补充：记录模型、提示词、工具、数据集、裁判版本与预算，让下一次比较知道自己在比什么。
展开：最小评估运行器伪代码
for task in suite:
  for trial_id in range(repetitions):
    env = reset_to(task.initial_state)
    trace = run_agent(task.input, env, frozen_agent_config)
    outcome = inspect_environment(env)
    checks = grade(task.criteria, trace, outcome)
    save(task.id, trial_id, checks, trace, outcome)
aggregate_by_task_and_failure_type()

这是教学伪代码，不是某个框架的配置 API。重置失败或工具服务故障应单独记录；直接混入能力失败，会把基础设施问题算到模型头上。

让最合适的证据，回答对应的问题

方式本例怎么用优势与代价常见误判
代码裁判比较 parent_id、ACL 集合、文件总数速度快、结果容易复查；需要可读取的状态只认某个文件名字符串，误拒绝有效结果
模型裁判按量表判断是否说明移动结果及失败原因能处理开放表达；成本与波动更高偏爱长答案，或被“我已成功”说服
人工裁判解决争议，检查量表是否符合真实需求能理解复杂上下文；慢且存在人际分歧标准没对齐，不同人给出不同结论

把“通过”与“做得多好”分开

本例硬条件

  • 目标文档确实位于项目甲。
  • 阅读权限集合保持不变。
  • 没有错误移动其他文档。

本例质量与效率

  • 完成说明是否清楚、准确。
  • 同名文档时是否正确澄清。
  • 用时、工具调用次数、成本。

原创评分设计：硬条件全部成立才算任务通过；说明质量另记 0–2 分。诊断时仍保留各项部分分，方便看出“已经移动成功，但权限出了错”。不要让文风得分抵消权限失败。

展开：可复核的模型评分量表
维度：完成说明的准确性
2 = 说明与环境证据一致，清楚指出成功或失败
1 = 没有虚构，但表达含糊、遗漏关键状态
0 = 声称了证据不支持的结果
Unknown = 提供的证据不足以判断

输出：分数 + 证据位置 + 一句理由
输入：用户请求、允许查看的过程记录、已核实的终态

先请人工给一批相同样本评分，再检查人机分歧集中在哪里。Unknown 表示需要补证据，不能自动算作成功。模型裁判读取的 Agent 文本是待评内容，不应成为裁判的新指令。

展开：工具调用顺序到底能不能检查？

可以，但要能追溯到要求。“必须先核实权限再修改共享设置”可以是明确的安全约束；“必须第 2 步点击某个按钮”通常只是在绑定一种实现。先问：换一条合法路径完成同一目标，为什么应该失败？

多试几次能成功，和每次都成功差很远

下面是数学演示：假设同一道题每次成功概率固定为 p，各次试验相互独立。它不代表任何模型的实测表现。

pass@k · 至少一次成功
k 次机会里找到一个可用结果。
pass^k · k 次全部成功
重复服务时，次次都不出错。
至少一次成功：1 − (1 − p)ᵏ全部成功：pᵏ

落到产品：允许反复生成候选稿时，可以关心有没有一个可用版本；每次都要准确执行用户操作时，需要关心稳定性。重试还涉及识别哪个结果正确，以及额外成本，不能只盯着越来越高的 pass@k。

展开：实际测评不要直接套“平均成功率”

不同题的难度不同。假设两道题的 p 分别为 100% 和 0%，平均 p 是 50%。各做两次后，逐题计算再平均的 pass@2 仍为 50%；把平均 p 代进公式却得到 75%。顺序不同，答案不同。

实际应按题记录多次结果，再汇总。有限样本也有不确定性；100% 的观测通过率不证明未来永不失败。共享缓存、同一个服务故障、前一次试验留下的文件，会破坏独立假设。

补充统计形式：一题采样 n 次、其中 c 次正确时，常见 pass@k 估计为 1 − C(n−c,k)/C(n,k)，要求 n≥k；它不同于把观测成功率粗略代入独立概率公式。

同一套思路，四种证据重点

这里给出独立设计的教学题。先想“什么证据足以判定”，再选裁判，不必为每道题堆满所有工具。

Agent 类型示例任务主要证据容易漏掉
编程修复重复提交产生两条记录复现测试转绿；既有测试不退化；审查改动测试是否能抓住根因？是否通过删除检查来过关？
对话帮助用户排查无法导出的原因问题解决状态；说明质量；必要信息是否问到模拟用户太配合，掩盖真实对话的歧义
研究比较三份技术方案的适用条件结论有依据；关键维度覆盖；来源足够可靠引用存在，却并不支持旁边的结论
电脑操作移动文档并保留权限目录、文件与权限终态；必要时界面证据页面弹出成功提示，后台操作其实失败

效率也要按场景衡量：读一篇文章与寻找某个视觉控件，适合的观察方式可能不同。DOM、截图、工具调用的选择，应同时看成功率、耗时和 token 成本。

如何开始：每一步留下一个可检查的产物

原文建议早期可从 20–50 条真实用例起步，这只是起点，不是统计充分性的保证。以下是我给这个文档管理 Agent 设计的起步方案，不是强制流程。

  1. 写成功约定把“整理文档”改成文档 ID、目标目录、权限约束及允许的澄清行为。产物：别人也能一致判分的题面。
  2. 收集有代表性的少量题先覆盖成功移动、同名歧义、没有写权限、目标已存在、无需移动等。产物：小型任务集及每题来源。
  3. 人工做出参考结果在同样环境中验证题能做；让正确结果通过裁判，错误目录或权限变化被拒绝。产物：参考状态与正反校验。
  4. 冻结比较条件固定工具、提示词、时间预算、测试空间与版本；每次恢复相同起点。产物：运行配置。
  5. 保存首轮基线记录每题、每次试验的状态、证据、用时和成本。产物：可追溯结果表，附失败样本。
  6. 修最有价值的失败先核对是任务、裁判、环境还是 Agent 的问题。一次修改对应一个解释。产物：前后对照。
  7. 同时看进步和退步难题集用于发现能力提升，已稳定题用于观察回归。产物：分题变化，而不是只有总分。
  8. 持续补真实案例把线上出现的新问题整理成脱敏、可重放的题；明确谁维护环境、谁维护题面。产物：有负责人和变更记录的套件。

能力集：帮助向前走

放目前还做不稳、但产品真正需要的题。题目过于简单，分数就无法反映进一步提升。

回归集：确认没有后退

保留过去已经证明能完成的工作。能力题做稳后可以转入回归集，再补更有挑战的题。一次掉分先查样本与波动，不直接断言能力下降。

分数变化，至少有四种解释

Agent 变了理解或执行确实改善／退化
题目变了要求含糊、难度或分布改变
裁判变了阈值或判断方式改变
环境变了数据、服务、权限、资源改变

我的判断顺序：先读失败证据，再解释聚合分数。看到新版本 84%、旧版本 80%，还应问差异发生在哪些题、跑了多少次、是否换了环境。

表面现象原创反例该补的证据
总分变高大量简单重命名掩盖了权限处理退化按业务场景拆分结果
一直零分题面允许同名文档，裁判却偷设唯一 ID参考解与题面一致性
连续全过前一轮已把文件移好，后续只读到成功状态每次初始快照与环境隔离记录
回复质量高语言流畅，但把 doc_18 当成 doc_17真实操作对象和终态
执行特别快省掉了必要澄清，碰巧选对同名文件成功率、约束与耗时一起看

两份页面自身也可以被这样评估：概念是否正确、图表是否算对、覆盖是否完整、读者是否能实际解释并应用。篇幅和视觉吸引力只是辅助信号。

离线评估之后，还要回到真实使用

用下面这条原创反馈链理解长期运行。每一层解决不同问题，不能因为一层“全绿”就跳过其余证据。

方式给你的答案它独自回答不了
离线自动评估已知题上的变化未知用法是否出问题
生产监控哪里慢、哪里出错、实际使用模式所有请求是否真的完成用户目标
A/B 测试真实用户结果是否随版本改变每一个差异的具体根因
用户反馈用户在意但你没想到的问题无反馈用户的整体质量
人工读过程失败如何发生、裁判是否合理低成本覆盖所有流量
系统化人工评审按统一标准校准主观质量没有争议的永久标准

真实问题 → 整理成题 → 跑出证据 → 改进 Agent → 回到真实使用。

展开：需要先选一个评估平台吗？

我的建议是先确定要保存的证据和要判断的条件，再决定工具。一个目录、一段脚本、一张结果表也可以开始；需要并发隔离、追踪或团队协作时，再选满足这些条件的平台。

原文附录列出的框架可作为进一步阅读入口：Harbor、Braintrust、LangSmith、Langfuse、Arize Phoenix / AX。这里不对它们的当前价格或功能做独立评测。

三道题，检查是否真的理解

1. Agent 没走参考解的点击顺序，但结果和权限都对。

2. p=75%，独立跑三次，至少成功一次与全部成功？

3. 新版本一次比旧版本高 4 个百分点，说明什么？
