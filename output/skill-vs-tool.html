AGENT 能力分工图解

为什么数据收集用 Skill，方案计算却用 Tool？

同一个 Agent 身上装着两种"外挂"，它们的干活方式完全不同。理解了差异，就理解了行程规划的所有设计。

1先搞清楚：Skill 和 Tool 到底是什么

模型大脑只能"想"和"说"。要联网、要算账，就得靠外挂。两种外挂的区别在于——活是模型自己干，还是代码干。
🧠
LLM 大脑
会理解、会判断、会生成
但不会"执行"外部动作
⇄
SKILL · 说明书

📖 Skill 是"教模型怎么干"

SKILL.md（操作手册）被塞进模型上下文。

模型读手册 → 模型自己动手（比如照着命令用法拼出 curl 去调 API）
活是模型干的 → 每一步都花"思考的钱"（token），且行为不完全稳定
⇄
TOOL · 办事窗口

🛠 Tool 是"让代码干"

模型只喊一声 + 传参数。

模型下单 → Java 代码执行（算完、查完）→ 结果递回给模型
活是代码干的 → 模型零消耗，结果精确稳定，过程模型看不见
一个类比：
📖 Skill = 给实习生一本《操作手册》
实习生（模型）自己读手册、自己打电话查航班。
灵活但慢、会记错手册、每次都要重新读。
🛠 Tool = 按一下计算器按钮
你只按"求和"，计算器（代码）瞬间给出精确答案。
快、准、免费，但它不会替你做判断。

2行程规划的流水线：两种外挂各守一段

整条流程分三段，恰好每段用对了一种能力。
用 SKILL

阶段一 · 数据收集

tuniu-cli skill 教模型拼 CLI 命令：
"上海→杭州 6月1日 航班" → 模型照手册调 API，拿回真实候选：5 个去程、3 个酒店、4 个返程

难点是"理解人话→拼命令"，模型擅长
→
用 TOOL

阶段二 · 方案计算 ⭐

60 种组合要算总价、总耗时、合规校验、偏好打分、归一化排序——交给 ItineraryPlannerTool，纯 Java 毫秒算完

难点是"批量精确计算"，代码擅长
→
用 TOOL

阶段三 · 方案审核

ItineraryReviewTool 从存储里取出方案文件做质量评估，同样不占用模型上下文

模型只做判断，不做计算
为什么阶段一不用 Tool、阶段二不用 Skill？
判断一句口诀："难点是理解 → 给 Skill；难点是计算 → 给 Tool"。
数据收集是"把中文需求翻译成命令参数"（理解题）；方案计算是"60 个组合逐一算账排序"（计算题）。下面看阶段二交给 LLM 会出什么事。

3问题来了：阶段二为什么死活不能交给模型？

假设 5 个去程 × 3 个酒店 × 4 个返程 = 60 种组合。让 LLM 在"脑子里"算这 60 笔账，会踩四个坑：

坑 ①：算得贵 —— 模型"想一遍"是要花钱花时间的

模型在上下文里展开 60 个组合逐一计算：60 组合 × 约 200 token ≈ 12000 token 纯计算。而 Java 的 for 循环：毫秒级、0 token。

// Java 三行搞定，模型要"写"60 段心算
for (去程 : 5) { for (酒店 : 3) { for (返程 : 4) { 组合.add(算总价/耗时/合规) } } }

坑 ②：记不住 —— 中间算过的数字会"失忆"（Lost in the Middle）

归一化要先记住全部 60 个组合的价格，回头取 min/max 再打分（两遍扫描）。试试你能否记住这串数字的中间部分：

方案1: 1580元 方案2: 1690元 方案3: 1750元 方案4: 1820元 方案30: 2620元（读到中间，前面的价格已经模糊了） …… 方案58: 4150元 方案59: 4230元 方案60: 4500元

模型对长上下文中间位置的记忆最差（开头和结尾记得清）。要它"记住全部再回头归一化"，结果必然失真。Java 代码有变量可以存状态，模型只有注意力。

坑 ③：判不准 —— 政策合规是"精确比较"，不是"我觉得"

酒店 399.50 元/晚 vs 政策限额 400 元：模型可能回答"基本合规"，代码给出确定答案 399.50 ≤ 400.0 → pass。
还有舱位校验：经济舱/economy、商务舱/business 这种中英文别名映射，靠代码查表，不靠模型猜。

合规判断没有中间态——对就是对，错就是错，这类判断只该出现在代码里。

坑 ④：塞不下 —— 上下文窗口是稀缺资源

环节如果让模型算（Skill）用 @Tool（代码算）
输入候选数据~3000 token~3000 token（传参）
组合计算过程~12000 token0 token（JVM 内执行）
归一化 + 排序~5000 token0 token
输出结果~2000 token~200 token（只报摘要）
额外总消耗~19000 token~200 token
差接近 100 倍。而且 SKILL.md 本身也要占上下文（tuniu-cli 手册 157 行），再为计算写个 Skill，窗口更挤。

4最妙的设计：结果不进上下文，只传"取件码"

就算算完了，60 个方案的完整结果也不能全塞给模型——审核阶段还要再看一遍，等于双份全量。gogo 的做法是「结果落存储，链路只传引用」：

❌ 如果全在模型脑子里（Skill 路线）

  • 搜索候选 → 进上下文
  • 60 个组合全量计算 → 全在上下文
  • 模型"感知"所有中间过程
  • 审核阶段：这些结果还在上下文里被反复读
  • 每轮对话都背着 19000+ token 的包袱

✅ 代码算完存库，只传地址（gogo 实际）

  • PlannerTool 算完 → 结果存 Redis（key：planner:result:{userId}）
  • 工具只回一句话："已生成 N 个方案"
  • 模型上下文里只多了 几个参数，不是 60 个方案
  • 审核 Tool 拿同样的 key 自己取文件再评估
  • 全链路瘦身：一次计算、多方复用、过程零污染
ItineraryPlannerTool // 阶段二：计算 算完 60 组合、排序 → save(userId, origin, dest, date, resultJson) 返回给模型: "已生成 8 个候选方案" ← 只报数，不报内容 ItineraryReviewTool // 阶段三：审核（另一个 Agent / 另一轮） load(userId, origin, dest, date) → 从 Redis 取回方案文件 → 逐条评估 两个工具 不共享会话对象，靠 Redis 接力
Skill = 教模型做事（模型读手册、自己干：适合理解型、灵活型步骤）
Tool = 替模型做事（代码干完递结果：适合计算型、精确型步骤） 选型口诀：能一句话说清怎么干 → Skill；需要算得准、批量算、结果要瘦身 → Tool。
本质是把「智能」留给模型（判断、生成），把「计算」沉给代码（枚举、比较、排序、存储）。
