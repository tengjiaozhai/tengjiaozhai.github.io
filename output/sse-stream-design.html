letter-auto 检测服务的 SSE 连接设计

一次检测的实时结果推送：浏览器 ↔ SSE 路由 ↔ 内存任务表/逐任务队列 ↔ 后台检测执行

前端mcp_tester.html
streamInspection()：EventSource 订阅 verdict 流，收到 complete/error 才 settle；pollInspection()：500ms×600 次轮询兜底。
服务端server.py
GET /v2/inspection/{task_id}/stream：快路径（已终态）或 live 流；15s keepalive 注释行。
状态层tasks.py + 队列
每任务一条 asyncio.Queue[RuleResult|None]；终态快照（COMPLETED/FAILED + report）是唯一报告权威。
执行层inspection.py
_run_inspection_inner 每产出一条 RuleResult 即 put 进队列（不含哨兵）。

③ 客户端拿到结果的四条路径（容错设计）

路径触发行为何时兜底生效
live 流（主）订阅时任务 RUNNINGverdict 逐条 → 哨兵 → complete/error → 关流正常情况
快路径订阅时任务已 COMPLETED/FAILED（迟到/重连）不走队列，立即发一次 complete/error 并关闭刷新页面、断线重连
轮询兜底SSE 失败/前端走 pollInspection每 500ms 调 MCP get_inspection，最多 5 分钟EventSource 连不上；终态仍可从任务表取到
错误事件服务端推 error 或连接重置 CLOSED带 data → reject 业务错误；无 data 且 CLOSED → reject SSE_UNAVAILABLE；CONNECTING → 浏览器自动重连检测程序失败 / 服务端异常

④ 连接何时结束（资源回收）

正常收尾：哨兵 → 终态事件 → 生成器耗尽 → 服务端关连接；前端收到后主动 close()
浏览器断开：keepalive 周期内 is_disconnected() 检测到 → 下一轮退出（延迟 ≤15s）
挂起的风险点：哨兵没 put 或队列被多消费者抢走 → 前端 Promise 无超时、一直转圈，只能等 error/重连/轮询

⑤ 设计要点（为什么这么搭）

  • 报告权威在内存任务表，SSE 只是通知通道：查询、重连快路径、轮询都读同一终态快照，多订阅者拿到的结果一致。
  • 队列 FIFO 保证顺序：哨兵排在所有 verdict 之后，「先收完结果、再发终态」由队列天然保证，不依赖时序竞态。
  • 毒丸只投一次：单生产者；多连接竞争时仅一个消费者正常收尾，其余靠断开检测回收——这是已知的简化，非 worker 池广播模型。
  • history 与 SSE 解耦：MySQL 延后到哨兵之后、在同一执行任务内 await，数据库再慢也不挡终态与页面展示（dcb2991）。
  • 终态事件只发一次、内容由服务端定：客户端不做结果拼装，complete 的 payload 就是最终报告。
