Harness v2 图解

pi 编码 Agent 的"执行引擎"是怎么工作的？
用最简单的话讲清楚一份 3400 行的设计文档。

一句话版本

Harness 就是一个不会丢进度的 AI 对话引擎。
你告诉它做什么 → 它调 AI、跑工具、记笔记 →
就算中途断电，重启后也能从断点继续。

1 核心比喻：一个超级记事本

把 Harness 想象成一个永远不会丢页的记事本。

想象你在写一本不会丢的作业本

普通记事本：写到一半掉水里，全没了。
Harness 记事本：每写一个字之前，先把要写什么记下来；写完之后，再打个勾。 就算掉水里，捞起来看看"记了但没打勾的"，就知道该从哪里继续。

📝

先写"打算"

做任何事之前，先写一条"我打算做 X"的记录。这叫 intent record。

✅

再写"结果"

做完之后，写一条"X 做完了，结果是 Y"。这叫 result entry。

🔄

崩溃恢复

重启后扫描：有"打算"但没"结果"的 → 重新做一遍或补一个假结果。

2 Session：一个会话的四件套

每个 Session（会话）由四个部分组成，就像一个人的四种记忆。

用 Slack 来理解

一个 Slack 频道 = 一个 Session。
频道里的每个帖子（thread）= 一条 Lane（车道）。
所有帖子的消息都在同一棵 对话树 上，但各自独立推进。
你可以在 A 帖子里聊代码，同时在 B 帖子里跑测试——互不干扰。

3 Lane（车道）：并行工作的秘密

为什么需要多条车道？因为 AI 经常要同时干好几件事。

🚗

每条车道一次只跑一个操作

就像一条车道上一次只能过一辆车。但不同车道可以同时过不同的车。

🌿

像 Git 分支

每条车道指向对话树的一个叶子节点。新消息追加到叶子后面，叶子就往前移一格。

🧭

可以跳转

车道可以"导航"到树上任意节点——就像 Git checkout 到旧提交，然后从那里开始新分支。

4 三种操作：跑、压、跳

车道上只能做三种操作，对应日常使用的三个动作。

🏃

Run（跑）

最常用

接受一个 prompt，调 AI，跑工具，自动续轮，直到没事干为止。就像你跟 AI 说"帮我修这个 bug"，它一直干到修完。

📦

Compaction（压）

上下文压缩

对话太长了，AI 的"脑容量"装不下了。把旧对话压缩成一段摘要，腾出空间继续聊。

🔀

Navigation（跳）

时间旅行

把车道的叶子节点跳到对话树上的任意位置。可以回到过去，从某个旧节点重新开始。

🔑 关键规则

每条车道同一时刻只能跑一个操作。想同时干两件事？开两条车道。这就是"并行"的实现方式——不是在一个车道上多线程，而是多个车道各跑各的。

5 持久化：崩溃了怎么办？

这是整篇文档最核心的设计——"先写打算，再写结果"。

📝 写"打算"
→
⚡ 执行操作
→
✅ 写"结果"

崩溃可能发生在三个位置

工具调用的崩溃恢复

工具分两种："安全重放"（比如读文件）和 "不能重放"（比如写文件、删东西）。

崩溃后恢复时：
• 安全工具 → 用之前记录的参数重新跑一遍
• 不安全工具 → 不重跑，直接补一个"被中断了"的假结果

这样就不会因为崩溃恢复而重复执行危险操作。

6 一次 Run 的完整生命周期

从你说"帮我修 bug"到 AI 说"搞定了"，中间发生了什么？

1️⃣ 接受 prompt

写 operation_started 记录。从这一刻起，这个操作就是"持久化"的——崩了也能恢复。

2️⃣ 写入用户消息

你的 prompt 变成对话树上的一个 entry。叶子节点移到这里。

3️⃣ 调 AI（assistant step）

写 step_attempt（第几次尝试），然后发请求给 LLM。AI 回复后写入 assistant entry。

4️⃣ 跑工具（如果 AI 要求）

每个工具调用：写 tool_started → 执行 → 写 tool result entry。多个工具可以并行跑。

5️⃣ 检查点（checkpoint）

每轮结束后过一遍检查点：应用延迟写入、消费转向消息（steer）、看看上下文是否需要压缩。

6️⃣ 继续 or 结束

如果工具结果需要 AI 继续处理 → 回到第 3 步。如果没事干了 → 写 operation_finished，Run 结束。

🔑 重试机制

AI 请求失败了可以重试，重试次数是持久化的（写在 step_attempt 里）。 这意味着就算崩溃重启，重试计数也不会归零——防止"崩溃→重启→崩溃"的死循环。

7 三种队列：插话、追加、预约

AI 正在干活的时候，你想加东西怎么办？

📢

Steer（转向）

插话

AI 正在跑，你突然说"等等，重点看测试文件"。这条消息会在下一个检查点被消费，AI 下一轮就能看到。

📬

FollowUp（追加）

追加

"等你干完这个，接着帮我做那个。"AI 本来要停了，看到追加消息就继续干。

📅

NextRun（预约）

预约

"下次 Run 的时候帮我做这个。"这条消息会一直等着，直到下一次 prompt 时被带上。

Abort 时的区别

如果你 abort（取消）一个 Run：
• Steer 和 FollowUp → 被丢弃，退还给调用方（它们是"这次"的）
• NextRun → 保留（它是"下次"的，跟这次无关）

8 Hooks 和 Events：拦截 vs 观察

扩展 Harness 行为的两种方式。

🪝 Hooks（钩子） 📡 Events（事件）
作用 拦截执行，可以改变行为 观察执行，不能改变行为
例子 before_tool：拦截工具调用，改参数或阻止 tool_start：通知 UI "工具开始跑了"
出错时 跳过这个 handler，继续跑 捕获异常，报告 handler_error
持久化 结果写入 record/entry 后才持久 不持久化，不重放
比喻 安检员：可以拦下你、改你的行李 监控摄像头：只能看，不能动
🛡️

关键 Hook

before_run — Run 开始前注入消息
before_tool — 工具执行前改参数/阻止
after_tool — 工具执行后改结果
before_compaction — 压缩前提供摘要

📊

关键 Event

run_start / run_end — Run 生命周期
message_start / end — 消息进出
tool_start / end — 工具执行
usage — token 消耗

9 上下文溢出：AI 脑子装不下了

LLM 有上下文窗口限制。对话太长怎么办？

🧠 AI 说"太长了"
→
🗑️ 丢弃溢出回复
→
📦 自动压缩
→
🔄 重试请求

怎么判断"真的装不下"还是"只是输出到了上限"？

AI 返回 stopReason: "length" 有两种可能：
• 真的上下文装不下 → 压缩后重试
• 只是输出 token 到了上限 → 正常处理

判断方法：比较实际输出 token 数和"本来打算给的最大输出"。如果实际远小于打算，说明是上下文压力导致的，可以压缩恢复。

🔑 安全阀

每次用户输入只允许一次"压缩→重试"。防止"压缩→重试→又溢出→又压缩"的死循环。

10 三种存储后端

Session 的数据存在哪里？三种选择，各有用途。

🧠

Memory（内存）

测试用

纯内存结构，重启就没了。跑测试最快，是"参考实现"——所有测试先跑它。

📄

JSONL（文件）

CLI 用

一个会话一个 .jsonl 文件，每行一条记录。兼容旧版 v3 格式。追加写一行就是原子操作。

🗄️

SQLite（数据库）

服务端用

正经的关系数据库 schema。有索引、有写锁（writer lease）、有分支缓存。适合多会话、高并发场景。

特性 Memory JSONL SQLite
持久化 ❌ ✅ 文件 ✅ 数据库
崩溃恢复 ❌ ✅ 截断坏行 ✅ 事务保证
写锁 内存队列 文件级 writer_leases 表
查询性能 O(n) 遍历 O(n) 全文件 索引查询
v3 兼容 — ✅ 自动转换 —
11 延迟请求：AI 说"等会儿再来拿"

有些 AI 请求不是即时返回的，而是"先给你一个取件码，过几个小时来拿结果"。

📤 发请求
→
🎫 拿到取件码
→
😴 车道挂起
→
📥 取回结果

典型场景：批量 API

比如 OpenAI 的 Batch API，提交任务后返回一个 handle，过一段时间结果才好。
Harness 把 handle 存进 assistant entry，车道进入 suspended 状态。
过几个小时（甚至换一个进程），调 resume() 去取结果，然后继续跑。

从存储角度看，suspended 和 crashed 完全一样——都是"有个操作没完成"。resume 统一处理。

12 手动驾驶模式：测试的杀手锏

怎么测试一个"崩溃恢复"系统？答案是：让每一步都可以暂停。

🤖

Automatic（自动）

生产模式。操作一路跑到底，不停。

🎮

Manual（手动）

测试模式。每个"效果"（写 entry、调 AI、跑工具）之前都停下来，等测试代码说"继续"才走下一步。

为什么这很重要？

测试可以这样做：
1. 跑到某个步骤 → 暂停
2. 模拟崩溃（关掉 harness）
3. 重新打开 → 验证恢复是否正确

生产和测试跑的是同一套代码，只是"边界"不同。这保证了测试覆盖的就是真实行为。

★ 总结：五个核心设计决策
1️⃣

先写打算，再写结果

没有多记录原子提交。每条记录独立持久化。崩溃后看"有打算没结果"的来恢复。

2️⃣

车道并行，单车道串行

并行不靠多线程，靠多车道。每条车道内部严格串行，避免竞态。

3️⃣

对话树只增不改

entry 一旦写入就永远不变。分支共享前缀，不复制。像 Git 的 commit 历史。

4️⃣

单写者

一个 Session 同一时刻只有一个 Harness 在写。由服务层保证。不需要分布式锁。

5️⃣

上下文只往尾巴长

发给 AI 的消息序列只在末尾追加。中间插入会破坏 KV cache，浪费 token。压缩是唯一允许的"例外"。
