LLM 推理策略 · TEST-TIME COMPUTE

四种推理组织策略，四种不同的成本结构

CoT 沿单一路径求解，Self-Consistency 多路径采样后投票，ToT 在状态空间里搜索与回溯，GoT 把中间结果连成图做复用与融合。它们不是四个模型，是四种把算力换成正确率的方式。

沿单一路径逐步求解，不主动维护多个搜索分支。

适用情况
多步骤问题，路径相对明确
主要风险
早期错误可能沿后续步骤传播

CoT 的边界：它是提示手段，不是验证手段

  • 模型写出的「推理步骤」是公开输出，不等于内部真实的计算轨迹，所以步骤写得多不等于更准。
  • 可验证的环节要交给外部工具：算术用计算器、代码跑测试、规则判断用规则引擎。用文字解释当验收证据，是本类方法最常见的误用。
  • 对现代推理模型，明确目标、约束、验收标准通常比强制输出长思维链更有效（OpenAI 推理模型文档明确指出 think step by step 类提示可能无益甚至有害）。

对同一问题独立采样多次，提取并归一化答案，再进行投票。

适用情况
答案可以客观比较、模型单次结果不稳定
主要风险
多个采样可能犯相同错误

三个必须拆开的动作：独立采样 → 归一化 → 投票

  • 独立采样：必须是多次模型调用。让模型在一次回答里扮演五个角色，不是五次采样 —— 共享同一段上下文意味着共享同一个偏差。
  • 归一化：13 与 13.0 要判等，日期范围 与 日期区间 要映射到同一组件类型。对整段自由文本做简单多数投票没有意义。
  • 投票：票数不是置信度。5 次里 4 次一致，正确概率不是 80% —— 同一模型的采样错误是相关的。多个答案票数接近时要交给验证器或人工，不能强行宣称可靠。
  • N 从 3 或 5 起步做对照实验，逐步测边际收益；N 不是越大越好。

维护候选中间状态，生成分支、评估、剪枝，必要时回溯。

适用情况
有多个候选路径，且中间状态可评价
主要风险
评估器不可靠时，搜索可能走偏

没有状态管理的「提三个方案选一个」不是 ToT

  • 先定义状态空间：当前状态含什么、一次动作改变什么、什么算成功、什么时候提前终止。缺了这四条，搜索无法复现。
  • 评估器优先用外部的：代码修复看单测与编译、SQL 看语法与执行结果、规划看约束校验。LLM-as-a-Judge 只做辅助。
  • 从 2～3 个候选、浅深度起步并设调用预算；每条分支至少留状态 ID、父状态、候选动作、评估结果、是否继续五项记录。
  • 对明确、简单的任务上搜索，是拿成本换噪声。

将推理结果作为图节点，允许跨分支复用、聚合与迭代改进。

适用情况
多份推理结果相互依赖，需要组合与复用
主要风险
状态管理与反馈循环增加复杂性

图和循环都是要付利息的

  • 节点要保持单一职责：提取约束、生成方案、校验兼容性各一个节点，别让每个节点都重跑整个任务。
  • 聚合后仍要能追溯来源，并做冲突检测再拼接 —— 不同来源的结论可能互相矛盾。
  • 反馈循环必须有停止条件：版本号、最大迭代次数、收敛阈值、预算上限，四选一以上。
  • 顺序执行能解决时，普通工作流比图调度器便宜得多；只选一条路线时，ToT 就够。

选型：先问「错在哪」，再问「该加哪层」

症状该加什么判据
问题要多步处理，但路线基本唯一CoT —— 分步求解，把验收条件写进 prompt首选
答案明确可比较，单次结果不稳定Self-Consistency —— 独立采样 + 归一化 + 投票性价比高
存在多条候选路径，中间状态可评分，早错会致命ToT —— 生成 / 评估 / 搜索 / 回溯成本陡增
多个中间结果要融合，且存在跨分支复用与迭代GoT —— 图节点 + 聚合 + 反馈收敛工程最重
普通 Agent Loop 已能稳定完成什么都不加默认

三句话记住分工：CoT = 分步求解；Self-Consistency = 多次采样 + 聚合；ToT = 生成候选 + 评估 + 搜索；GoT = 推理图 + 聚合 + 复用 + 反馈。

Prompt 能做到的，和必须由代码做到的

方法Prompt 模拟真正的工程实现
CoT要求按步骤解释单路径执行 + 外部验证
Self-Consistency一次回答里提多个答案独立采样、答案标准化、投票
ToT列出三个方案作比较显式状态、搜索预算、回溯
GoT分析多个模块再合并节点依赖调度、融合、反馈收敛
Prompt 能引导推理方式，但替代不了必须由程序执行的采样、搜索、状态管理与验证。判断一段实现是不是 ToT，看它有没有可回放的状态记录，而不是看 prompt 里有没有「请评估这三个方案」。

怎么证明加对了：消融与成本收益

  • 先立 baseline（普通 prompt / Agent Loop 的实际任务完成率），再加实验组，固定模型版本、任务集、工具与环境。
  • 做消融：去掉 Self-Consistency 的投票、去掉 ToT 的中间评估、去掉 GoT 的融合或反馈，看增益是否真的来自那个模块。
  • 报三组指标：质量（任务完成率 / 准确率 / 约束满足率 / 无效输出率）、效率（token、端到端与 P95 延迟、工具调用次数）、可靠性（多次运行稳定性、验证失败率、回退成功率）。
  • 结论不写在「准确率更高」，而写在「多花的算力与延迟，换来的质量提升是否值」。照搬论文结论做生产选型，是这条路上最常见的错。
