Spring 对标: AOP @Around 前置逻辑
🛡️
Middleware (中间件)
AgentScope 抽象: MiddlewareBase
☕ Java Spring 终极对标
OncePerRequestFilter + Spring AOP @Around
把控整个请求的进入（Inbound）与穿出（Outbound），拥有 proceed() 的放行/短路裁决权。
// Java Spring AOP 环绕切面 @Around("execution(* Agent.reply(..))") public Object aroundReply(ProceedingJoinPoint pjp) { // 1. 前置：记录耗时、启动后台线程 long start = System.currentTimeMillis(); try { return pjp.proceed(); // 穿透进入内层 } finally { // 2. 后置：统一清理资源、防内存泄漏 cleanup(); } }

为什么有状态？ 中间件是一个 Object 实例（类似带有成员变量的 Request-scoped Bean），前置放进去的句柄，后置在 finally 里精准释放。

🪝
Hook (生命周期钩子)
AgentScope 抽象: on_reasoning, on_acting
☕ Java Spring 终极对标
Spring @EventListener / AOP @Before
框架在主干流程固定节点暴露的“插槽/观察点”。主干只是在特定时刻回调通知你，你无法“包裹”主流程。
// Java Spring 事件监听器（单向旁路通知） @EventListener public void onReasoningStep(ReasoningEvent event) { // 只是单点被触发，无法包裹内层代码 if (hasMemory()) { event.injectHint(...); // 动态塞入提示 } }

为什么不能单独当组件？ Hook 只是一个孤立的事件回调方法。如果把多个 Hook 拆成零散函数，跨 Hook 传递参数就只能依赖丑陋的静态全局变量。

🧰
Tool (工具)
AgentScope 抽象: Toolkit / ToolBase
☕ Java Spring 终极对标
业务层 @Service Bean / FeignClient
暴露给核心大脑（LLM）主动调用的具体业务方法。LLM 决定“调不调”、“何时调”、“传什么参数”。
// Java 业务 Service：主动调用的业务工具 @Service public class FileStorageService { public void writeFile(String path, String content) { // 由 LLM 大脑决策后主动发出指令执行 Files.writeString(Path.of(path), content); } }

本质差别： Tool 是被动的武器，LLM 是拿起武器的手；而 Middleware 是管着整个屋子的电闸、门禁和安检机。

三者工程化属性全景天梯表

工程维度 Middleware (中间件) Hook (拦截点/钩子) Tool (工具)
驱动力 (Who triggers) 框架运行时自动环绕触发 框架在特定时机单点回调 LLM 大脑自主决策主动调用
控制流模式 双向折返跑 (Inbound ➔ Outbound) 单向单点回调 (Point-in-time) 外部方法调用 (RPC / API)
生命周期包裹能力 ✅ 拥有 try...finally 绝对掌控权 ❌ 无法包裹整个主流程 ❌ 仅负责单一业务动作返回
状态存储机制 实例私有成员 (self._task) 无状态（被迫依赖全局字典或上下文） 通常无状态或单例内部无副作用
Java 架构对标 Spring AOP @Around / FilterChain Spring @EventListener / @Before Spring @Service / Feign Client
