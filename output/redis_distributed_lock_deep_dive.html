第一步：原子抢锁与自旋等待 (Spinlock with Backoff)

src/agentscope/app/message_bus/_redis_message_bus.py (Line 664-670) Python 3.10+ 
token = uuid.uuid4().hex
# Acquire (poll until success).
while True:
    ok = await self._client.set(key, token, nx=True, ex=ttl_secs)
    if ok:
        break
    await asyncio.sleep(self._LOCK_RETRY_DELAY_SECS)  # 默认 100ms

① 为什么必须带上 UUID token？

绝不能简单地 SET key 1 NX！必须为每一次加锁生成全局唯一的随机字符串（uuid.uuid4().hex），作为持锁者的身份凭证（Ownership Token）。后续所有的解锁操作都必须校验这个 Token，防止自己释放了别人的锁。

② 为什么 NX 和 EX 必须在同一条命令？

早期 Redis 开发者常犯错误：先执行 SETNX key val，再执行 EXPIRE key 600。如果程序在两条命令中间遭遇 Crash，该 Key 将变成永久死锁。Redis 2.6.12 引入了原子复合指令 SET key val NX EX 600，在底层 C 语言引擎内原子执行。

自旋等待的轻量级调度：await asyncio.sleep(0.1)

在抢锁失败时，代码没有使用死循环（CPU 100%），也没有使用同步 time.sleep()（会卡死事件循环）。通过 await asyncio.sleep(0.1)，当前协程让出控制权，让事件循环处理其他 HTTP 请求，100ms 后再醒来重试，属于非常轻量优雅的自旋锁。

第二步：看门狗自动续期机制 (The Watchdog Heartbeat)

分布式锁最臭名昭著的悖论：TTL 设短了，大模型慢推理可能还没结束锁就丢了；TTL 设长了，Worker 突然断电宕机，其他节点必须干等几个小时！

src/agentscope/app/message_bus/_redis_message_bus.py (Line 672-681) Watchdog Coroutine 
# Heartbeat: renew TTL every ttl/2 seconds.
async def _heartbeat() -> None:
    while True:
        await asyncio.sleep(max(1.0, ttl_secs / 2))  # 默认 600s / 2 = 300s
        await self._client.expire(key, ttl_secs)     # 续回 600s

hb_task = asyncio.create_task(
    _heartbeat(),
    name=f"lock-heartbeat:{key}",
)
🐕 看门狗工作哲学（对标 Java Redisson Watchdog）
  • 只要进程还活着：后台协程 _heartbeat 会在租约过去一半时，准时向 Redis 发送 EXPIRE key 600，租约永远不会过期。
  • 一旦进程彻底宕机（Kill -9 / OOM / 断电）：_heartbeat 协程随之瞬间死亡，续期动作立刻停止。Redis 上的 Key 会在剩下的 300~600 秒内自然过期删除，整个集群自动完成故障自愈，绝不产生永久死锁！

第三步：临界区上下文转移 (Context Manager Yield)

Python 协程执行栈转移 
try:
    yield  # 👈 控制权交出，进入调用方（如 ChatService._run_body）代码块执行
finally:
    # 无论调用方正常完成，还是抛出异常，百分之百回到这里！

@asynccontextmanager 装饰器将这个生成器包装成合法的异步上下文管理器。当 yield 发生时，持锁成功，此时调用方开始读取会话状态、调度 Agent 思考。即便业务层发生任何未捕获的严重崩溃，Python 运行时的异常回溯机制也会确保必定进入下面的 finally 块。

第四步：停机与安全解锁 (Safe Token Verification)

src/agentscope/app/message_bus/_redis_message_bus.py (Line 685-700) Finally Block 
finally:
    # 1. 第一件事：立刻杀掉看门狗，不再延寿
    hb_task.cancel()
    try:
        await hb_task
    except asyncio.CancelledError:
        pass

    # 2. 第二件事：核对 Token。只删除属于自己的锁！
    try:
        current = await self._client.get(key)
        if current == token:
            await self._client.delete(key)
    except Exception:
        pass
⚠️ 致命陷阱：为什么不能直接 `DEL key`？

假设 Worker A 在临界区内遭遇了极端卡顿（如网络分区或长暂停），导致看门狗续期失败，Redis 上的锁过期被释放了。此时 Worker B 成功抢到了锁。 如果 Worker A 恢复后不做任何判断直接 await self._client.delete(key)，它就会把 Worker B 刚抢到的锁给删掉！ 因此，必须在删除前核对：current == token，只有锁还在自己手里时，才执行删除。

深入思考：为什么 AgentScope 没用 Lua 脚本而是用 GET + DEL？

在 Java Redisson 中，通常用 Lua 脚本把 if get(key) == token then del(key) 合成一条命令执行。

AgentScope 作者在代码 docstring（Line 649-653）中特意给出了极具深度的工程解释：

"The non-atomic GET+DEL race window opens only after the heartbeat is cancelled, in a sub-millisecond span; the ttl_secs lease still has plenty of time left so the race effectively never materialises."

大白话解释：看门狗刚被取消后，Redis 锁剩下的租期还有整整几百秒（plenty of time），而随后的 GET 和 DEL 操作在亚毫秒（<1ms）内就会结束。在微秒级时间内锁被别人顶替的概率在数学上几乎为 0，因此用原生的 GET + DEL 省去了加载和编译 Lua 脚本的开销，这是一种清醒实用的工程折中（Pragmatic Engineering Trade-off）。
