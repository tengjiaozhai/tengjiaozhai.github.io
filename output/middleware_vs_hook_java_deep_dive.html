先抓住区别：你得到的是“一个时机”，还是“一段流程”？

假设你已经有一个方法 answer(question)：收到问题，调用模型，返回答案。现在要加日志、鉴权、缓存、记忆检索。你不想每增加一种能力，就把这些代码塞进 answer()。框架于是提供了“让外部代码参与执行”的办法。

Hook：流程到这里，
调用你提供的代码。

Hook 的核心是扩展点。例如“调用模型之前”“工具返回之后”。框架定义时机、参数和返回值的含义，你在这些位置接入逻辑。

先问：它什么时候调用我？给我什么？允许我改变什么？

Middleware：把能力接进流程，
由统一机制组合执行。

Middleware 的核心是可组合的处理组件。常见设计会把后续处理交给它，让它在前后加逻辑；也有设计把多个生命周期回调组织成一个组件。

先问：它怎样接入？能否调用或包裹后续流程？怎样组合？

所以，两者并不总是互斥选项。一个 Middleware 完全可以通过多个 Hook 接入框架。

你最常见到的对比，是“带 next() 的环绕式中间件”与“固定时机触发的普通回调”。这两种形态确实不同，但不能据此断言：所有 Middleware 都有 next，所有 Hook 都只能观察。

本文始终区分三个层次：先用简化模型建立直觉；再看 Java 中相似的接口；最后核对这个仓库里的 AgentScope 实现。类比帮助理解，具体能力由接口和调度代码决定。

把一次请求，想成餐厅处理一张订单

订单来了，要完成“接单 → 做菜 → 出餐”。现在餐厅增加计时、验单和会员优惠。这些附加逻辑可以有不同的接入方式。

Hook 像预先留好的通知时机

厨房规定：“开始做菜前，叫一下验单员；菜做好后，叫一下质检员。”什么时候叫人、叫完后做什么，仍由厨房流程决定。

验单员能不能取消订单？取决于厨房规则。如果规则接受“拒绝”结果，他就能拦截；如果只要求他记录一条日志，他就没有正常返回意义上的取消权。

类比对应：时机 = 扩展点；验单员提供的方法 = 回调；厨房 = 框架调度器。

环绕式 Middleware 像接管订单的服务台

服务台先验单，再把订单交给下一站，等下一站处理完再打包。“交给下一站”本身就在服务台的代码里。

发现已经有做好的同款套餐，可以直接返回；如果继续下单，则可以在下游完成后统一记录耗时。这里的“把订单交下去”，就是 next() 或 proceed()。

类比对应：服务台 = 中间件；下一站 = 下游处理器；打包 = 返回后的处理。

普通 Hook：主流程向外调用回调

框架接单
→
调用 before Hook回调结束，回到框架
→
框架安排做菜
→
调用 after Hook

环绕式 Middleware：中间件向内调用下游

服务台前置逻辑
→
next()：交给厨房当前方法等待下游完成
→
回到服务台收尾

两种方式都能做验单、计时。差别不是“谁有用”，而是附加逻辑与主流程如何连接，谁负责继续执行，以及跨阶段的工作由谁组织。

拆开 Hook：插槽、回调、调度器，是三件事

“Hook”有时指框架留出的插槽，有时指你注册进去的函数。为了不混淆，我们把它拆开：

扩展点
框架明确说：“调用模型前，我会触发 beforeModel。”这是接入的位置。
回调
你写的 addMemory(context) 或 recordLog(context)。这是接入的代码。
调度器
框架遍历已注册回调，传入参数，处理返回值，再决定后面如何执行。这才是实际掌握流程的地方。

教学 Java：一个只支持修改上下文的 before Hook。这里没有缓存短路协议。

interface BeforeModelHook {
    void run(Context ctx);
}

// 用户提供回调：在真正调用模型前，补上记忆。
BeforeModelHook memoryHook = ctx -> ctx.addHint("用户偏好简洁回答");

// 以下是框架代码，不是 Hook 自己的代码。
Answer answer(Context ctx) {
    for (BeforeModelHook hook : hooks) {
        hook.run(ctx);     // 1. 框架调用 Hook
    }
    return model.call(ctx); // 2. 框架继续调用模型
}

读代码时盯住第二个调用：model.call(ctx) 写在框架的 answer 方法里。Hook 做完就返回，它没有拿到“后面的模型调用”这个对象，不能直接把那次调用放进自己的 try/finally。

但 Hook 并不等于“只能看，不能改”

不同 Hook 契约，给出的权力可以完全不同
接口长什么样它通常允许什么关键前提
void onEvent(Event e)记录日志、发送通知等副作用事件是否可修改、是否同步，仍看框架
void before(Context c)修改可变上下文框架后续确实使用修改后的内容
Decision before(Context c)返回继续、拒绝、跳过等决策调度器必须检查并执行这个决策
Answer after(Answer a)替换或加工结果框架采用回调的返回值
around(ctx, next)环绕、短路，某些契约支持重试它虽可能叫 Hook，但已具备环绕能力

名称只给提示，签名和调用方才给答案。如果一个 Hook 返回了 false，而框架完全没检查，写这个返回值就不会产生拦截效果。反过来，框架明确支持返回拒绝，Hook 就能正常阻止后续流程。

“抛异常可以让执行失败”不等于“支持业务短路”。抛异常是在走失败路径；缓存命中直接返回答案是在走成功路径。不要把异常当成任何 Hook 都有完整控制权的证明。

拆开 Middleware：关键是把“后面怎么执行”交给它

先看最典型的环绕式设计。next 不是神秘关键字，只是一个参数，指向剩余的处理流程。它可能代表另一个中间件，也可能已经是模型调用。

教学 Java：下面的 Handler、Middleware、Context 都是用于讲解的自定义类型。

interface Handler {
    Answer handle(Context ctx);
}
interface Middleware {
    Answer invoke(Context ctx, Handler next);
}

// 一个中间件：前后逻辑在同一个方法、同一次调用里。
Answer invoke(Context ctx, Handler next) {
    long start = System.nanoTime();
    try {
        Answer result = next.handle(ctx);
        return result;
    } finally {
        logElapsed(System.nanoTime() - start);
    }
}

当 next.handle(ctx) 被调用，当前方法还没有结束。它把执行权交给内层，等内层返回或抛出异常，再继续自己的后半段。因此，start 这样的局部变量可以自然贯穿前后，不用拆成两个回调再另找地方传递。

“洋葱模型”是普通嵌套调用产生的顺序

假设外层是日志中间件 A，里面是缓存中间件 B，最里面是模型。组合起来相当于 A(B(Model))。

A：日志开始
B：查询缓存，未命中
Model：生成答案
B：收到答案，写入缓存
A：记录总耗时，返回答案

进入：A → B → Model　　返回：Model → B → A

先进入 A，再进入 B。B 没结束，A 的 next 就没返回。于是收尾时自然先 B 后 A。这个反向顺序来自调用嵌套；一组独立的 before/after 回调不会仅凭名字自动获得它。

短路：返回答案，但不再调用下游

Answer invoke(Context ctx, Handler next) {
    Answer cached = cache.get(ctx.key());
    if (cached != null) {
        return cached; // 成功返回；本次不调用 next。
    }
    Answer result = next.handle(ctx);
    cache.put(ctx.key(), result);
    return result;
}

缓存中间件可以不调用模型，而外层日志中间件仍会正常收尾。注意这个“可以不调用”来自这里定义的接口；不能反推所有框架都允许不调用、多次调用或重新调用下游。例如重试还要考虑接口是否允许重复调用，以及下游操作是否会产生重复副作用。

自己点一遍：到底是谁在推动下一步？

下面用同一件事对比：先记日志，再检查缓存，必要时调用模型。它是确定性的教学模拟，没有发出模型请求。普通 Hook 版本仅允许修改上下文，框架提供错误和最终通知；中间件版本允许返回答案并跳过下游。

一次问答的执行轨迹

框架调度器入口与最终返回
日志中间件 A开始计时 / 收尾
缓存中间件 B可以决定不调用 next
模型核心执行真正的问答
框架继续主流程回调返回后由框架推进

    建议看三个位置：缓存命中时，模型有没有运行；模型抛错时，正常的 after 是否还会运行；最后收尾的逻辑，是中间件自己用 finally 包住，还是框架显式触发。

    同一件事，两种写法都能做，成本放在不同地方

    假设目标只是“记录一次模型调用的耗时，无论成功失败都记录”。普通 Hook 和环绕中间件都能实现。关键是框架有没有提供合适的最终通知，以及一次调用的状态放在哪里。

    Hook：框架负责配对与收尾时机

    // 用户的两个回调
void before(Context ctx) {
    ctx.start = System.nanoTime();
}
void finish(Context ctx) {
    logElapsed(now() - ctx.start);
}

// 框架必须真的这样调度
before(ctx);
try {
    return model.call(ctx);
} finally {
    finish(ctx);
}

    计时状态放进每次调用的 ctx。只要框架保证 finish 的正确触发，这样就合理。Hook 不是做不到，而是它依赖框架提供这个生命周期契约。

    Middleware：在包裹代码里直接配对

    // 用户的一个环绕方法
Answer invoke(Context ctx,
              Handler next) {
    long start = System.nanoTime();
    try {
        return next.handle(ctx);
    } finally {
        logElapsed(now() - start);
    }
}

    计时状态是当前调用的局部变量。前后配对关系直接写在一个代码块里，阅读时不必再追踪两个回调如何关联。

    要完成的能力普通 Hook 的实现条件典型环绕 Middleware 的实现方式
    记录日志对应时机有回调即可在调用 next 前后记录
    添加提示词允许修改上下文，或返回替代输入改好输入，再交给 next
    使用缓存答案框架有“返回替代结果并跳过核心”的协议命中后直接 return，不调用 next
    失败后重试需要专门的重试决策点或环绕扩展点若接口允许重调下游，可在异常路径重试
    打开 / 关闭资源需要可靠配对的结束、失败、取消通知用 try/finally 包住下游实际生命周期
    多个阶段共用能力把回调绑定到同一个对象或上下文一个组件集中组织多个入口和依赖

    如果框架已经有好用的 Hook，不必为了“中间件更高级”再包一层。如果确实需要跨越整段调用做配对管理，环绕接口通常能把责任表达得更直接。

    回到 AgentScope：Middleware 里，本来就有 Hook

    这不是抽象猜测。当前仓库的 MiddlewareBase 文档把扩展入口明确分成 Onion Pattern Hooks 和 Transformer Pattern Hook。也就是说，这里的 Middleware 是组件，on_* 方法是组件接入框架的 Hook，其中有些 Hook 就具有环绕能力。

    一个 Middleware 实例：集中组织一项扩展能力
    on_reply / on_reasoning / on_acting …
    拿到 next_handler，可以包裹对应阶段
    on_system_prompt
    接收当前字符串，返回转换后的字符串

    “组件”与“组件上的扩展点”是不同层次，不需要二选一。

    七个扩展点：六个 Onion Hook + 一个 Transformer · 源码定位

    看一个真实接口形状：计时 Middleware

    按当前 Python 接口编写的示意代码；保留流式转发和 finally，省略业务配置。

    import time
from agentscope.middleware import MiddlewareBase

class TimingMiddleware(MiddlewareBase):
    async def on_reasoning(self, agent, input_kwargs, next_handler):
        start = time.perf_counter()
        try:
            async for event in next_handler():
                yield event  # 把每个事件继续传给外层
        finally:
            print("reasoning elapsed:", time.perf_counter() - start)

# 构造 Agent 时，把实例加入 middlewares=[TimingMiddleware()]。

    对 Java 读者来说，next_handler() 类似“调用下一层”；async for 表示不断取出下一层产生的事件；yield event 表示把事件交给外层消费者。这里的 yield 可以发生很多次，它是在转发流，不是“只交接一次”的固定插槽。

    finally 包住的是这个异步生成器实际执行与展开的范围。消费者提前停止读取时，还要确认调用方如何关闭或取消生成器，不能仅凭这段代码就承诺所有资源立即释放。

    注册顺序，如何变成真正的调用顺序？

    middlewares = [A(), B()]

// _reply 中 execute_chain 的概念展开：
A.on_reply(next_handler = B)
  └─ B.on_reply(next_handler = reply_impl)
       └─ reply_impl 产生事件 / 最终消息
       └─ B 将事件向外 yield；B 收尾
  └─ A 将事件向外 yield；A 收尾

    当前 _reply 用 execute_chain(index + 1) 构造下一层。测试也明确断言：A 前置、B 前置；每个事件先经过 B 再经过 A；正常消费结束后 B 后置、A 后置。这里的洋葱关系有实际调用链和测试支撑。查看定位。

    边界一定要画对：on_acting 不包含完整工具生命周期

    当前实现先解析与校验工具输入、做权限决策，再进入 on_acting 包住的工具执行层。上下文写入等工作也在这个 Hook 外面。验权扩展点是 on_check_permission，不能把 on_acting 直接标成“验权插槽”。

    解析 / 校验
    →
    on_check_permission得到权限决策
    →
    允许执行时：on_acting包住原始工具执行
    →
    运行时后续处理例如上下文写入

    同样叫 next_handler，返回协议也不同。on_check_permission 可以不调用下游，直接返回权限决策；on_reply 处理事件流，并且对 ReplyEndEvent 有继续下一轮的专门语义。不能给所有 Hook 生造一个统一的 return false，也不能把改变事件流简单等同于普通 Java 方法返回值替换。

    源码里还看得到 pre_reply 等旧 Hook 名称，意味着两套机制并存吗？

    当前 types/_hook.py 仍有这些字符串类型别名，但本次检查没有发现它们在当前 Agent 中对应的旧式注册与调度体系。当前执行入口使用 middlewares 和 on_*。看到历史名称或类型声明，不能据此认定运行时仍沿用旧流程。

    这一节核验的是用户当前 Python 工作区。文件名中的 Java 指讲解视角；此处没有宣称 AgentScope-Java 提供同名接口。

    对应到 Java：看接口形状，比记注解更有用

    下面这些是相似机制的映射，不是说它们在所有场景下完全等价。尤其要区分 HTTP 请求、一次 Java 方法调用、一次 Agent 回复：三者的生命周期长度可能不同。

    Java / Spring 机制与本文概念的对应关系
    Java 机制接入方式最像什么不能忽略的边界
    Servlet Filter拿到 FilterChain，调用 chain.doFilter环绕式中间件可以不放行；普通方法返回不必等于整个异步请求结束
    Spring AOP @Around拿到 ProceedingJoinPoint，调用 proceed()方法级环绕扩展通过受代理调用生效；异步结果完成要另处理
    HandlerInterceptorpreHandle / postHandle / afterCompletion一组生命周期 HookpreHandle=false 可以中断；afterCompletion 有触发条件
    @EventListener收到被发布的事件，执行监听方法事件型 Hook 的类比默认同步分发，不是天然后台执行；没有通用 next 参数
    @Before匹配方法运行前触发 advice前置 Hook 的类比没有 proceed；正常返回后由 AOP 框架继续

    Filter 中的“前后”，是 doFilter 的前后

    // Servlet Filter 方法体示意；例子讨论同步处理路径。
long start = System.nanoTime();
try {
    if (!isAllowed(request)) {
        response.sendError(403);
        return; // 没有调用 chain，下游不会在这里被执行。
    }
    chain.doFilter(request, response);
} finally {
    logElapsed(System.nanoTime() - start);
}

    这里展示的是控制流形状。Servlet API 明确允许 Filter 决定是否调用链。不能因为看见 chain，就推导出“随便调用两遍做重试也安全”：请求体、响应状态和下游副作用都可能不允许这么做。查看 Filter 官方契约。

    Interceptor 很好地说明：Hook 也能阻止后续执行

    boolean preHandle(HttpServletRequest request,
                  HttpServletResponse response,
                  Object handler) {
    if (!isAllowed(request)) {
        response.sendError(403);
        return false; // DispatcherServlet 识别这个返回值。
    }
    return true;
}

    false 生效，是因为 Spring 的调度器按契约解释它。对当前拦截器来说，afterCompletion 要求它自己的 preHandle 成功完成且返回 true；postHandle 则是在 handler 正常执行后触发。异步请求还有额外调度规则。因此，不能把所有名字里含 after 的方法都当成 finally。查看 HandlerInterceptor 官方说明。

    不要把类比扩展成部署或安全结论。OncePerRequestFilter 的名字不表示“每次请求都创建一个对象”；Interceptor 也不应被不加区分地当成应用的完整安全边界。本页用它们解释调用与调度关系。

    状态隔离的关键：谁共用这块内存？

    这是最容易被术语误导的地方。Hook 可以有状态；Middleware 也可能并发串数据。用函数还是类、变量叫 self 还是 static，都不能单独决定安全与否。

    继续记忆检索的例子：同一个用户发出请求 A“查项目预算”，紧接着发出请求 B“查天气”。我们需要保证 A 拿到任务 A，B 拿到任务 B。

    并发沙盘：改变状态的归属

    固定交错顺序：A 写入 → B 写入 → A 读取 → B 读取。用于展示覆盖条件，不代表本仓库真实服务端一定允许同一实例并发。

    为什么 self 并不自动等于 request scope？

    self.task 的含义只是“这个对象的成员变量”。如果两次调用共用这个对象，就共用这个变量。如果每次调用拿到不同对象，它们才各有一份。Agent 生命周期、会话生命周期、请求生命周期可能不同。“给每个 Agent 配一个 Middleware”并不能证明“每个并发请求都有独立 Middleware”。

    Hook 也能保持独立状态

    // ctx 每次调用一份，多个回调共享本次 ctx。
before(ctx)  -> ctx.task = startSearch();
reason(ctx)  -> read(ctx.task);
finish(ctx)  -> cleanup(ctx.task);

    环绕方法可优先使用局部变量

    invoke(ctx, next) {
    Task task = startSearch();
    try { return next.handle(ctx); }
    finally { cleanup(task); }
}

    闭包、绑定对象、显式 Context、按调用 ID 维护的受控容器，都可以承载跨 Hook 的状态。全局 Map 也不必然错误：键是否唯一、并发访问是否安全、条目何时移除，才决定它是否适用。它的生命周期管理通常更复杂。

    检查并发时，连续问三件事：这份状态属于谁？会不会被另一次调用同时读写？成功、异常、取消后由谁释放？问清这些，比“把全局变量改成 self”更可靠。

    异常、异步、流式输出：为什么“之后”不一定是“结束”？

    成功之后、失败之后、最终结束，是不同的时机

    before();
try {
    Result result = core();
    afterSuccess(result);    // 只有 core 正常返回才到这里。
    return result;
} catch (Exception e) {
    onError(e);               // 出错通知，不自动等于吞掉异常。
    throw e;
} finally {
    onFinish();              // 正常返回和异常展开都会经过。
}

    如果释放资源写在 afterSuccess，异常时就可能漏掉。Hook 方案需要框架提供可靠的结束通知；环绕方案通常把资源管理写在 finally。但进程被强制终止、机器断电等情况，不在一般语言级 finally 的保证范围内。

    返回一个 Future，不等于 Future 已经完成

    同步方法的“调用返回”与“工作做完”通常接近；异步方法可能立即返回一个 CompletionStage，真正的工作还在后台。如果在方法返回时就停止计时或关闭资源，时间点就早了。

    // Java 异步示意：把收尾挂到实际结果完成时。
CompletionStage<Answer> invoke(Context ctx, AsyncHandler next) {
    long start = System.nanoTime();
    try {
        return next.handle(ctx).whenComplete((value, error) -> {
            logElapsed(System.nanoTime() - start);
        });
    } catch (RuntimeException | Error e) {
        // next 在返回 CompletionStage 之前就同步抛错。
        logElapsed(System.nanoTime() - start);
        throw e;
    }
}

    这里假设返回非空 CompletionStage，且计时函数不抛异常。不同异步类型的取消传播各有契约；这个示例不承诺自动取消底层任务。

    流式输出还有“第一段”和“最后一段”

    方法返回 Stream可能尚未消费
    →
    收到第一段首字延迟
    →
    持续输出可能中途取消
    →
    完成 / 失败 / 取消终止时机

    环绕“创建流对象”与环绕“消费完整个流”是不同的边界。一次 HTTP 请求结束、一次 Agent 回复结束、一次后台任务结束，也未必重合。读接口时，务必确认它包住的是哪个区间。

    后台任务的清理，不是调用 cancel 就万事大吉

    例如 Python 中启动了 asyncio.create_task()，调用 cancel() 只是发出取消请求。通常还需要等待任务处理取消，明确异常处理，以及关闭它占用的资源。真正的清理策略应依据任务与框架契约设计，不能只画一条“finally → cancel → 完美释放”的箭头。

    实际开发怎么选：从你需要的控制权出发

    只想在某个时刻做一件事

    例如模型调用前追加提示、工具执行后记日志。优先使用现成 Hook，确认输入是否可改、返回值是否生效。

    要对一段调用做前后配对

    例如计时、资源借用与归还、错误转换。优先寻找框架已有的环绕扩展点；同一方法内表达配对通常更清楚。

    要不执行核心就返回结果

    例如缓存命中。检查是否有 next/proceed 的短路能力，或者 Hook 明确支持替代结果。不能仅靠一个 before 方法名判断。

    要失败后重试

    先检查重入契约、错误分类和幂等性，再选择环绕调用或框架专用重试机制。把工具付款、写文件等操作重复执行，可能有副作用。

    能力横跨多个生命周期

    例如记忆模块要准备检索、注入上下文、回复后写回。把这些入口组织进同一个组件，统一依赖与配置；底层入口仍可以是 Hook。

    需要让模型选择一项业务动作

    例如查天气、查库存。通常定义 Tool，由模型提出工具调用，再由运行时执行。工具选择与生命周期扩展是不同问题。

    贯穿案例：记忆增强问答，三个角色如何合作？

    1. 用户问：“继续上次那个项目。”

      Agent 开始一轮回复。记忆组件在回复开始阶段准备检索。

    2. 调用模型前，注入检索到的相关信息。

      通过合适的 reasoning / model 扩展点修改输入。是同步等待还是后台并行，属于独立的调度选择。

    3. 模型判断还缺资料，提出 search_project 工具调用。

      Tool 提供具体业务能力。中间件可以在工具执行前后做检查、记录或结果处理。

    4. 模型生成最终回答。

      记忆组件在适当结束阶段写回信息、清理临时任务。多个生命周期入口服务同一个功能。

    Hook 解决“从哪里接入”；Middleware 解决“这个扩展能力如何组织并参与流程”；Tool 解决“可以执行什么具体业务动作”。在真实框架里，这些概念可以同时出现，并不是必须三选一。

    Tool 也不保证无状态或只由模型触发：应用代码可以直接调用它。这里描述的是典型 Agent 工具调用路径。

    把容易记错的几句话，改成准确的说法

    “Hook 是旁路，不会影响主流程。”

    很多 Hook 在主调用栈内同步执行，或在异步函数里被 await。慢 Hook 会拖慢主流程，异常可能向上传播。能否修改输入、阻止执行、替换输出，要看框架契约。只有明确异步投递且隔离执行时，才适合用“后台旁路”描述。

    “Middleware 是类，Hook 是函数，所以只有前者能有状态。”

    两种机制都能用函数、对象方法或闭包实现。是否有状态、状态归谁、是否共享，是与接入机制不同的维度。类的单例成员可能比每次调用独立的闭包更容易共享错状态。

    “before + after 就是 Around。”

    从输出看可能相似，但普通回调需要框架把时机和状态配好；Around 直接拿到后续执行能力，把前后逻辑放在同一调用中。若框架把两个回调设计成严格配对的完整协议，可以实现相近效果，但仍应检查异常与取消。

    “有 Middleware 就一定有 next，而且可以调用很多次。”

    有的框架以 next 表达继续执行的能力，也有的把多个生命周期方法组织成组件。多次执行下游是否允许，要单独检查。当前 AgentScope 的多个 on_* Hook 接收 next_handler；其中的 yield 是流式事件转发，不等于重新调用下游，更不能凭它推断重试安全性。

    “所有 after 都会逆序执行。”

    嵌套环绕调用通常自然倒序返回；普通回调列表的顺序完全取决于调度器。甚至同一框架里，不同种类 Hook 也可能有不同顺序。

    “Middleware 越多，代码就越清楚。”

    中间件也会带来顺序依赖：日志包在缓存外面统计全部请求，放在缓存里面可能只统计未命中的模型请求。注册越多，越需要说清输入变化、短路行为和边界。只为一个简单打印增加通用流水线，通常没有必要。

    “Hook 指的就是 React Hooks / Git hooks。”

    Hook 是被多种生态借用的名字。本文主要讨论框架生命周期扩展点。React Hooks 有渲染与状态管理规则；Git hooks 是 Git 命令在特定阶段调用脚本。不能仅凭同一个词套用所有语义。

    几个词，读代码时这样理解

    回调 callback
    把一段可调用代码交给别人，让对方按约定时机调用。
    下游 downstream
    当前组件之后的处理流程，不一定是网络远端服务。
    next / proceed
    代表继续执行后续处理的能力；具体可调用几次、传什么参数，由接口规定。
    短路 short-circuit
    在没有执行部分后续步骤的情况下，提前形成结果或结束本次处理。
    环绕 around
    扩展逻辑跨在核心调用的前后，并参与这段调用的执行边界。
    生命周期 lifecycle
    一次处理从开始到结束经历的阶段；先确定“一次处理”具体指什么。

    三道题：能判断具体接口，就是真的理解了

    不用背名字。看调度方式、返回值协议和状态归属。

    1. 一个 Hook 的 preHandle 返回 false，框架随后跳过核心处理。这说明什么？

    2. 两个并发请求使用同一个 Middleware 对象的 self.task，会怎样？

    3. 注册 A 包住 B，B 命中缓存直接返回。什么路径会发生？

    以后读一个新框架，只检查这五件事

    1. 在哪里触发？整轮回复、单次模型调用，还是单次工具调用？
    2. 传进来什么？只读事件、可变上下文，还是 next / proceed？
    3. 返回值算什么？被忽略、替换输入输出，还是控制继续 / 停止？
    4. 什么时候收尾？正常返回、异常、取消、流结束分别怎样处理？
    5. 状态和顺序归谁管？实例是否共享，调用是否并发，前后是同序还是逆序？

    Hook：框架在哪些时机调用你的扩展。
    Middleware：扩展组件如何被组合进处理流程。

    如果拿到了继续执行的能力，就重点看环绕与短路；如果只拿到某阶段的数据，就重点看回调契约。一个 Middleware 也可以实现多个 Hook，二者不必对立。
